# 顶点与顶点属性设计对比：neug、ladybug 与当前项目

结论前置：当前项目在标签容量、属性类型丰富度、列存编码与 MVCC 精细化方面有优势，但存在三处关键设计缺陷，建议写入改进计划：外部 ID 与主键列双源不一致、无类型标签的顶点 ID 编码、多 Tag 接口与单标签存储不匹配。另有删除路径与索引回收、复杂类型列存覆盖度等次级问题。

参考位置：

- neug 运行时顶点：`ref/neug/include/neug/storages/graph/`（`schema.h`、`vertex_table.h`、`vertex_timestamp.h`），属性与列：`ref/neug/include/neug/utils/property/`，标识与类型：`ref/neug/include/neug/utils/property/types.h`、`ref/neug/include/neug/common/types.h`
- ladybug 顶点标识与类型：`ref/ladybug/src/include/common/types/types.h`，目录与表：`ref/ladybug/src/include/catalog/`、`ref/ladybug/src/include/storage/table/`（`node_table.h`、`node_group.h`、`chunked_node_group.h`、`column_chunk_data.h`）
- 当前项目：`crates/graphdb-core/src/types/storage_ids.rs`、`crates/graphdb-core/src/vertex_edge_path.rs`、`crates/graphdb-core/src/types/tag.rs`，存储：`crates/graphdb-storage/src/vertex.rs`、`crates/graphdb-storage/src/vertex/vertex_table/core.rs`、`crates/graphdb-storage/src/vertex/id_indexer.rs`、`crates/graphdb-storage/src/vertex/vertex_timestamp.rs`、`crates/graphdb-storage/src/vertex/column/column.rs`，写入链路：`crates/graphdb-storage/src/engine/graph_storage/writer/vertex.rs`、`crates/graphdb-storage/src/engine/graph_storage/context/vertex_ops/write.rs`、`crates/graphdb-storage/src/engine/graph_storage/schema_engine.rs`

## 一、三者模型速览

neug 采用单标签单主键模型。顶点逻辑身份就是主键值，内部行号是按标签分配的 32 位整数，标签最多 256 个。每个标签一张顶点表，属性按列存放，主键列不重复存入属性表，而是通过无锁哈希索引在主键值与内部行号之间映射。顶点有效性用插入时间戳数组加删除集合表达，查询时按时间戳过滤。

ladybug 采用表即标签模型。顶点逻辑身份是表 ID 加行偏移的二元组，表 ID 为 64 位，行偏移为 64 位。每个标签一张节点表，表内按约 13 万行分组、组内按约 2 千行分块，组织为列块。属性在目录中注册为带列号的定义，主键为强制列并建有主键哈希索引。顶点值在查询层表达为包含内部 ID、标签与全部属性的结构体。

当前项目采用类 Nebula 的多 Tag 接口加按标签分表存储。顶点对外身份是变长字节标识，支持 64 位整数与最长 32 字节字符串，标签为 32 位整数。接口层一个顶点可携带多个 Tag，每个 Tag 自带属性映射，顶点自身还有一份顶点级属性映射。存储层每个标签一张分片顶点表，表内由外部键到 32 位内部行号的双向索引、列式属性存储、行级时间戳三部分组成。拓扑只存于边 CSR，顶点表不存邻接。

## 二、逐项对比

### 顶点标识

neug 区分外部主键与内部行号，内部行号为 32 位，标签 8 位，全局身份可拼装。ladybug 用表 ID 加 64 位偏移，天然全局唯一且可直接定位分组。当前项目用最长 32 字节的无类型字节串统一表达整数与字符串，优点是兼容 Nebula 风格的混合 ID，缺点是类型信息丢失：8 字节字符串与 8 字节整数无法区分，整数用有符号大端字节排序导致负数顺序错误，无符号大整数在转换路径中可能被按有符号解读，超长字符串在部分构造路径静默截断。

### 标签模型

neug 单顶点单标签，上限 256，简单但扩展受限。ladybug 单顶点单表，表 ID 空间大，扩展性好。当前项目接口允许多 Tag，存储按标签分表。写入时同一顶点标识会被扇出到多个标签表，每个表独立分配内部行号与生命周期；读取按单标签返回单 Tag 视图。这造成同一逻辑顶点的多份物理行之间没有统一身份约束，跨表一致性依赖调用层循环保证，而不是存储层原子保证。

### 主键与外部 ID 的关系

这是三者分歧最大的一点。neug 主键即索引键，单源，不可能分叉。ladybug 主键是表内一列，索引建于该列之上，单源。当前项目存在两个并行的键：写入入口传入的外部标识，以及模式中声明的主键属性列。插入路径不对二者是否一致做强制校验与自动填充，更新主键列与重建索引键是两条独立路径。因此可能出现索引键与主键列值不一致，而读取、删边、建索引各取其一的隐患。附带问题是主键类型校验允许布尔、浮点、日期、UUID 等多种类型，但索引键枚举只有整数与文本两种，宽主键类型没有对应的索引键表达。

### 属性类型与列存

neug 属性类型较窄，以整数族、浮点、字符串、日期时间为主，实现简单快速，但表达力弱。ladybug 类型体系完整，为布尔位 packed、字符串字典、列表、结构体等分别设置列块子类，并配空值列、压缩、统计信息。当前项目接口类型最丰富，还包含向量、地理、JSON 等，且列层配有字典、游程、位 pack、多压缩算法、溢出文件、 zone map 与基数估计，纸面能力最强。落差在于复杂类型在列层的实际覆盖不足，多数走通用回退路径，享受不到分类型编码与统计剪枝的好处，文档中列出的定宽与变宽映射表也只覆盖标量子集。

### 有效性与删除

neug 为顶点级时间戳加删除集合。ladybug 为版本信息加撤销缓冲加本地未提交表，配合预写日志与检查点。当前项目为行级起止时间戳加逐列版本链加行可见性三层结构，历史读能力最细。问题在删除只标记时间戳而不摘除索引条目，存活枚举直接取自索引而不经过时间戳过滤，导致存活集合可能包含已删行；紧凑重用存在时间戳复用与空闲表复用两条路径，插入后删除再插入走时间戳复位，而索引层空闲复用走另一条路径，两者缺乏统一不变量说明。

### 并发与工程化

neug 索引为无锁结构，适合高并发点查。ladybug 以页式分组与本地表处理写事务。当前项目以分片表加分片锁提供表级并发，批量写入配有容量预留与预检上下文，工程化程度较好。代价是跨分片的同一外部标识映射、跨标签的多 Tag 写入、顶点删边级联等仍需多步循环，失败回滚为逆序补偿而非原子提交。

## 三、当前项目的优点

- 标签用 32 位，优于 neug 的 8 位上限，与单节点规模匹配。
- 顶点标识统一兼容整数与字符串，迁移 Nebula 风格数据更顺。
- 属性类型与值体系表达力强，为向量与文档类负载留出空间。
- 列存编码、溢出、zone map、基数估计、版本链等优化点齐全，点查与分析各有抓手。
- 模式版本历史、分片表、批量预检与预留容量等工程化设施较完整。

## 四、当前项目需要改进的方面

以下按严重程度排序，前三项为关键缺陷，后三项为次级但应排期处理。描述中只讲行为与方向，不展开代码细节。

1. 统一外部标识与主键列的单源关系
   现象：外部写入键与主键属性列可各自独立演进，无强制一致约束。
   改进方向：二选一并贯彻到底。要么主键列即身份，索引键必须由主键列值派生，写入时从属性中提取主键并拒绝缺失或不一致；要么外部标识即身份，主键声明仅为约束与索引提示，禁止更新主键列而不经过身份变更通道。同时收窄主键允许类型与索引键表达能力的差距，未支持的类型要么禁用作主键，要么补齐索引键编码。

2. 给顶点标识加类型标签或拆分双通道
   现象：变长字节串无类型位，8 字节临界、负数排序、大整数符号、超长截断均存在误判风险。
   改进方向：引入显式类型位或改用枚举式标识，排序比较按类型分组后再按值比较，整数比较用数值语义而非字节序，超长输入一律报错而非截断或告警后截断。边界行为需要单测锁定。

3. 收敛多 Tag 接口与单标签存储的语义
   现象：接口多 Tag、存储单标签，属性在顶点级与 Tag 级重复存放，查询语义靠多层回退拼凑，同一标识扇出多表后缺乏跨表原子性。
   改进方向：明确产品语义。若保留多 Tag，则定义主从关系、跨表读写合并规则、跨表删除原子性与回滚边界，并消除顶点级与 Tag 级属性的重复存放。若实际为单标签，则接口应收敛为单标签单属性映射，删除按标签路由而非全表扇出。无论哪种，都需要统一属性查找的优先级说明，避免按名回退与按标签名返回整映射的隐式行为。

4. 统一删除与回收的不变量
   现象：删除标记与索引摘除分离，存活枚举与可见性判断各取其一，复用存在两条路径。
   改进方向：规定删除是否摘索引、存活枚举是否过滤时间戳、复用走哪一条路径，并让删除、枚举、紧凑、重插入四处实现同一不变量。建议删除路径的索引处理、存活枚举的过滤条件、复用入口三者只保留一种真相来源。

5. 补齐复杂类型的列存路径
   现象：丰富类型多走通用回退，压缩、统计、剪枝收益只落在标量上。
   改进方向：为常用复杂类型逐个明确存储策略，是原生列块、字典加溢出，还是退化为二进制加索引，并补齐空值语义与统计信息。未明确的类型应在建表时给出可预期的能力说明，而不是静默降级。

6. 收敛负数标识与端点编码的边界
   现象：上层写入拒绝负整数标识，但底层标识与边端点编码仍可表达负数，校验位置不一致。
   改进方向：将标识合法性判断下沉到一处，边端点编码的区间转换规则与顶点标识规则保持一致，并在写入、恢复、边级联删除三处使用同一校验入口。

## 五、与 neug、ladybug 的取舍总结

neug 的优点是简单可靠，单源主键加窄类型使正确性易于保证，缺点是标签上限与类型表达力不足，大规模与多模负载吃力。ladybug 的优点是类型完整、列块分层清晰、主键与索引单源，缺点是实现重量大，页组、溢出、压缩、版本、本地表、日志检查点全套机制的复杂度高于单节点轻量目标。当前项目站在两者之后，取了丰富的类型与细粒度 MVCC，但把身份这一最基础的不变量做成了双源，把标签语义做成了接口与存储两张皮，这是需要优先偿还的设计债。建议先修复身份与标识两项，再收敛标签语义，最后补齐复杂类型列存。
