# Ladybug / linkrs / Nebula 计划节点类型对比分析

> 分析对象：
> - **Ladybug** — `https://github.com/LadybugDB/ladybug`（C++，Kuzu 复刻/更名版本，列式磁盘存储 + CSR + 向量化/因子化/morsel 并行执行）
> - **linkrs** — `https://github.com/kkkqkx123/linkrs`（Rust，单节点图数据库，CSR + MVCC；**明确为 NebulaGraph 的 Rust 重写版**）
> - **Nebula** — `https://github.com/vesoft-inc/nebula`（C++，分布式图数据库，linkrs 的内核参照原点）
>
> 三个仓库均已通过 `git clone https://gh-proxy.com/https://github.com/...` 拉取至本地 `analysis/` 目录。
> 本文聚焦**查询计划节点（Plan Node）类型**的对比，并分析 linkrs 在计划节点层面的不足。
> 文中所有"节点清单 / 枚举定义"均基于实际源码核实，关键源码索引附于文末。

---

## 1. 项目背景与计划节点体系总览

三个项目都是**图数据库**，但计划节点的设计哲学源于两条不同的内核血统链：

```
Kuzu  ─────────────▶  Ladybug          (因子化 / 向量化执行)
NebulaGraph  ───────▶  Nebula  (单一计划表示，查询 + 管理合一)
        └────────────▶  linkrs  (Rust 重写，逻辑/物理分离 + 更现代的枚举体系)
```

| 维度 | Ladybug | linkrs | Nebula |
|------|---------|--------|--------|
| 内核血统 | Kuzu 复刻 | NebulaGraph 的 Rust 重写 | 分布式图数据库，linkrs 的参照原点 |
| 执行模型 | 向量化 + **因子化（factorized）** + morsel 并行 | **流式（tuple-at-a-time）** 执行器 | 流式执行器（executor 按节点类别分目录） |
| 图遍历风格 | 原生递归/打包扩展算子 | `Expand`/`Traverse` + 原生递归片段（`RecursiveFragmentSpec` 四变体） | `GetNeighbors`/`Expand`/`Traverse` 流式 |
| 逻辑/物理分离 | 是（逻辑枚举 + 物理枚举） | 是（逻辑 `PlanNodeEnum` + 物理 `PhysicalPlan`） | **否（逻辑与物理合一，单一枚举）** |
| 计划节点总数 | 逻辑 60 + 物理 69（两枚举） | 逻辑 **78**（vector 下 81）单枚举 + 物理 spec 模型 | **136**（单一 `PlanNode::Kind` 枚举） |
| 节点构成 | 查询 + DDL 混合（逻辑/物理各一枚举） | 查询 + DDL 混合（参数化子枚举压缩） | 查询(~50) + 管理/元数据(~86) 混合于同一枚举 |

三者最大的共性是把"计划节点"作为查询引擎的一等抽象；最大差异在于：
1. **逻辑/物理是否分离** —— Ladybug、linkrs 显式分离；Nebula 合一。
2. **图遍历如何表达** —— Ladybug 走因子化（Kuzu 基因），Nebula/linkrs 走流式（Nebula 基因）。
3. **linkrs 是 Nebula 的 Rust 移植**：其 `__analysis__` 文档每行列均标注"对应 nebula-graph"，并有专门的"与 nebula-graph 的对比分析"章节——这解释了为何 linkrs 的节点命名（`GetNeighbors`/`HashInnerJoin`/`FulltextIndexScan` 等）与 Nebula 高度雷同。

## 2. 计划节点类型盘点

### 2.1 Ladybug 的计划节点

Ladybug 用**两个独立枚举**分别表示逻辑计划与物理计划：

**逻辑计划** — `LogicalOperatorType`（`src/include/planner/operator/logical_operator.h`，共 **60** 个类型）：

| 类别 | 节点类型 |
|------|---------|
| 扫描/访问 | `SCAN_NODE_TABLE`、`SCAN_REL_TABLE`、`EXPRESSIONS_SCAN`、`DUMMY_SCAN`、`INDEX_LOOK_UP`、`QUERY_PRIMARY_KEY_LOOKUP` |
| 图遍历（因子化） | `EXTEND`、`PACKED_EXTEND`、`RECURSIVE_EXTEND`、`MULTIPLICITY_REDUCER`、`NODE_LABEL_FILTER`、`SEMI_MASKER`、`PATH_PROPERTY_PROBE`、`REACHABLE_COUNT`、`COUNT_REL_TABLE`、`REL_DEGREE_TABLE` |
| 关系算子 | `FILTER`、`PROJECTION`、`DISTINCT`、`AGGREGATE`、`ORDER_BY`、`LIMIT`、`CROSS_PRODUCT`、`HASH_JOIN`、`INTERSECT`、`UNION_ALL`、`MERGE`、`UNWIND`、`FLATTEN`、`ACCUMULATE`、`PARTITIONER` |
| DDL / DML | `CREATE_GRAPH`、`CREATE_TABLE`、`CREATE_INDEX`、`CREATE_TYPE`、`CREATE_SEQUENCE`、`CREATE_MACRO`、`ALTER`、`DROP`、`DELETE`、`INSERT`、`SET_PROPERTY`、`COPY_FROM`、`COPY_TO`、`ANALYZE`、`ATTACH_DATABASE`、`DETACH_DATABASE`、`IMPORT_DATABASE`、`EXPORT_DATABASE`、`USE_DATABASE`、`USE_GRAPH`、`TRANSACTION`、`EXPLAIN` |
| 控制/杂项 | `NOOP`、`EMPTY_RESULT`、`DUMMY_SINK`、`STANDALONE_CALL`、`TABLE_FUNCTION_CALL`、`EXTENSION_CLAUSE`、`UNWIND_DEDUPLICATE` |

**物理计划** — `PhysicalOperatorType`（`src/include/processor/operator/physical_operator.h`，共 **69** 个类型）。
物理计划在逻辑计划基础上把"一个逻辑算子"拆成"多个执行阶段"，典型拆分：

- 连接：`HASH_JOIN` → `HASH_JOIN_BUILD` + `HASH_JOIN_PROBE`
- 聚合：`AGGREGATE` → `AGGREGATE_FINALIZE` + `AGGREGATE_SCAN`
- 排序/TopK：`ORDER_BY` → `ORDER_BY_MERGE` + `ORDER_BY_SCAN`；`TOP_K` → `TOP_K_SCAN`
- 集合：`UNION_ALL` → `UNION_ALL_SCAN`；`INTERSECT` → `INTERSECT_BUILD` + `INTERSECT`
- 额外物理节点：`RESULT_COLLECTOR`、`PROFILE`、`SKIP`、`BATCH_INSERT`、`PACKED_FILTERED_COUNT`、`PRIMARY_KEY_SCAN_NODE_TABLE`、`INSTALL_EXTENSION`/`LOAD_EXTENSION`/`UNINSTALL_EXTENSION`、`DUMMY_SIMPLE_SINK` 等

> **要点**：Ladybug 的物理计划节点数量（69）多于逻辑计划（60），差距正是"build/probe、scan/merge"这类执行阶段拆分带来的。

### 2.2 linkrs 的计划节点

linkrs 的逻辑计划由单一枚举 `PlanNodeEnum` 表示（`crates/graphdb-query/src/query/planning/plan/core/nodes/base/plan_node_enum.rs`，**78 个变体**，启用 `vector` feature 时追加 3 个向量节点为 81 个），并通过 `PlanNodeCategory` 显式分为 **9 类**：

| 类别（PlanNodeCategory） | 节点类型 | 数量 |
|------|---------|------|
| Access（访问层） | `Start`、`GetVertices`、`GetEdges`、`GetNeighbors`、`ScanVertices`、`ScanEdges`、`IndexScan` | 7 |
| Operation（操作层） | `Project`、`Filter`、`Sort`、`Limit`、`TopN`、`Sample`、`Dedup`、`Aggregate`、`Window` | 9 |
| Join（连接层） | `InnerJoin`、`LeftJoin`、`RightJoin`、`CrossJoin`、`FullOuterJoin`、`SemiJoin` | 6 |
| Traversal（遍历层） | `Expand`、`ExpandAll`、`Traverse`、`AppendVertices`、`BiExpand`、`BiTraverse` | 6 |
| ControlFlow（控制流） | `Argument`、`Loop`、`PassThrough`、`Select`、`BeginTransaction`、`Commit`、`Rollback` | 7 |
| DataProcessing（数据处理） | `DataCollect`、`Remove`、`PatternApply`、`RollUpApply`、`Union`、`Minus`、`Intersect`、`Unwind`、`Materialize`、`Assign`、`Apply` | 11 |
| Algorithm（算法层） | `MultiShortestPath`、`BFSShortest`、`AllPaths`、`ShortestPath` | 4 |
| Management（管理/DDL，参数化子枚举） | `SpaceManage`、`TagManage`、`EdgeManage`、`IndexManage`、`UserManage`、`FulltextManage`、`VectorManage` | 7 |
| Management-Data（数据修改/DDL 数据） | `InsertVertices`、`InsertEdges`、`DeleteVertices`、`DeleteEdges`、`DeleteTags`、`DeleteIndex`、`PipeDeleteVertices`、`PipeDeleteEdges`、`Update`、`UpdateVertices`、`UpdateEdges` | 11 |
| Stats / System（统计/系统信息） | `ShowStats`、`ShowConfigs`、`ShowQueries`、`ShowSessions` | 4 |
| DataAccess（全文/向量，含 feature-gated） | `FulltextSearch`、`FulltextLookup`、`MatchFulltext`；`VectorSearch`、`VectorLookup`、`VectorMatch`（仅 `vector`） | 3 + 3 |

linkrs 的**物理计划**不采用扁平枚举，而是一套基于 `Spec` 的表达（`crates/graphdb-query/src/query/executor/streaming/plan/`）：`OperatorKindSpec`（`types.rs:418`）、`BinaryOperatorSpec`（`fragment_ops.rs:613`）、`FragmentKind`（`types.rs:241`）、`PhysicalPlan`/`FragmentGraph` 等。逻辑计划经由 `PhysicalPlanBuilder` 落地为物理计划。

> **要点**：linkrs 用一个扁平大枚举表达逻辑计划（78 种，vector 下 81 种），并把 DDL/DCL 通过"参数化子枚举"压到 9 类之中；物理计划则用 spec/片段（fragment）模型表达，与逻辑枚举解耦。

### 2.3 Nebula 的计划节点（linkrs 的参照原点）

Nebula 的计划节点由**单一枚举** `PlanNode::Kind` 定义（`src/graph/planner/plan/PlanNode.h`，共 **136** 个 kind），**不区分逻辑/物理**——规划器（Planner）直接产出执行计划，优化器（`src/graph/optimizer/`，规则集 `rule/`）在同一套节点结构上做改写。executor 按节点类别分目录（`admin`/`algo`/`logic`/`maintain`/`mutate`/`query`），与 `Kind` 一一对应。

这 136 个节点中，**约 50 个为"查询节点"，约 86 个为管理/元数据/DDL 命令**，二者被放在同一枚举里。Nebula 内部用 `isQueryNode()`（`kind_ <= Kind::kStart`）区分：从 `kGetNeighbors` 到 `kStart` 共 50 个为查询节点，其后全部为管理类。按 enum 注释分组如下：

| 类别（依据 enum 注释） | 节点（Kind） | 数量 |
|------|---------|------|
| Query（图遍历/访问） | `kGetNeighbors`、`kGetVertices`、`kGetEdges`、`kExpand`、`kExpandAll`、`kTraverse`、`kAppendVertices`、`kShortestPath` | 8 |
| Index scan（索引/扫描，注释标 `TODO(yee): refactor in logical plan`） | `kIndexScan`、`kTagIndexFullScan`、`kTagIndexPrefixScan`、`kTagIndexRangeScan`、`kEdgeIndexFullScan`、`kEdgeIndexPrefixScan`、`kEdgeIndexRangeScan`、`kScanVertices`、`kScanEdges`、`kFulltextIndexScan`、`kValue` | 11 |
| 关系/集合/连接/算法 | `kFilter`、`kUnion`、`kUnionAllVersionVar`、`kIntersect`、`kMinus`、`kProject`、`kUnwind`、`kSort`、`kTopN`、`kLimit`、`kSample`、`kAggregate`、`kDedup`、`kAssign`、`kBFSShortest`、`kMultiShortestPath`、`kAllPaths`、`kCartesianProduct`、`kSubgraph`、`kDataCollect`、`kInnerJoin`、`kHashLeftJoin`、`kHashInnerJoin`、`kCrossJoin`、`kRollUpApply`、`kPatternApply`、`kArgument` | 27 |
| Logic（控制流） | `kSelect`、`kLoop`、`kPassThrough`、`kStart` | 4 |
| schema related（DDL） | `kCreateSpace`、`kCreateSpaceAs`、`kCreateTag`、`kCreateEdge`、`kDescSpace`、`kShowCreateSpace`、`kDescTag`、`kDescEdge`、`kAlterTag`、`kAlterEdge`、`kShowSpaces`、`kSwitchSpace`、`kShowTags`、`kShowEdges`、`kShowCreateTag`、`kShowCreateEdge`、`kDropSpace`、`kClearSpace`、`kDropTag`、`kDropEdge`、`kAlterSpace` | 21 |
| index related（含 Insert/Job） | `kCreateTagIndex`、`kCreateEdgeIndex`、`kCreateFTIndex`、`kDropFTIndex`、`kDropTagIndex`、`kDropEdgeIndex`、`kDescTagIndex`、`kDescEdgeIndex`、`kShowCreateTagIndex`、`kShowCreateEdgeIndex`、`kShowTagIndexes`、`kShowEdgeIndexes`、`kShowTagIndexStatus`、`kShowEdgeIndexStatus`、`kInsertVertices`、`kInsertEdges`、`kSubmitJob`、`kShowHosts` | 18 |
| user related | `kCreateUser`、`kDropUser`、`kUpdateUser`、`kGrantRole`、`kRevokeRole`、`kChangePassword`、`kListUserRoles`、`kListUsers`、`kListRoles`、`kDescribeUser` | 10 |
| Snapshot | `kCreateSnapshot`、`kDropSnapshot`、`kShowSnapshots` | 3 |
| Update/Delete | `kDeleteVertices`、`kDeleteEdges`、`kUpdateVertex`、`kDeleteTags`、`kUpdateEdge` | 5 |
| Show | `kShowParts`、`kShowCharset`、`kShowCollation`、`kShowStats`、`kShowConfigs`、`kSetConfig`、`kGetConfig`、`kShowMetaLeader` | 8 |
| zone related | `kShowZones`、`kMergeZone`、`kRenameZone`、`kDropZone`、`kDivideZone`、`kAddHosts`、`kDropHosts`、`kDescribeZone`、`kAddHostsIntoZone` | 9 |
| listener related | `kAddListener`、`kRemoveListener`、`kShowListener` | 3 |
| service related | `kShowServiceClients`、`kShowFTIndexes`、`kSignInService`、`kSignOutService`、`kShowSessions`、`kUpdateSession`、`kKillSession`、`kShowQueries`、`kKillQuery` | 9 |

> **要点**：Nebula 的计划节点数量是三者中最大的（136），但其中**近 2/3（~86）是管理/元数据命令**而非查询算子。这正是 linkrs 早期节点枚举膨胀到 90+ 变体的根源——linkrs 继承了 Nebula 庞大的 DDL 节点面，又叠加了自身单机场景并不需要的部分。

## 3. 计划节点类型逐项对比

### 3.1 图遍历 / 递归查询（核心差异）

| 能力 | Ladybug（因子化） | linkrs（流式） | Nebula（流式，linkrs 原点） |
|------|------------------|----------------|------------------------------|
| 单跳扩展 | `EXTEND` | `Expand` / `ExpandAll` / `Traverse` | `kExpand` / `kExpandAll` / `kTraverse`（`kGetNeighbors` 取邻居） |
| 双向扩展 | （单向组合） | `BiExpand` / `BiTraverse`（原生） | 无独立节点（靠 `kTraverse`+筛选） |
| 变量长度/递归 | `RECURSIVE_EXTEND` + `PACKED_EXTEND`（**原生递归算子**） | `RecursiveFragmentSpec`（SP/MultiSP/BFS/AllPaths）+ `variable_length_path_planner.rs`（**原生递归算子**） | `kLoop` + `kExpand` 模拟 |
| 因子化半连接掩码 | `SEMI_MASKER`（**原生**） | 无对应节点 | 无对应节点 |
| 多重性消除 | `MULTIPLICITY_REDUCER`（**原生**） | 用 `Dedup` 近似 | 用 `kDedup` 近似 |
| 路径/算法 | （无独立节点） | `ShortestPath`/`AllPaths`/`MultiShortestPath`/`BFSShortest` | `kShortestPath`/`kAllPaths`/`kMultiShortestPath`/`kBFSShortest`/`kSubgraph` |

**差异本质**：Ladybug 把图遍历深度融入**因子化执行模型**（Kuzu 遗产），递归扩展、半连接掩码、多重性消除都是一等公民算子；linkrs 走**流式**路线，但已为路径类查询引入**原生递归片段算子**（`RecursiveFragmentSpec` 四变体 + VLP 规划器），`LoopNode` 仅保留为通用控制流；Nebula 仍依赖 `kLoop` + `kExpand` 模拟。linkrs 的递归建模已领先于其参照原点 Nebula（详见 §5.2 修订）。

### 3.2 关系算子对比（高度重叠，连接类型有落差）

`Filter`、`Project`、`Aggregate`、`Sort`、`Limit`、`TopN`、`Dedup`、`CrossProduct/Join`、`Union`/`Intersect`/`Minus`、`Unwind` 等三者都有对应节点，覆盖面相当。差异点集中在**连接类型**：

| 连接类型 | Ladybug（逻辑层） | linkrs（逻辑层） | Nebula（单一枚举） |
|---------|------------------|------------------|---------------------|
| Inner | `HASH_JOIN`（物理层 build/probe 展开） | `InnerJoin` | `kInnerJoin`、`kHashInnerJoin` |
| Left | （物理层） | `LeftJoin` | `kHashLeftJoin` |
| Right | 无 | `RightJoin` | **无** |
| FullOuter | 无 | `FullOuterJoin` | **无** |
| Semi | 无 | `SemiJoin` | **无** |
| Cross | `CROSS_PRODUCT` | `CrossJoin` | `kCrossJoin` |
| Apply 变体 | 无 | `Apply`、`PatternApply`、`RollUpApply` | `kPatternApply`、`kRollUpApply` |

- **linkrs 的连接覆盖面其实宽于其参照原点 Nebula**：linkrs 有 `RightJoin`/`FullOuterJoin`/`SemiJoin`/`LeftJoin`，而 Nebula 只有 `Inner`/`HashLeft`/`HashInner`/`Cross` + Apply 变体——**Nebula 根本没有 Right/FullOuter/Semi 节点**。
- **Ladybug** 逻辑层连接变体最少，主要依赖物理层的 build/probe 拆分表达。

### 3.3 DDL / DCL 体量与风格

- **Nebula**：DDL/DCL/元数据命令占节点主体的 ~86/136（约 63%），涵盖 Space/Tag/Edge/Index/User/Snapshot/Zone/Listener/Service/FTS 等全方位集群管理——因为 Nebula 是**分布式**系统，这些节点对应真实的控制面操作（如 `kAddHosts`、`kSubmitJob`、`kCreateSnapshot`）。
- **linkrs**：**22** 个顶层管理/DDL 节点（7 参数化子枚举 + 11 数据修改 + 4 统计/系统），每个参数化子枚举再包裹若干具体 DDL 子变体（合计 48 个具体管理节点），是逻辑枚举中体量最大的部分。linkrs 是**单节点**数据库，却继承了 Nebula 庞大的 DDL 面，且近期用"参数化子枚举"把 90+ 变体压到 78（`manage_node_enums.rs` 顶部注释自承 "reduced the total variant count from 90+ to ~50"，后续又扩展回 78）。
- **Ladybug**：DDL 同样并入同一枚举，但更偏向"关系表 + 图"混合（还有 `CREATE_TYPE`、`CREATE_SEQUENCE`、`CREATE_MACRO`、`ANALYZE`），反映 Kuzu 的关系/图双模型定位。

> 三者都把 DDL 并入计划节点体系，但 **Nebula 的 DDL 占比最高且是架构刚需**，linkrs 则是"继承过度"——单节点场景下大量 Nebula 风格的管理节点并无对应执行价值。

### 3.4 全文 / 向量检索

- **Nebula**：有 `kFulltextIndexScan`（全文索引扫描）与 `kCreateFTIndex`/`kDropFTIndex`/`kShowFTIndexes`（FTS 管理），但**枚举中无向量检索节点**（向量能力非该版本内核枚举的一部分）。
- **linkrs**：有独立 `FulltextSearch`/`FulltextLookup`/`MatchFulltext`，以及（feature-gated）`VectorSearch`/`VectorLookup`/`VectorMatch` 节点，归属 `DataAccess` 类——在全文/向量维度上比 Nebula 本版枚举**更前沿**。
- **Ladybug**：C++ 引擎内未将 FTS/向量作为计划节点（索引仅 `HASH`/`ART`）。

### 3.5 逻辑 / 物理分离架构对比（三者根本分歧）

| 架构 | Ladybug | linkrs | Nebula |
|------|---------|--------|--------|
| 是否分离 | 是 | 是 | **否（合一）** |
| 逻辑表示 | `LogicalOperatorType`（60） | `PlanNodeEnum`（~75） | 无独立逻辑层 |
| 物理表示 | `PhysicalOperatorType`（69） | spec/fragment 模型 | 即 `PlanNode::Kind`（136）本身 |
| 优化器作用对象 | 逻辑节点 → 物理节点（CBO + DP） | 逻辑枚举 → 物理 spec（启发式 + CBO + 反馈闭环） | 同一 `Kind` 节点的规则改写 |
| 阶段拆分 | build/probe、scan/merge | `PhysicalPlanBuilder` 落地 | 无（单阶段） |

**关键判断**：Nebula 采用"逻辑与物理合一"的单一计划表示，规划器直接产出可执行计划；Ladybug 与 linkrs 则都采用了更现代的"逻辑/物理两阶段"分离。linkrs 作为 Nebula 的 Rust 移植，**在架构层面反而比原点更先进**（补回了逻辑/物理分离），但在"节点命名与粒度"上仍明显带着 Nebula 的历史包袱（见 5.7）。

## 4. 实现方式对比

### 4.1 节点定义机制

| 方面 | Ladybug（C++） | linkrs（Rust） | Nebula（C++） |
|------|---------------|----------------|----------------|
| 类型声明 | 逻辑/物理两个 `enum class` | 单一 `enum PlanNodeEnum` + 每节点一个 `struct` | 单一 `enum class PlanNode::Kind`（136） |
| 类型判别 | 基类持 `operatorType_`；`constCast`/`ptrCast`（`dynamic_cast` 校验）向下转型 | 基于枚举的 `is_*`/`as_*`/`category()`，由宏批量生成 | 基类 `kind_` 字段 + `asNode<T>()`（`DCHECK(dynamic_cast)`） |
| 穷尽性 | `switch` + `default` 兜底（非穷尽） | `match` 穷尽检查，编译器强制覆盖 | `switch` + `default`（非穷尽） |
| 访问者 | — | — | `PlanNodeVisitor`（visitor 模式，`accept()`） |
| 依赖建模 | 基类 `children` 向量（0/1/2/多输入统一） | 显式 trait：`ZeroInputNode`/`SingleInputNode`/`BinaryInputNode`/`MultipleInputNode` | 基类 `dependencies_` 向量 + `SingleDependencyNode`/`SingleInputNode`/`BinaryInputNode`/`VariableDependencyNode` 派生 |

linkrs 用 Rust 枚举 + 宏获得了**编译期穷尽性**与类型安全；代价是 `plan_node_enum.rs` 882 行大量重复的宏展开（`is_*`/`as_*`/`as_*_mut`/`type_name`/`category`/`describe` 每个节点各一份）。Nebula 与 Ladybug 同属 C++ 阵营，依赖 `dynamic_cast`/`DCHECK` 运行时校验，非穷尽。

### 4.2 分类元数据

- **linkrs**：显式 `PlanNodeCategory` 枚举，附 `is_leaf()`（Access/DataAccess）、`is_root()`（ControlFlow/DataProcessing）、`supports_parallelism()`（Operation/DataProcessing/Algorithm）等语义方法，直接服务于优化器决策。
- **Ladybug**：逻辑层只有类型枚举，无等价"类别"抽象；相关判断散落在 `LogicalOperatorUtils::isUpdate()`、`isAccHashJoin()` 等辅助函数。
- **Nebula**：以 `isQueryNode()`（`kind_ <= kStart`）做"查询 vs 管理"的粗粒度二分，无 linkrs 那种细粒度类别语义方法。这反映出 Nebula 的"类别"需求被其分布式执行框架（executor 目录天然按类别划分）隐式满足了。

### 4.3 优化器与计划节点协同

- **Ladybug**：`join_order/join_plan_solver`（连接重排）+ `subplans_table`（动态规划）+ `CardinalityEstimator` + `CostModel`，计划节点自带 `cardinality`/`cost` 字段。
- **linkrs**：启发式优化器（规则约 53 条）+ CBO（`cost_based/`）+ 执行反馈闭环（`stats/feedback/`，EWMA 选择性修正）+ `EXPLAIN`/`PROFILE` 支持 table/dot/tree/json 四格式。
- **Nebula**：规则化优化器（`src/graph/optimizer/`，`OptRule` + `rule/` 规则集 + `OptGroup` 分组），在**同一套 `PlanNode::Kind` 节点**上做等价变换，无独立物理表示层。

三者都形成了"计划节点 → 优化器规则 → 物理落地"的闭环，但 linkrs 的优化器工程化（规则计数、反馈回写、多格式 EXPLAIN）在文档层面最显完整；Nebula 的独到之处是用单一节点表示贯穿规划与优化，减少了"逻辑→物理"转换的复杂度（但牺牲了物理阶段拆分的表达力）。

## 5. linkrs 在计划节点层面的不足

以下结论均基于源码核实，按与"计划节点类型"主题的相关度排序。linkrs 作为 Nebula 的 Rust 移植，其不足多与"移植时的取舍与文档滞后"相关。

### 5.1 【严重】计划节点文档与实现对齐失效（且有事实性错误）

`crates/graphdb-query/src/query/planning/plan/core/__analysis__/` 下两份"权威"设计文档曾与实际代码严重脱节（**2026-08-16 已重写修复，本节注明历史问题与修复结果**）：

- **历史问题**：`plan_node_category_analysis.md` / `plan_node_dependency_analysis.md` 曾描述一个 **69 节点、8 类、对齐 NebulaGraph** 的旧模型：含 `HashInnerJoin`、`HashLeftJoin`、`FulltextIndexScan`，并**明确写道** `BiExpand`/`BiTraverse`/`RightJoin`/`FullOuterJoin`/`SemiJoin` "GraphDB 暂未实现"。
- 但实际 `PlanNodeEnum` 早已重构为 **78 变体（vector 下 81）、9 类** 的模型，**已经包含** `BiExpand`、`BiTraverse`、`RightJoin`、`FullOuterJoin`、`SemiJoin`、`FulltextSearch`、`Materialize`、`Apply`、`CorrelatedApply`、`Savepoint`、`ReleaseSavepoint` 等，并且**没有**任何 `Hash*` 变体。

更严重的**事实性错误**：旧文档曾写"**nebula-graph 中还有 RightJoin、FullOuterJoin 等，GraphDB 暂未实现**"——但源码核实表明：
- Nebula 的 `PlanNode::Kind` **根本没有** `RightJoin`/`FullOuterJoin`/`SemiJoin`（仅 `kInnerJoin`/`kHashLeftJoin`/`kHashInnerJoin`/`kCrossJoin` + Apply 变体）；
- linkrs 的代码中**反而包含** `RightJoin`/`FullOuterJoin`/`SemiJoin`/`LeftJoin`。

即文档对"Nebula 有什么"和"linkrs 有什么"两处断言**双双错误**（`plan_node_category_analysis.md` 的 `:265` 示例代码曾引用 `PlanNodeEnum::FulltextIndexScan`，指向不存在的变体）。

**修复状态（2026-08-16）**：两份 `__analysis__` 文档已按当前代码重写；`define_enum_type_name!` 宏在定义处生成
`ALL_VARIANT_NAMES` 权威清单（与 `type_name()` 同表，编译器强制穷尽），内嵌一致性测试断言
变体数（默认 78、vector 81）、名称唯一、与文档镜像清单一致、旧变体不存在、向量节点 feature 门控，
将"事实来源"从代码 + 文档漂移转为"枚举 ↔ 宏清单 ↔ 文档"三方受测试门禁约束，防止复发。

### 5.2 【已落地】变量长度遍历：原生递归算子（原"无原生递归算子"结论已过时）

**修订（2026-08-16）**：早期结论"linkrs 的递归/多跳遍历只能通过 `LoopNode` 控制流模拟"**已过时**。
当前实现：

- `RecursiveFragmentSpec`（`executor/streaming/operators/spec.rs`）四变体：`ShortestPath` /
  `MultiShortestPath` / `BFSShortest` / `AllPaths`，含方向、深度、起点/终点、环路策略；
- `recursive_fragment_operator.rs`：原生递归片段算子（frontier / visited-set / 路径前驱 / 结果队列按内存池记账，逐轮检查取消令牌）；
- `variable_length_path_planner.rs`：VLP 规划器（`[:TYPE*min..max]`，含 `*`/`+`/`*n`）→ `VariableLengthPathPlan`，
  带 `PathPruner` / `PruningStrategy` / `VLPConfig` / `VLPStrategy`；
- `paths.rs`：`match_path_planner` / `shortest_path_planner` / `variable_length_path_planner` 三分支。

与 Ladybug 的差异收窄为**执行模型**之争（因子化 vs 流式）而非"有无原生递归算子"：
linkrs 的递归能力已从"Loop 模拟"演进为**原生算子 + 规划器**，`LoopNode` 保留为通用控制流。

### 5.3 【中等】缺乏因子化执行所需的计划节点

Ladybug 拥有 `SEMI_MASKER`、`MULTIPLICITY_REDUCER`、`NODE_LABEL_FILTER` 等因子化（factorized）专用节点，这是多跳图查询高效执行的关键。linkrs（流式模型，与 Nebula 同源）没有等价节点：

- 半连接/去重类需求靠 `Dedup`/`Filter` 近似，无法在"因子分解"层面裁剪中间结果；
- 这一缺口直接对应 linkrs 自身 `docs/analysis/linkrs_vs_ladybug_存储对比分析.md` 第 5.7 节已记录的"缺少向量化/因子化/morsel 并行执行器"——计划节点模型与执行器能力相互影响，因子化节点的缺失是根因之一。

### 5.4 【中等】全文 / 向量节点 feature-gated，默认构建不完整

- 向量节点 `VectorSearch`/`VectorLookup`/`VectorMatch` 全部 `#[cfg(feature = "vector")]` 门控（`plan_node_enum.rs:29-32, 250-256`）；Nebula 本版枚举中甚至**没有**向量节点，linkrs 在此反而超前。
- 全文节点存在但依赖 tantivy 等外部组件。

因此 `PlanNodeCategory::DataAccess` 声称"始终存在"，但向量节点仅在启用 `vector` 时才进入枚举。对"linkrs 一共支持哪些计划节点类型"这个问题，答案**取决于编译 feature**，文档未显式标注这一前提，易产生"默认构建即含全部节点"的误解。

### 5.5 【修正】管理/DDL 节点：已真实落地且有明确用途，不应强行缩减

> **重要修正**：本文初稿曾将"DDL 节点占比过重"列为 linkrs 的不足并建议缩减。经对源码与测试的双重核实，该结论**不成立**，在此更正。

**DDL 在 linkrs 中是真实实现、且被充分测试的，而非占位：**

- 物理算子层面存在完整的 DDL 执行器（`executor/streaming/operators/ddl_operator/`）：`schema_executor.rs`（**985 行**，Space/Tag/Edge/Index 管理）、`auth_executor.rs`（**151 行**，用户/角色/权限）、`maintenance_executor.rs`（**253 行**）、`ddl_operator.rs`（**354 行**），合计 **1743 行**真实实现；
- 测试层面有专门的 `tests/dcl/`（含 `user_management.rs`、`role.rs`、`permission.rs`、`security_tests.rs`、`concurrent_operations.rs`、`transaction_consistency.rs`）与 `tests/ddl/`、`integration_management.rs` / `integration_management_extended.rs`——说明 DDL/DCL 是**被验证可用的功能面**，不是装饰性节点；
- 这些节点服务于真实的"建库建图、建索引、多租户鉴权、数据增删改"需求，对一个图数据库而言是**核心能力**而非冗余。

**未来分布式扩展恰恰需要扩充而非缩减管理面：**

- linkrs 当前管理节点（Space/Tag/Edge/Index/User/Fulltext/Vector）是**单节点 / 单图**视角；
- 其参照原点 Nebula 的 136 节点中，近 2/3 是**分布式集群管理命令**（`kAddHosts`、`kBalance`、`kSubmitJob`、`kCreateSnapshot`、`kMergeZone`、`kDivideZone`、`kDropHosts` 等），这些 linkrs **目前反而缺失**；
- 若 linkrs 推进分布式，正需要**补齐**主机/分区/均衡/作业/快照等管理节点——即管理面会进一步**增大**，而非减小。

**结论**：DDL 节点占比高是 linkrs 继承 Nebula 血统的合理结果，且已落地、已测试、且为分布式演进所必需。真正值得关注的不是"缩减"，而是 **5.1 提到的文档与代码对齐**（分析文档未随 DDL 实现更新，2026-08-16 已修复），以及后续分布式管理节点的**有序扩展**。早期 90+ 变体 → 参数化子枚举压缩（`manage_node_enums.rs` 注释自承 "90+ to ~50"，后又扩展回 78）是恰当的工程手段，已解决枚举膨胀的可维护性问题。

### 5.6 【轻微】样板代码与维护成本

`PlanNodeEnum` 用宏为每个变体生成 `is_*`/`as_*`/`as_*_mut`/`type_name`/`category`/`describe` 共 6 套方法，文件 882 行、重复度极高。新增一个计划节点需要同步修改导入、`enum` 变体、6 个宏展开块（is/as/as_mut/category/type_name/describe），遗漏任一都会编译失败或运行时行为不一致。穷尽性检查是优点，但"新增节点的改动面"偏大。

### 5.7 【轻微】分类粒度与命名的历史包袱（Nebula 血统）

linkrs 计划节点分类与命名直接对齐 NebulaGraph：`plan_node_category_analysis.md` 通篇以"对应 nebula-graph"为基准，`GetNeighbors`/`Expand`/`Traverse`/`HashInnerJoin`（旧名）等节点名与 Nebula 一一对应。这带来兼容性收益，但也继承了 Nebula 的节点拆分粒度（例如 `GetVertices`/`GetEdges`/`GetNeighbors` 各自独立，而非统一 `Scan`+谓词下推），在 linkrs 自研执行器上并非最优拆分。

## 6. linkrs 逻辑/物理分离完整性评估

用户关注的第一个问题："linkrs 现有的逻辑/物理分离是否完整？"——答案是**完整且真实可用**，并非名义上的两阶段。

**证据链（均基于源码核实）：**

1. **逻辑→物理映射全覆盖**：`physical_planner.rs` 共 **1007 行**、**112 个 match 分支**逐一将 `PlanNodeEnum` 各变体落地为物理 `Spec`；全文仅 1 处 `panic!`，且位于 `DedupNode` 构造的**错误传播路径**（非未实现占位），**无任何 `unimplemented!` / `todo!` 残留**。
2. **物理算子 inventory 齐全**：流式执行器已实现的物理算子覆盖全部逻辑类别——
   - 连接：`HashJoin`/`MergeJoin`/`NestedLoopJoin`/`CrossSemiJoin`/`ShuffleJoin`；
   - 阻塞：`Aggregate`/`Sort`/`Materialize`/`Window`；
   - 图：`Expand`/`Traverse`/`Subgraph`；
   - 源：`Neighbors`/`IndexScan`/`PointLookup`/`StorageScan`；
   - 集合：`Union`/`Intersect`/`Minus`/`Dedup`；
   - 算法：`BFS`/`ShortestPath`/`AllPaths`/`MultiShortestPath`；
   - **DDL**：`schema_executor`（985 行）+ `auth_executor`（151）+ `maintenance_executor`（253）+ `ddl_operator`（354）；
   - **分布式原语**：`Exchange`（`Concatenate`/`RepartitionHash`）、`Gather`、`ShuffleJoin`。
3. **分布式原语已真正接入执行**：`engine.rs` 用 `GatherOperator` 跨 partition 做 `merge_sort`/`concatenate`；`partition.rs`（1300+ 行）以 `Exchange` 片段装配多 partition 执行树；测试 `parallel_partition_execution.rs` 直接验证分区执行路径。

**结论**：linkrs 的逻辑/物理分离是**端到端打通**的（逻辑枚举 → `PhysicalPlanBuilder` → spec/fragment → 物理算子 → 分区执行），且已具备分布式执行所需的 Exchange/Gather 骨架。当前唯一的"单节点"局限在于 Exchange 目前是**进程内分区/重分布**（intra-process shuffle），尚未跨网络——但架构已是分布式就绪（distributed-ready），与 linkrs 后续的分布式扩展路线一致。

## 7. 基于实际功能的对比（而非仅节点数量）

节点"数量"容易误导：Nebula 的 136 节点近 2/3 是集群管理命令，Ladybug 的 60 逻辑节点里也混有大量 DDL。真正重要的是**各项目实际落地了哪些能力**。下表按"功能"而非"节点数"对比：

| 功能能力 | Ladybug | linkrs | Nebula |
|---------|---------|--------|--------|
| 因子化执行 | ✓ 完整（`factorized_table`/`semi_masker`/`multiplicity_reducer`） | ✗ 流式模型 | ✗ 流式模型 |
| 原生递归遍历 | ✓ `RECURSIVE_EXTEND` + `PACKED_EXTEND` | ✓ 原生 `RecursiveFragmentSpec`（SP/MultiSP/BFS/AllPaths）+ VLP 规划器 | ✗ `kLoop` + `kExpand` 模拟 |
| 批量导入/导出（CSV/Parquet/NPY） | ✓ 完整（并行 CSV 读取器 + Parquet 读写 + COPY FROM/TO） | ✗ 未见 COPY 等价物 | △ storage 层 |
| 事务 | ✓ `transaction.cpp` | ✓ `txn_operator.rs` | ✓ |
| 多租户 / RBAC 安全 | ✗ 单用户 | ✓ 完整 DCL + 专项测试（user/role/permission/security） | ✓（user/snapshot/zone） |
| 扩展机制（install/load/uninstall extension） | ✓ | ✗ | ✗ |
| 数据库 attach/detach/import/export | ✓ | ✗ | ✓（集群级） |
| 图算法 / GDS | ✓ `function/gds` 函数库 + 图算子 | ✓ `algorithms.rs`（BFS/SP/AllPaths/MultiSP） | ✓ `algo` |
| 连接类型覆盖 | 少（物理层 build/probe 展开） | 宽（Inner/Left/Right/Cross/FullOuter/Semi + Apply） | 中（Inner/Hash*/Cross + Apply） |
| 全文 / 向量检索 | ✗ | ✓（feature-gated `vector` 向量） | △ 全文（本版无向量节点） |
| 分布式执行 | ✗ 单节点嵌入式 | △ 架构就绪（Exchange/Gather，目前单进程） | ✓ 原生分布式 |
| 宏 / 序列 / 自定义类型 | ✓ `CREATE_MACRO`/`SEQUENCE`/`TYPE` | 部分（类型系统较简） | ✓ |

**功能性结论（修正"仅数数量"的视角）：**

- **Ladybug 的强项是单节点功能丰富度**：因子化执行、原生递归、并行 CSV/Parquet/NPY 批量导入导出、PostgreSQL 式扩展生态、数据库 attach/detach、宏/序列/类型、GDS 函数库——它已经是一个**功能完整的嵌入式分析引擎**。linkrs 在这些"数据工程 / 可扩展性"维度上仍有明显缺口（尤其批量导入导出与扩展机制）。
- **linkrs 的强项是分布式就绪 + 多租户安全 + 现代工程化**：Exchange/Gather/Shuffle 分布式骨架、完整的 RBAC DCL、更宽的连接类型覆盖、全文/向量检索——它瞄准的是**可扩展的服务端图数据库**，而非嵌入式分析。
- 两者并非简单的"谁更好"，而是处于**不同的成熟度 / 规模定位**：Ladybug 在单节点深度功能上领先，linkrs 在横向扩展与多租户架构上领先。双方的功能缺口（linkrs 缺批量导入/扩展机制；Ladybug 缺分布式/多租户）恰好互补。

## 8. 总结

| 维度 | Ladybug | linkrs | Nebula |
|------|---------|--------|--------|
| 计划节点总数 | 逻辑 60 + 物理 69（两枚举） | 逻辑 **78**（vector 下 81）单枚举 + 物理 spec 模型 | **136**（单一 `PlanNode::Kind` 枚举） |
| 逻辑/物理分离 | 是（build/probe、scan/merge 阶段拆分） | **是，且端到端完整**（physical_planner 112 分支 + 物理算子齐全） | **否（逻辑/物理合一）** |
| 图遍历表达 | 因子化原生算子（`EXTEND`/`RECURSIVE_EXTEND`/`SEMI_MASKER`） | 流式 `Expand`/`Traverse` + 原生递归片段（`RecursiveFragmentSpec` 四变体） | 流式 `kExpand`/`kTraverse` + `kLoop` |
| 节点分类元数据 | 弱（仅类型枚举 + 少量 utils） | 强（`PlanNodeCategory` + 语义方法） | 粗（`isQueryNode()` 二分） |
| 类型安全 | 运行时 `dynamic_cast` 校验 | 编译期 `match` 穷尽 + trait 约束 | 运行时 `dynamic_cast`/`DCHECK` |
| DDL 落地情况 | 已实现（`operator/ddl/*`） | **已实现且充分测试**（1743 行 + `tests/dcl`、`tests/ddl`） | 已实现（分布式集群管理） |
| 分布式就绪度 | ✗ 单节点嵌入式 | △ 架构就绪（Exchange/Gather，目前单进程） | ✓ 原生分布式 |
| 文档与代码一致性 | 设计文档体系完整 | **计划节点分析文档已与代码对齐**（2026-08-16 重写 + 一致性测试门禁） | — |

**核心结论**：

1. 三者都把"计划节点"作为查询引擎的一等抽象，但**只有 Ladybug 与 linkrs 显式区分逻辑/物理计划**，Nebula 采用逻辑/物理合一的单一表示——linkrs 作为 Nebula 的 Rust 移植，架构上反而比原点更先进（补回了逻辑/物理分离），且经核实其分离**已端到端打通**（见第 6 节）；
2. Ladybug 的计划节点体现 Kuzu 的**因子化**基因，图遍历与多跳查询的表达更"原生"、更高效；linkrs 走**流式**路线，但已为路径类查询提供原生递归片段算子（`RecursiveFragmentSpec` 四变体 + VLP 规划器），`LoopNode` 仅保留为通用控制流——已不再"靠 Loop 拼装"（见 5.2 修订）；Nebula 仍依赖 `kLoop` + `kExpand` 模拟；
3. linkrs 在**工程化**（类型安全枚举、显式分类、规则化优化器、多格式 EXPLAIN、超前的全文/向量节点、分布式就绪的 Exchange/Gather 骨架）上做得更"现代"。其计划层曾最突出的 **5.1 文档与实现对齐失效**（分析文档不仅陈旧，还事实性误述了 Nebula 与 linkrs 各自的节点集）已在 **2026-08-16 修复**：两份 `__analysis__` 文档重写 + 宏表生成的 `ALL_VARIANT_NAMES` 一致性测试门禁；
4. **DDL 不应被视为缺陷或缩减对象（修正初稿 5.5）**：linkrs 的 DDL/DCL 已真实实现（1743 行）并被专项测试覆盖，是核心能力；且面向分布式扩展，linkrs 当前反而**欠缺** Nebula 式的集群管理节点（主机/分区/均衡/作业/快照），需要**扩充**而非缩减管理面；
5. 从**功能**而非节点数量看，Ladybug 在单节点深度功能（因子化执行、批量导入导出、扩展生态、DB 管理、GDS 函数库）上领先，linkrs 在分布式就绪与多租户安全上领先——这是不同规模定位的体现，而非优劣之分；linkrs 若要在复杂分析负载上对标 Ladybug，重点应补**批量导入导出与扩展机制**（功能缺口），而非纠结节点数量。
