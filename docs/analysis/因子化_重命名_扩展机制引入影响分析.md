# 因子化 / 重命名 / 扩展机制引入影响分析

> 关联文档：`docs/analysis/计划节点类型对比分析.md §5.3/5.7/§7`、`docs/plan/plan_node_remaining_issues_improvement_analysis.md §3`
> 核验基线：`crates/graphdb-query/src/query/planning/plan/core/nodes/base/plan_node_enum.rs:567`、`crates/graphdb-storage/src/storage/edge/property_table.rs`、`crates/graphdb-query/src/query/executor/streaming/operators/spec.rs:950`、`crates/graphdb-query/src/query/executor/streaming/plan/arena_builder/`、`AGENTS.md:3`
> 目的：对 plan 文档中标记为 `P3 不改 / P2 按需` 的三项（因子化、重命名历史包袱、扩展机制）做"若现在引入"的**增量影响**分析，明确优缺点与边界，避免误判为必做。

## 1. 总览

| 能力 | Ladybug 参照 | linkrs 现状 | 本报告判定 | 引入本质 |
|------|-------------|-------------|-----------|---------|
| **因子化** `factorized` | `factorized_table` + `SEMI_MASKER` + `MULTIPLICITY_REDUCER` + 向量化 `DataChunk` | 流式 `tuple-at-a-time` + `SlotLayout` + `Dedup/Filter` 近似 | **P3 不改，条件触发** | 存储 + 执行器重构，非补节点 |
| **重命名** 去 Nebula 包袱 | Kuzu 自洽命名 `SCAN_NODE_TABLE / EXTEND` | `GetVertices / GetNeighbors / Expand / Traverse` 细粒度 Nebula 血统 | **P3 不改** | 全链路重命名，破坏兼容无性能收益 |
| **扩展机制** `INSTALL EXTENSION` | `install_extension / load_extension / attach_database` 嵌入式生态 | 无，仅 `FulltextManage / VectorManage` 插件式管理 | **P3 不改** | 新增插件框架与安全边界，偏离轻量定位 |

> 三者共同点：**均非 PlanNode 枚举的局部改动**，而是牵一发动全身的架构级引入；且均与 `AGENTS.md:3` 的"轻量单节点、聚焦本地部署"定位存在取舍。

## 2. 因子化（Factorized Execution）

### 2.1 是什么

Ladybug 的因子化（Kuzu 血统）指多跳图查询中**不物化笛卡尔积中间结果**，而以因子压缩形式传递，并在算子层裁剪：

- `src/processor/result/factorized_table.cpp` — 因子化中间表
- `operator/semi_masker.cpp` — 半连接掩码，过滤不可达路径
- `operator/multiplicity_reducer.cpp` — 多重性消除
- 配合 `DataChunk` 2048 批量向量化 + `ListVector` 嵌套列 + morsel 并行

linkrs 当前为 `spec.rs:144 SlotLayout` 的流式模型，每行一元组，`DedupNode`/`FilterNode` 在物化后去重。

### 2.2 若引入，需改动哪些层面

| 层 | 现状 | 引入后 | 工作量 |
|----|------|--------|--------|
| **存储** | 边属性行存 `property_table.rs:records: Vec<Option<PropertyRecord>>`；顶点列存；CSR `Multiple/Single/MultiSingle` | 边属性列存化（每属性一列）+ 列段压缩 + min/max 谓词下推；CSR 密度自适应/零拷贝 Arrow | 2-3 周，涉及 `graphdb-storage` 重写 |
| **执行器** | `executor/streaming/` 流式，`RecursiveFragmentSpec:950` 已原生但仍逐行 | 引入 `DataChunk` 批量、`FactorizedTable`、`Vector` 类型体系、`SEMI_MASKER` 等新 `GraphSpec` 变体，morsel 调度 | 3-4 周 |
| **Plan** | `PlanNodeEnum:567` / `GraphSpec:355` / `JoinSpec` | 新增 `SemiMasker`/`MultiplicityReducer`/`NodeLabelFilter` 等逻辑节点 + 物理 `build/probe` 拆分 | 1 周 |
| **优化器** | `optimizer/` 启发式 + CBO | 需因子化代价模型（基数估计按因子而非行） | 1 周 |
| **测试/基准** | `benches/storage_bench.rs` 微基准 | 需 LDBC SNB 多跳聚合基准，否则无法证明收益 | 持续 |

**合计**：约 7-10 周，且与 `docs/analysis/linkrs_vs_ladybug_存储对比分析.md:5.7` 的存储重构耦合，无法独立交付。

### 2.3 优点

- **分析查询性能**：`MATCH (a)-[:KNOWS*3..5]->(b) WHERE ...` 等多跳聚合，中间结果从 `O(n^k)` 物化降为因子压缩，内存与 CPU 峰值显著下降（Ladybug/LDBC SNB 压倒性优势来源）。
- **半连接裁剪**：`SEMI_MASKER` 在扫 `Expand` 时即过滤不满足下游谓词的路径，优于事后 `Filter`。
- **与列存协同**：列裁剪 + 向量化批次天然适配因子化，未来若走向分析负载是必经路。

### 2.4 缺点与风险

- **与定位冲突**：linkrs 优势在 OLTP + 时序（`MVCC tombstone` + `tests/dcl/` RBAC），当前无分析 SLAs，投入无基准驱动（`linkrs_vs_ladybug_存储对比分析.md:5.8` 已指基准方法论缺失）。
- **存储重写风险**：行存→列存是破坏性变更，影响 `WAL`/`checkpoint`/`freeze`（`freeze.rs:120` 已属脆弱路径），需数据迁移工具（`graphdb-migration` 未覆盖此粒度）。
- **维护成本**：`FactorizedTable` 生命周期、内存池记账、morsel 线程池引入大量 `unsafe`/`parking_lot` 细节，与现有流式代码双轨并存，复杂度翻倍。
- **收益不确定**：无 `RecursiveFragmentSpec` 前最痛的是递归 `Loop` 模拟，现已原生，剩余因子化边际收益收敛。

### 2.5 引入影响

- **正面**：打开 OLAP 天花板，可宣称对标 Kuzu/Ladybug 分析性能。
- **负面**：短期 2-3 个月无法交付其他能力（批量导入、本地向量 Tier1）；引入后问题域从"正确性/可用性"转向"向量化正确性/并发调度"，团队上下文切换成本高。
- **判定**：**不引入**，文档中标注为"分析负载可选演进"，待出现真实 `ldbc_snb` 基准红线再触发。

## 3. 重命名（去 Nebula 历史包袱）

### 3.1 是什么

指将 `GetVertices / GetNeighbors / GetEdges / Expand / ExpandAll / Traverse / AppendVertices`（`plan_node_enum.rs:134` Access/Traversal 13 变体）合并/重命名为更自洽的 `ScanVertices + ScanEdges + Expand` 或 `Scan + 谓词下推` 统一模型，消除对 `nebula-graph` 的粒度继承（`plan_node_category_analysis.md` 每行"对应 nebula-graph"）。

`AGENTS.md:3` 已声明 **No-backward-compatible**，理论上此时重命名成本最低。

### 3.2 若引入，需改动哪些层面

| 影响面 | 具体文件 | 说明 |
|--------|---------|------|
| **Plan 枚举** | `plan_node_enum.rs:567` / `macros/enum_methods.rs:176` / `plan_node_traits.rs` | 合并变体，`ZeroInputNode / MultipleInputNode` 体系重排 |
| **Spec/Builder** | `spec.rs:70 SourceSpec / 355 GraphSpec` / `arena_builder/specs.rs:811` | `SourceSpec::GetNeighbors` 等需重映射或删除 |
| **Parser/Planner** | `query/planning/planner.rs` / `statements/paths/` | 语法到逻辑节点的映射全改 |
| **优化器** | `optimizer/partitioning.rs` / `cost_based/` | `is_leaf() / supports_parallelism()` 语义重算 |
| **EXPLAIN / Wire** | `plan/explain/` / `graphdb-wire` / `tests/` | 输出字符串、快照测试、文档全量替换 |
| **外部兼容** | `graphdb-api` / `graphdb-server` / `graphdb-cli` | 若曾暴露 Plan 名称，需提供别名层 |

工作量约 1-2 周，但为**全仓字符串替换 + 快照更新**，非逻辑重构。

### 3.3 优点

- **命名自洽**：`GetVertices`（按上游 ID 列表）与 `ScanVertices`（全表扫）从用户视角易混，统一为 `Scan` 可降低新成员心智负担。
- **谓词下推更自然**：统一后 `IndexScan` 与 `Scan` 的边界更清晰，利于后续列存谓词下推。
- **去历史债**：彻底摆脱"Rust 重写版 Nebula"的注释包袱，架构叙事更独立。

### 3.4 缺点与风险

- **零性能/正确性收益**：仅为"更优雅"，`EXPLAIN` 输出变字符串，无执行加速。
- **全量 breaking**：`EXPLAIN` 文本、日志、监控、测试快照、文档示例全部失效，搜索 `GetNeighbors` 需重定向。
- **`No-backward-compatible` 的误用**：该声明本意为"允许存储格式/磁盘不兼容"，并非鼓励无收益的重命名；此时引入会消耗"不兼容预算"，却未换得架构自由度。
- **与 Spec 合并重复**：存储层已在 `GraphSpec` 做合并，Plan 层保留细粒度利于 `MultipleInputNode` 精确建模，合并后反而损失表达力。

### 3.5 引入影响

- **正面**：文档阅读体验 +5%。
- **负面**：2 周全仓 churn，PR review 噪音大，`git blame` 断裂，后续与 Nebula 对比分析需重写。
- **判定**：**不引入**，保留现状并在 `plan_node_category_analysis.md` 中已说明取舍即可；若未来做列存/因子化重构时**顺带**重命名，则边际成本可接受，单独立项不值得。

## 4. 扩展机制（Extension / Attach Database）

### 4.1 是什么

Ladybug 的 `INSTALL EXTENSION / LOAD EXTENSION / UNINSTALL EXTENSION`（`src/processor/operator/simple/install_extension.cpp`）与 `ATTACH DATABASE / DETACH / IMPORT / EXPORT`（`attach_database.cpp` 等），提供类 PostgreSQL 的插件与多库管理；`CREATE MACRO / SEQUENCE / TYPE` 等亦属此列。

linkrs 现有仅 `FulltextManage / VectorManage` 的索引级插件能力，无通用扩展框架。

### 4.2 若引入，需改动哪些层面

| 层 | 引入内容 | 说明 |
|----|---------|------|
| **Plan** | 新增 `ExtensionManage / DatabaseManage` 参数化子枚举（仿 `manage_node_enums.rs:173`） | 枚举膨胀可控，但 `PlanNodeCategory::Management` 语义扩张 |
| **执行器** | `ddl_operator/` 新增 `extension_executor.rs`，涉及动态库加载 `libloading` | 需 `unsafe` 加载边界，`docs/archive/unsafe.md` 需新增条目 |
| **安全** | 沙箱、签名校验、权限（`UserManage` 需新增 `INSTALL` 权限） | 轻量定位下安全审计成本突增 |
| **存储** | `ATTACH` 需多库 `GraphDataStore` 隔离 + 跨库事务 | 与当前单库 `data/edges/<src>_<dst>_<edge>/` 布局冲突 |
| **API/运维** | `graphdb-api / graphdb-server` 新增管理接口，CLI 适配 | 与 `vector_local_engine_plan.md` 的本地引擎分阶段冲突 |

工作量约 2-3 周（最小 `INSTALL` 闭环），完整 `ATTACH + IMPORT + GDS` 约 1 月。

### 4.3 优点

- **生态可扩展**：社区可不改内核交付 `GDS` 图算法、自定义函数、数据源连接器。
- **对标 Kuzu**：补齐 `linkrs_vs_ladybug_存储对比分析.md:6.2` 中 Ladybug"功能完整嵌入式分析引擎"的叙事缺口。
- **多库场景**：`ATTACH` 对"联邦查询/数据联邦"有价值。

### 4.4 缺点与风险

- **与轻量定位背离**：`AGENTS.md:13` 强调轻量单节点、聚焦本地部署；扩展机制是"嵌入式数据库的可扩展性"命题，linkrs 定位为服务端（HTTP/gRPC），扩展应通过 API/服务层而非进程内动态库。
- **安全与稳定性**：`dlopen` 引入崩溃面（`panic` 跨 FFI）、供应链风险、与 `Never use unwrap` 原则冲突；`ATTACH` 的多库事务显著复杂化 `graphdb-transaction`。
- **需求不明确**：当前无插件消费方，`Fulltext / Vector` 已以 `manage_node_enums.rs` 的参数化方式满足索引扩展，无需通用框架。
- **维护长尾**：扩展 ABI 需版本化，与 `No-backward-compatible` 冲突（扩展需稳定 ABI）。

### 4.5 引入影响

- **正面**：生态想象空间。
- **负面**：安全审计、ABI 兼容、多库事务三重负担，且无真实用户驱动。
- **判定**：**不引入**，保持 `FulltextManage / VectorManage` 的"索引即插件"粒度；若未来出现 GDS 强需求，优先以 `function/gds` 纯函数库（无需动态加载）而非 `INSTALL EXTENSION` 满足。

## 5. 综合影响与建议

| 引入项 | 对现有架构冲击 | 对定位契合度 | 维护成本 | 建议 |
|--------|---------------|-------------|---------|------|
| **因子化** | ★★★★★ 存储+执行重写 | 低（OLAP vs OLTP） | 极高 | **不引入**，待 LDBC 基准触发 |
| **重命名** | ★★★ 全仓 churn | 中（可读性） | 中 | **不引入**，单独无收益，随重构顺带 |
| **扩展机制** | ★★★★ 安全/ABI/多库 | 低（轻量 vs 嵌入式生态） | 高 | **不引入**，以索引级插件满足 |

**共同影响**：三者若同时引入，将使 `crates/graphdb-query` 从"可维护的流式引擎"滑向"高复杂度分析引擎"，与 `crates/graphdb-storage` 的列存重构、`crates/vector-search` 的本地化、`crates/graphdb-sync` 的分布式就绪三条主线资源争抢，且均无当前负载的基准支撑。

**推荐**：维持 `docs/plan/plan_node_remaining_issues_improvement_analysis.md:95` 的分级——仅 `P1 样板代码生成` 立项，`P2 COPY FROM CSV` 按需，三者均标注为 `P3 不改` 并在本分析中留档，避免后续重复立项。如需演进，**因子化需存储先行、重命名需搭重构便车、扩展机制需先有 GDS 函数库**，三者均不单独作为起点。
