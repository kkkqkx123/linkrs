# 事务生命周期回调动态分发分析

## 一、分析对象

本文分析以下动态分发是否多余：

```rust
pub type CommitCallback = Arc<dyn Fn(&TransactionEvent) + Send + Sync>;
pub type RollbackCallback = Arc<dyn Fn(&TransactionEvent) + Send + Sync>;
```

相关实现位于：

- `crates/graphdb-transaction/src/transaction/types.rs`
- `crates/graphdb-transaction/src/transaction/manager.rs`

`TransactionManager` 分别使用两个 `RwLock<Vec<...>>` 保存提交和回滚回调。事务离开
`active_transactions` 后，管理器取得回调快照并同步逐个调用。

## 二、结论

**结论：在当前公共扩展契约下，这一处动态分发不多余，应当保留。**

但需要区分两个判断范围：

| 判断范围 | 结论 | 原因 |
|----------|------|------|
| 仅看当前生产代码 | 可以移除 | 当前生产订阅者只有事务统计，可直接调用具体类型 |
| 看公共回调注册 API | 不应移除 | 注册方可提供任意捕获环境的闭包，多个不同闭包类型需要存入同一集合 |
| 看阶段 2 的解耦目标 | 不应移除 | 静态枚举会让新增订阅者重新依赖并修改事务核心 |

因此，`dyn Fn` 不是为了隐藏一个已知的固定实现，而是为了支持开放式、运行时注册的
订阅者集合。若未来明确取消公共注册能力，并将订阅者收敛为固定的内部组件，才应改回
具体类型或静态枚举。

## 三、当前调用模型

### 3.1 注册阶段

管理器构造时注册两个默认统计回调：

1. `Committed` 更新提交统计。
2. `CommitDurableButUnfinalized` 更新提交及清理失败统计。
3. `Aborted` 更新回滚统计。

外部组件还可以通过以下接口增加订阅者：

```rust
pub fn register_commit_callback(&self, callback: CommitCallback);
pub fn register_rollback_callback(&self, callback: RollbackCallback);
```

闭包通常需要捕获 `Arc<StatsManager>`、存储协调器或其他组件状态。每个捕获闭包都有
独立的匿名类型，无法直接放入同一个 `Vec<T>`。

### 3.2 派发阶段

事件仅在事务终结路径派发：

- 正常提交后派发 `Committed`。
- 提交已持久化但清理失败时派发 `CommitDurableButUnfinalized`。
- 回滚释放资源并移出活动表后派发 `Aborted`。

它不位于逐行读取、逐属性写入或冲突检测循环中。动态调用频率等于事务终结频率，而非
数据操作频率。

## 四、为什么需要类型擦除

假设存在三个订阅者：

```rust
let stats_callback = move |event| stats.record(event);
let catalog_callback = move |event| catalog.invalidate(event);
let storage_callback = move |event| storage.notify(event);
```

即使参数和返回值相同，这三个闭包仍然是三个不同的编译期类型。要在运行时决定注册数量，
并将它们放入同一个容器，必须采用以下某种类型擦除方式：

- `Arc<dyn Fn(...)>`；
- `Arc<dyn TransactionObserver>`；
- 手工函数指针加无类型状态；
- 消息通道，将动态性转移到接收端。

当前的 `Arc<dyn Fn>` 是其中最直接且闭包使用体验最好的方式。改成 observer trait 仍然是
动态分发，并不能消除 `dyn`。

## 五、替代方案比较

| 方案 | 是否消除动态分发 | 优点 | 主要问题 | 结论 |
|------|------------------|------|----------|------|
| 直接调用 `TransactionStats` | 是 | 最简单、无间接调用 | 恢复核心与统计耦合，无法注册其他组件 | 不符合阶段 2 目标 |
| 泛型 `TransactionManager<C, R>` | 是 | 完全静态分发 | 泛型传播到 API、存储及共享管理器；异构多订阅者组合复杂 | 不采用 |
| 固定订阅者枚举 | 是 | 容器类型确定 | 每加订阅者都要修改事务 crate，形成反向依赖 | 仅适合封闭集合 |
| `fn` 函数指针 | 是 | 表示紧凑 | 不能直接捕获组件状态；附加状态后仍需类型擦除 | 不采用 |
| `dyn TransactionObserver` | 否 | 可将多个事件方法组织到一个接口 | 样板代码更多，仍使用虚调用 | 无明显收益 |
| 消息通道 | 管理器侧是 | 可异步隔离慢订阅者 | 引入队列、线程、背压和关闭语义，改变同步可见性 | 仅适合异步通知 |
| `Arc<dyn Fn>` | 否 | 开放注册、支持捕获闭包、API 简洁 | 存在一次间接调用及回调治理问题 | 当前最合适 |

### 5.1 泛型方案为何不合适

泛型只能自然表示固定数量和固定组合的回调。例如 `TransactionManager<C, R>` 可以保存一个
提交回调和一个回滚回调，但无法直接表达运行时追加的任意数量回调。继续使用元组或类型级
列表会使管理器具体类型随订阅者组合变化，并向 `Arc<TransactionManager<...>>` 的所有调用方
传播，明显扩大事务模块的类型复杂度。

### 5.2 枚举方案为何违背解耦目标

枚举适合实现集合有限且由当前 crate 拥有的场景。生命周期订阅者却可能来自统计、目录、
存储、索引或 API crate。将这些订阅者定义成事务 crate 内的枚举变体，会迫使事务底层依赖
上层组件，破坏现有依赖 DAG。

## 六、性能成本判断

动态分发本身的成本包括：

1. 每个订阅者一次虚表间接调用。
2. 间接调用通常无法跨 trait object 边界内联。
3. `Arc` 保存 fat pointer，单个元素比普通函数指针更大。

这些成本在当前路径中不是主要问题，原因如下：

- 每个事务只在终结时派发一次事件。
- 提交路径通常已经包含 WAL、同步、锁和时间戳管理。
- 回调执行的统计原子操作或存储通知成本通常高于一次虚调用。
- 默认订阅者数量很少。

当前没有专门基准测试，因此不能给出可靠的纳秒数或百分比。基于调用位置，可以判断该动态
分发不属于值得优先消除的逐记录热路径。

## 七、当前实现中更重要的成本与风险

### 7.1 每次派发都会克隆整个回调向量

当前实现先执行：

```rust
let callbacks = self.commit_callbacks.read().clone();
```

这会分配一个新 `Vec`，并对每个回调执行一次 `Arc` 引用计数增加。订阅者较多时，这部分成本
比虚调用本身更值得关注。

克隆快照也有合理性：它能在调用用户回调前释放 `RwLock`，避免回调重入注册接口时死锁，
并防止慢回调长期占用注册锁。

若基准测试证明派发成本显著，可将容器改为写时复制快照：

```rust
RwLock<Arc<[CommitCallback]>>
```

注册时复制切片，派发时只克隆外层 `Arc`。事务终结远多于回调注册时，这种成本转移更合理。

### 7.2 回调同步串行执行

所有回调都在提交或回滚调用线程中同步执行。任一慢回调都会直接增加事务尾延迟。动态分发
不是该问题的根因，回调的执行模型才是。

建议保持以下边界：

- 同步回调只做短时、无阻塞的状态更新或任务投递。
- I/O、重试和恢复处理应投递到后台队列。
- 不允许回调等待当前事务持有或刚释放的外部资源。

### 7.3 panic 会穿透事务终结 API

回调类型返回 `()`，但未隔离 panic。外部回调 panic 时，事务已经从活动表移除，调用方却会
观察到栈展开，容易误判提交结果。

这是当前实现最需要明确的正确性契约。可选策略有：

1. 将回调限定为内部可信代码，并文档化“回调不得 panic”。
2. 使用 `catch_unwind` 隔离每个外部回调，记录错误并继续派发。
3. 改为任务投递接口，由后台执行器隔离失败。

在没有统一错误处理策略前，不建议把任意用户插件回调直接注册到该同步路径。

### 7.4 缺少注销与身份标识

当前注册接口只追加回调，不返回注册令牌，也不能注销。长期运行过程中动态加载、卸载组件时，
回调持有的 `Arc` 会持续保留组件资源。

如果注册仅发生在启动阶段，此问题可以接受；如果未来支持插件热加载，应引入
`CallbackRegistrationId` 和注销接口。

### 7.5 回调顺序是隐式行为

当前按照注册顺序执行，默认统计回调先于外部回调，但 API 没有声明该顺序是否稳定。外部组件
不应依赖这一顺序。若未来确实存在依赖，应显式定义优先级，而不是依赖 `Vec` 插入顺序。

## 八、建议

### 当前阶段

1. 保留 `Arc<dyn Fn(&TransactionEvent) + Send + Sync>`。
2. 保留派发前释放 `RwLock` 的快照语义。
3. 将回调限定为短时、无阻塞操作，并明确不得 panic。
4. 不为消除一次虚调用而将 `TransactionManager` 泛型化或引入固定订阅者枚举。

### 后续触发条件

只有满足以下条件之一时才需要继续重构：

- 基准测试证明回调快照分配影响事务吞吐：改用写时复制的 `Arc<[Callback]>`。
- 需要执行存储清理、网络通知等慢任务：增加异步事件通道，不在同步回调中执行 I/O。
- 支持组件热加载：增加注册令牌和注销机制。
- 允许不可信插件注册：增加 panic 隔离和执行预算。
- 产品明确取消开放注册能力：删除回调 trait object，恢复具体的内部订阅者调用。

## 九、最终判断

这一处 `dyn` 的必要性来自“开放、异构、运行时注册”的集合语义，而不是当前统计回调的实现
数量。当前只有一个生产订阅者并不代表动态分发多余，只说明扩展点尚未被更多组件使用。

因此当前应保留动态分发。优化重点应放在回调快照分配、同步执行延迟、panic 隔离和生命周期
管理上，而不是虚表调用本身。
