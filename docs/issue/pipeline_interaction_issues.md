# 流水线与缓存交互问题清单

范围为绑定器与规划器之外的直接调用方，含流水线、优化器引擎、计划缓存与扩展点。

## 调用链分散

完整查询链路为解析、数据操纵形状模板化、模板缓存查找、读写分支绑定、请求定稿、执行总调度、编译缓存、物理构建、执行。串联点分散在流水线的请求准备、前端、编译器与执行结果等多个子模块，阅读时需要在多个文件之间跳转。近期无需合并文件，但需要在整改方案中给出唯一链路说明，避免后续重构误拆。

## 优化器与规划器各持一套连接排序

规划期连接排序针对查询图做动态规划枚举，优化器代价连接排序针对已规划连接链做重排。两者注释互相声明分工，但同一职责在两个阶段各做一次，且代价常量需要跨模块保持一致，属于跨模块常量耦合。应统一代价类型入口与文档说明，明确各自适用阶段。

## 缓存键与备忘键双轨

计划缓存键与数据操纵备忘键在键构造与失效维度上各写一遍，备忘键为无指纹版本加事后兼容校验。两者有意构成两级设计，分别服务跳过绑定的写路径备忘与读路径计划复用，但构造点分散在流水线与编译器两处。模板抽取器作为第三套模板化无人消费，加剧了理解成本。应收敛为单一键构造说明，删除无人消费的一套。

## 扩展点无生产实现

解析、绑定、规划与映射四类扩展点均已接线并对外暴露，测试覆盖完备，但全仓仅有测试桩实现，无生产注册。属于实验性预留开销，应在文档中明确去留，避免后续规划器误依赖扩展点做兼容。

## 优化器反向依赖规划器

优化器引擎在物理映射阶段直接调用物理映射器的映射与提示合并能力，规划文档自称单向逻辑到物理，实际存在优化器反向依赖。这不是重复代码，而是决策时机划分问题，应在整改方案中明确依赖方向，避免后续拆分模块时循环依赖。
