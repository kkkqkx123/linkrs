# P2 [simvec] filter_selectivity 低选择性反而慢 ~11×

## 现象（实测）

`filter_selectivity/100k`（selectivity = 保留比例）：

| selectivity | 中位时间 |
|---:|---:|
| 100% | [2.4499, 2.5095, 2.5835] ms |
| 50% | [26.909, 28.909, 30.642] ms |
| 10% | [20.501, 26.095, 28.921] ms |
| 1% | [30.003, 30.905, 31.754] ms |

数据来源：`bench_results/linkrs-simvec.log:235-263`

- **低选择性（1%/10%/50%，即过滤掉更多）反而比 100%（不过滤）慢约 11×**（30.9ms / 2.51ms ≈ 12.3×）。
- 反常：直觉上低选择性（结果更少）应更快，实际相反——过滤路径异常慢。

## 影响

带过滤的向量扫描是最常见查询形态，在选择性低时严重变慢，直接拉低召回/过滤类查询吞吐。

## 疑似根因

- 过滤实现可能是"先全量扫描所有向量，再逐条判定 + collect"，低选择性下仍全量扫描且额外承担过滤判定/收集开销；
- 可能走了未优化的 miss 路径（对比 `alloc_stats_bench` 中 `search xN filtered-miss` 有 4493 次分配，分配抖动明显）；
- 100% 与 1% 走的可能不是同一代码路径，1% 路径未做位图/索引预筛。

## 建议

1. 对比 100% 与 1% 的代码路径差异，确认低选择性是否走了未优化分支；
2. 引入位图 / 索引预筛，使低选择性成本 ≤ 高选择性（或仅略高），而非 11×；
3. 把 `filter_selectivity` 各档纳入 CI 回归，防止过滤路径回退。
