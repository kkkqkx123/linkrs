# P2 [storage] 边扫描并行加速比 ≈ 1.0（零加速）

## 现象（实测）

`edge_scan_speedup_bench` B1「edge-table scan parallel speedup」，单分区 1M 边：

| workers | T(n) µs | E(n) | eta |
|---:|---:|---:|---:|
| 1 | 415834 | 1.00 | 1.00 |
| 2 | 412763 | 1.01 | 0.50 |
| 4 | 412030 | 1.01 | 0.25 |
| 8 | 406988 | 1.02 | 0.13 |

数据来源：`bench_results/linkrs-storage.log:1552-1564`

- 并行效率 E(n) 在 1→8 worker 间稳定在 **1.00–1.02**，墙时 415834µs → 406988µs（变化 <2%）。
- 即增加 worker 对边扫描**没有任何加速**，eta 列（理论加速比）从 1.0 掉到 0.13，说明多核投资零回报。

## 影响

边扫描无法利用多核，1M 边扫描固定在 ~413ms。并行化改造在这里完全没生效。

## 疑似根因

- 单分区（partitions N=1）配置下，扫描可能未真正分片到多 worker（单分区本就无法并行）；
- 或 worker 间存在共享锁 / 结果串行收集（collector），使多 worker 退化为串行。
- 日志只给了 partitions N=1 一组，无法判断是多分区下亦无加速（属框架缺陷）还是单分区本就预期无加速。

## 建议

1. 补充 `partitions = [4, 16]` 组的实测，确认分区数=1 时是否本就无加速（预期行为）还是 worker 分发逻辑缺陷。
2. 若多分区仍无加速，排查扫描 reader 的共享锁 / collector 串行化——worker 是否真正并发读取不同分区。
3. 结合 `query-parallel-efficiency.md`（查询并行效率同样崩溃到 0.04–0.12），并行执行框架很可能是共因，应统一排查。

## 严重级
**P2（性能）** —— 受单分区配置限制，需补测多分区后定性。
