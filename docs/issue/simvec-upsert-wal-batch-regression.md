# P2 [simvec] upsert_wal 批量接口反而更慢（单元素慢 ~9.8×）

## 现象（实测）

`upsert_wal` bench（`-- --sample-size 10`）：

| 变体 | 中位时间 | 单元素成本 |
|---|---:|---:|
| `single` | [900.79, 915.11, 948.58] µs | 915 µs/op |
| `batch_100` | [885.90, 901.73, 917.95] ms | **9.02 ms/op** |

数据来源：`bench_results/linkrs-simvec.log:265-276`

- `batch_100` 单元素成本 = 901.73ms / 100 = **9.02 ms/op**，比 `single` 的 915 µs/op 慢 **≈9.8×**。
- 即"批量"接口是**负优化**：批量写入预期吞吐收益完全没实现，反而逐元素慢近 10 倍。

## 影响

WAL upsert 的批量路径不可用——任何调用 `batch_100` 的代码都比逐条写更慢，违背批量接口设计初衷。

## 疑似根因

- `batch_100` 可能未真正合并 WAL 记录 + 单次 fsync，而是逐条仍走单条写入 + 同步，外加批量路径的额外锁/大 buffer 重建开销；
- 901ms/100 ≈ 9ms/op 接近 `single` 的 10×，疑似批量路径每次都重做单条的全部工作并叠加额外成本。

## 建议

1. 排查 `batch_100` 实现：是否合并 WAL 记录、是否单次 fsync / 单次序列化；
2. 与 `single` 对齐语义后对比 per-op 成本，目标批量应 **低于** single 的 per-op 成本；
3. 若批量是为吞吐设计却更慢，修复前应在 API 文档标注或在内部 fallback 到批量更优实现。
