# 写入路径使用指导

本文说明四种写入路径的语义、成本与选用原则。数字为 devs 共享宿主（HDD）实测，
SSD 上绝对值更小，但相对关系不变。

## 路径一览

| 路径 | 入口 | 持久语义 | 适用场景 |
|---|---|---|---|
| 自动提交单写 | `insert_vertex` / `insert_edge` | 每条语句一次提交、一次落盘 | 交互式单条、低频写入、语义测试 |
| 显式事务 | 绑定事务上下文后多次写入，一次提交 | 全部语句一次提交、一次落盘 | 交互式多语句、需原子性的业务单元 |
| 批量 API | `batch_insert_vertices` / `batch_insert_edges` | 一次提交、一次落盘 | 同类型大批量建图、fixture、导入 |
| 组提交 | `execute_batch_grouped(queries, group_size)` | 每组一次提交、一次落盘 | 多语句 DML 流、每组内语义等价即可 |
| 会话批量 | `begin_bulk_load` | 触发器抑制、按会话结算 | 超大批量导入（见批量导入文档） |

## 成本 reality check

- HDD 上一次落盘约数十毫秒。自动提交单写 200 条边约 53ms/条，
  不是 bug——每条就是一次持久提交。
- 显式事务 200 条边约 0.4ms/条，批量约 0.3ms/条：分摊的都是落盘次数。
- 顶点同理：5 万顶点单条循环在 HDD 上是数十分钟量级，fixture 必须走批量。

## 反模式

- 用单条循环做任何规模性建图、fixture、压测（probe 已改批量 fixture 为例）。
- 把"单条慢"当作引擎 bug 去优化单条路径的落盘：那是持久语义本身，
  动它等于动正确性。批量化永远是正解。
- 混用：同一批数据一半单条一半批量，导致提交点不可预测，恢复分析困难。

## 选用流程

1. 同类型万级以上走批量 API。
2. 多语句且需原子性走显式事务。
3. 多语句 DML 流、不需逐条持久、要限流落盘次数，走组提交并调 group_size。
4. 其余走自动提交单写。
