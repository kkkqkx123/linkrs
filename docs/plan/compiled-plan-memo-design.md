# 已编译物理计划复用设计（独立任务）

## 1. 背景

当前分区计划缓存的命中发生在逻辑优化之后。重复查询仍然付出 parse、plan、
optimize 的固定成本，目标查询实测约 0.96 ms，其中 optimize 约 0.84 ms。
本方案针对这个固定成本，属于通用编译缓存任务，与有序存在性形状的快速优化
路径相互独立。

## 2. 目标

在同一会话内重复执行同一查询文本时，命中后直接复用已编译的 `PhysicalPlan`，
跳过 bind、逻辑规划、优化与物理构建；冷执行仍走完整路径。结果数据永不缓存。

## 3. 缓存键

键由以下不可变上下文组成：

- 规范化后的查询文本与参数类型签名；
- 空间名、schema 版本与布局版本；
- 分区配置哈希、worker 数等影响物理形状的规划配置；
- 读上下文标识，特别是是否存在 staged write；
- 优化统计反馈的 epoch 或指纹。

命中后仍执行现有的 checked-serve 校验；任一项不匹配立即失效并重新编译。

## 4. 失效条件

- DDL、schema/layout 版本变化；
- 分区或代价配置变化；
- 统计刷新或反馈写入导致优化决策变化；
- 同一文本在普通读与 staged write 读之间切换；
- 参数值类型变化导致参数签名变化。

失效必须发生在服务缓存计划之前，不能通过降级语义掩盖过期计划。

## 5. 风险与控制

- 范围只覆盖只读、可缓存查询；DML 沿用现有 memo。
- 新缓存置于现有 `compile_or_get_cached` 的入口之前，但复用其 checked-serve
  出口，避免两套校验语义漂移。
- 增加命中/失效/校验失败计数器，bench JSON 区分冷编译与物理计划缓存命中。
- A/B 要求冷执行计划形状不变、热执行结果逐值一致；分区、TopK、join 与 DQL
  全量门必须通过。
- 分阶段落地：先只缓存非分区计划，再评估分区计划；每次单独采集指标。

## 6. 验收

- 重复执行的热查询 `compile_median_us` 接近 cache probe 成本；
- `plan_cache_hits` 与新增的物理计划缓存命中计数一致；
- 失效注入后下一次执行必须重新编译并得到正确结果；
- 不因缓存引入结果数据复用或跨读上下文的脏读。
