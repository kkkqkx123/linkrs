# CSR 变体整改分阶段方案

本文对应 `docs/issue/csr_variant_issues.md` 中的问题清单，给出分阶段修改方案。以自然语言描述目标、范围、步骤与验收，不含完整代码片段。

总体原则：正确性、可靠性、防误用优先于兼容性，不保留有歧义的旧语义。只修改原模块，不新增替代模块，不按好坏标准拆分模块，名称保持职责导向。全部编译与测试合并为尽量少的运行批次。

## 第一阶段：统一观测与回收语义

目标是让碎片观测、回收探测、回收需求判断三组接口在七变体上互相一致，消除按入口行为分裂的问题。

范围限定在变体分发层与底层各形态的回收观测实现，包括变体核心观测方法、变体 trait 适配、组容器透传、边表回收触发所依赖的接口语义。不涉及写路径错误码与持久化格式变更。

做法是先明确每种形态的回收能力契约：通用多边与单槽具备完整行回收能力，纯拓扑以物理空洞表达删除故可观测但回收语义与时间戳无关，内联标量随拓扑双列同步回收，冻结堆具备堆内回收能力，映射视图因需重建服务文件而不具备原地回收能力，空占位无回收。然后将该契约落实到分发层：碎片口径对具有主块加溢出结构的形态给出真实计算而非零，回收探测统一委托到底层实现而非对部分形态短路，需求判断统一基于可回收计数而非按形态硬编码，映射视图明确表达不支持原地回收而非伪装成无碎片。底层纯拓扑的计数恒零问题随之处理，使其行普查与可回收判断自洽。组容器与边表不新增逻辑，只复用统一后的变体接口。

验收以边存储行层与组层单测为主：构造各形态含空位与墓碑的行，分别检查三组接口返回值一致；构造映射与冻结同内容组，检查两者在可回收项上的表达差异符合契约；运行组级回收触发路径，确认纯拓扑与内联标量组不再被静默跳过或误判。建议与第二阶段验收合并运行，减少编译次数。

风险在于观测值变化可能触发既有阈值逻辑更频繁地回收。应对是本阶段不调整组级合并门限，只修正观测口径，门限调优留待全量回归后再议。

## 第二阶段：统一写拒绝与定位能力

目标是让只读形态与空占位在全部写入口下行为一致，并补齐单槽形态缺失的定位能力，消除静默零与报错混用的情况。

范围限定在变体 trait 适配、底层单槽实现、冻结与映射实现的写入口、空占位默认分支。不改变记录形态选择与冻结流程。

做法是先统一只读语义：冻结与映射的所有变更入口一律显式拒绝，不再出现部分入口返回零的静默行为；调用方只需处理拒绝一种情况。空占位同样收敛到统一风格：读返回空，变更入口统一拒绝或统一表达未找到，不再按入口区分三种风格，具体收敛方向按边表调用方的处理成本选择其一并同步更新文档。然后补齐单槽定位能力：为单槽实现按边定位与定位删除恢复，使其与通用多边、纯拓扑、内联标量对齐；单槽行内至多一槽，定位实现为常量复杂度，不引入新结构。定位跨变体复用的防护保持不变，仍要求层间交接先按键重解，定位写对无能力形态保持显式失败。

验收以变体分发单测与边表写路径单测为主：对冻结、映射、空占位分别调用全套变更入口，检查错误风格一致；对单槽构造含活边与墓碑的行，检查定位读写与按编号读写结果一致；检查跨变体位置复用仍被拒绝而非静默回退。建议与第一阶段测试合并为一次边存储测试运行。

风险在于收紧语义可能使既有调用方首次遇到更多显式错误。应对是按失败关闭原则处理：宁可报错也不静默成功，调用方按新契约调整，符合本次不保留向后兼容的要求。

## 第三阶段：厘清持久化、清空与冻结语义

目标是消除持久化标签共享带来的误解，降低冻结路径代价，明确映射清空回退与形态演进的操作指引。

范围限定在变体持久化、组冻结与解冻、映射服务视图开关、记录形态迁移指引与文档。不改变七变体划分本身。

做法是先正视冻结与映射共享标签的事实：转储保留权威字节，加载一律重建堆形态，映射身份不持久。在文档与方法说明中明确该不对称，并为检查点加载路径补充分支注释，使调用方不再假设视图类型可 roundtrip。映射清空回退为空占位的类型跃迁同样在组层显式处理，避免清空后按原类型调度。然后优化冻结路径：纯拓扑与内联标量的冻结不再经由临时通用多边全量重建，改为按目标紧凑布局直接打包；内联标量含有效值时禁止冻结的限制保留，但将其前置检查提前到冻结规划阶段，并指引用户先迁移到列式形态，避免在耗时打包后才报错。记录形态自动推导的锁定语义补充用户可见提示：建表时说明推导结果与后续演进成本，模式变更破坏前置条件时给出迁移指引而非泛化错误。墓碑复用水位的传播范围同步澄清：仅通用多边生效，其余形态忽略，构造新变体时不再给人以全形态生效的印象。

验收以持久化往返单测、冻结解冻单测、服务视图开关单测、形态迁移单测为主：检查映射转储加载后为堆形态且逻辑内容一致；检查清空后变体类型与后续分支行为符合预期；检查纯拓扑与内联标量冻结不再经过临时表且内容一致；检查含有效值的内联标量冻结报错信息指向迁移操作。建议单独运行一次含检查点与服务视图的测试批次。

风险在于冻结路径改动触及数据重建逻辑。应对是保持逻辑内容不变的红线：时间戳过滤读在冻结前后观察到相同逻辑项，只允许物理顺序变化；解冻重演保持同样红线。

## 第四阶段：收紧读遍历与分发可维护性

目标是降低内联标量值列漏读、范围查询语义放宽、行有序假设误用三类误用风险，并约束未来新增变体时的遗漏。

范围限定在变体读方法、迭代器枚举、值伴随访问、范围访问、行有序说明与查询层使用约束。不新增遍历方言，不新增变体。

做法是先强化内联标量值配对：拓扑迭代与值读取保持配对使用，文档与方法命名明确警示单独遍历拓扑会丢值，边表侧的内联值读写统一经由配对入口，避免分散的二次查询。范围查询对纯拓扑与内联标量的半键丢弃行为改为显式化：在接口说明中声明排序键半被忽略，调用方需按端点区间构造查询，跨形态复用同一二元组区间时由调用方负责收紧而非分发层静默放宽。行有序契约保持按形态承诺：冻结、映射、单槽有序，其余无序承诺，查询计划只在承诺有序的形态上选择二分，其余走线性扫描；内存态有序标志不持久的现状保留，但计划缓存不得跨重启复用该标志。分发可维护性方面，为新增变体整理一份存于代码注释之外的检查清单：枚举、宏分支、持久化标签、迭代器、维护、值、文档需同步修改，上线前按清单逐项核对。

验收以读路径单测与查询层回归为主：检查内联标量遍历配对与单独遍历的差异符合文档；检查范围查询在纯拓扑与内联标量上的实际扫描范围符合声明；检查行有序标志在加载前后重建一致；按新增变体检查清单做一次走查而不实际新增变体。建议与既有查询回归合并运行。

风险较低，主要为文档与注释更新。应对是本阶段不改变任何持久字节与错误码，只收紧说明与调用约束。

## 测试与落地顺序

四个阶段按顺序落地，前两阶段可合并验证，后两阶段各独立验证。全程合并为三次左右的编译测试批次：边存储行层与组表层一次，检查点与服务视图一次，读路径与查询回归一次。每批次附带格式化检查。每个阶段完成后更新 `docs/storage/csr/` 下对应现状文档，使代码与文档保持一致。
