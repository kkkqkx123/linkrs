# 四个遗留点的后续分析与设计

日期：2026-11-16
对应问题：`docs/issue/count-slow-vs-ladybug.md`
前置方案：`docs/plan/count-slow-vs-ladybug.md`、`docs/plan/metadata-count.md`

本文对元数据计数收尾时记录的四个现象逐一回答"要不要改、怎么改"。
结论先行：恒真过滤残留要集中消除；操作上下文门限本身不再收紧、改的是
embedded 调用侧的绑定选择；无方向元数据本次不做、只做慢路径语义锁定；
存活期在元数据的拒绝保持不变、要修的是流式游标扫描漏滤过期行。
四项各自独立，可分开落地，任一收紧都自动回到原路径，无需数据迁移。

## 一、纯计数链的 Filter(true) 残留：暂缓集中消除，先记机制

### 现状与证据

规划器对 `(n:Tag)` 生成标签成员检查过滤叠在定标签扫描之上，实测纯
计数链与简单扫描链常见双过滤形状：一个是标签成员检查，另一个是规
划期挂载的常量真适配器。谓词下推的标签消除规则擦除成员检查分支后，
只剩常量真过滤；清理批没有处理它的规则，它存活到执行。

曾尝试在恒假消除规则上增加对偶分支（字面量真且无子查询即擦除），
端到端验证发现该擦除破坏正确性，已回滚，过程与证据见下。

### 设计（已验证不可行，回滚）

曾在已有的恒假消除规则上增加对偶分支：过滤条件为布尔字面量真且
该节点不带任何子查询即擦除。触发前置本身是安全的（字面量真不引用
列、不求值，无子查询即无额外语义），但它与单遍快形状链和下游折叠
规则产生了不可接受的交互，已整体回滚，原因如下。

快形状链只跑单遍且注解批先于清理批：注解审计看到的一直是消除前形
状。擦除后，原来被真过滤挡住的两条下游改写被放行——无操作投影消除
把唯一的投影吃掉、无关过滤缺席时限制下推把限制推进扫描——最终形成
以行缺失扫描为计划输出的形态，执行层输出边界无法从纯类型列重建客户
行，`RETURN n LIMIT` 类查询从 3 行变成 0 行。真过滤节点的存在恰好挡
住这两条改写（它不在无操作投影允许的子节点表里，也挡住限制下推），
并为行缺失块重建行视图：它是当前架构下实际承重的节点，不是可有可无
的残留。

因此穿透分支不是死代码：在单遍链路上它是注解审计与清理消除之间的
排序适配。真正的根治需要无操作投影消除的行缺失感知（输入行缺失时
不得移除最后的行重建器），以及身份审计对根输出整实体位置的显式处理
（裸实体变量直达客户端时不得置身份），那是独立的正确性项目，不在本
次低风险范围内。本次回滚消除规则与检测器容忍分支的删除，保留既有
穿透分支与管道拼接处理不动。

### 验证

回滚后全量端到端用例通过，数值不变；`RETURN n LIMIT` 类查询恢复 3
行。穿透分支继续覆盖单遍链路的行跳过标记断言。

### 明确不做

本次不消除 `Filter(true)`，不改规划器构造逻辑；恒假分支行为保持不变。
根治方向（无操作投影消除的行缺失感知、身份审计的根输出整实体处理）
另立项目。

## 二、写能力 autocommit 上下文门限：门限不再收紧，改调用侧绑定

### 现状与证据

探针走 embedded 会话执行，其自动提交路径对所有语句统一绑定写能力
自动提交上下文，不做语句分类。管线内其实已有分类绑定（写与 DDL 走
自动提交写绑定，纯读走只读绑定），但 embedded 调用方在管线之前就把
写绑定传了进去，使分类逻辑对这条调用链失效。元数据门限为此放行了
"普通自动提交（非组模式）"，实测五条查询全部命中新路径。

### 门限为什么保持现状

门限的当前形态是刻意平衡的结果，不宜再收紧为只读。解释与画像语句
在管线分类中属于诊断语句，同样走写能力绑定；若门限只认只读，解释
输出将展示慢路径计划，而实际执行走元数据路径，造成解释与执行分叉。
现在的"显式写事务与组模式才拒绝"同时容纳只读绑定、普通自动提交与
诊断绑定，三者展示与执行一致。组模式共享暂存必须拒绝，显式写事务
可能持有未提交行也必须拒绝，这两条保留。

### 设计

改 embedded 会话自动提交单语句路径的绑定选择，判断复用管线已有的
语句分类函数，不另起一套分类。纯只读语句改走无调用方绑定的普通执
行入口，由管线按语句类型自行绑定只读存储；写、DDL、诊断、事务、
会话命令、批量与分组路径保持现有绑定不变。分类所需解析若失败，保
守走老路（写绑定），下游仍会报出原始解析错误，行为不变。

显式事务内语句、批量分组语句不在本次范围内：前者必须保持事务绑定，
后者语句间共享时间戳与暂存，读语句也可能读到同组写入，维持现状。

预期收益不在元数据本身（门限已放行），而在语义精度与 per 语句开销：
纯读不再消耗写时间戳、不再分配撤销日志与暂存结构；诊断语句绑定不
变，解释与执行继续一致。

### 验证

分类函数单测复用管线既有用例；embedded 端到端覆盖纯读、写、DDL、
USE、会话命令在改前改后结果一致；探针五条查询数值与计划标记不变；
对比纯读语句的写时间戳消耗确认不再增长。

### 明确不做

不改管线内部分类与绑定逻辑，不碰批量分组与显式事务路径，不收紧
元数据门限。

## 三、无方向边计数：元数据本次不做，先做语义锁定

### 慢路径语义与证据

纯计数形状走计数专用度数尾：按种子逐个去重后直接累加邻接回调，
只要求种子端存活，远端不检查，与有向度数求和一致（实测含自环、
悬空远端、跨标签种子的固件得 6：种子 0/1/2 各贡献 2/2/2，悬空边
从存活种子侧计入；解析型展开才会丢弃缺失远端，但纯计数走不到
那两条路）。折算下来，无方向纯计数等于种子端存活的出腿计数加
种子端存活的入腿计数，再减去存活自环（双腿各计一次）。

### 为什么不做

直接支持需要新的双腿计数原语（两条腿各走一次种子侧存活检查）再加
自环修正，还要把同构标签、单边类型的前置全部形式化。无方向全局
计数在基准与业务中均低频，证明负担与收益不成比例。当前拒绝分支
保留，行为正确。

### 设计

本次只做语义锁定，为将来留下可直接引用的 oracle：构造含自环、悬空
远端、跨标签种子的固件，断言慢路径无方向计数的精确值（含自环单计
与悬空远端计入），并断言元数据路径明确拒绝该形状。未来若要支持，
公式为种子端存活的出腿计数加种子端存活的入腿计数减存活自环数，复用
有向元数据已有的种子侧存活检查，只是两条腿各走一次再修正自环；门限
定为单边类型、源宿同标签、无开放类型、无截断采样、端点标签无存活期，
执行期复核与快照规则与有向路径一致。

### 验证

新增慢路径语义锁定用例（数值按公式手算钉死）；既有无方向回退用例
继续通过；解释输出仍不出现无方向元数据标记。

## 四、存活期：元数据拒绝不变，修流式游标漏滤

### 两侧行为证据

读路径存在两套存活期处理，行为不一致。物化读路径（按标签扫描顶点、
按节点取边、点查）在构造实体后逐行判定过期并丢弃，"过期视为不存在"
的契约成立。流式游标路径（顶点与边游标的批量、扁平、列式读取）只解
码属性与谓词下推，从不判定过期；上层流式扫描算子与装配层也没有任何
存活期处理。纯拓扑扫描更进一步跳过属性解码，连判定所需字段都不读。

后果是同一查询在不同引擎路径下结果可能不同；元数据对存活期标签的
拒绝回退到的恰恰是游标侧慢路径，存活期表的计数当前可能包含过期行。
各拓扑快路径在存活期激活时回退物化读的做法是对的，漏的是最普通的
游标扫描本身。存活期以墙钟逐行判定，另有可指定时刻的变体可供扫描内
部统一时间基准。

### 设计

元数据的存活期拒绝保持不变：免解码计数不可能精确判定逐行过期，拒绝
回退是正确选择。远期可评估的中间层（只解码存活期单列的计数）本次只
记录方向，不实现。

要修的是游标扫描：在顶点与边游标的批量扫描处，按表存活期配置过滤
过期行，复用既有基于属性切片的判定原语，时间基准与物化读路径一致
（扫描内可固定一次取值，避免行间时钟漂移）。只改游标原模块：按表
打开时判定一次该表是否配置有效存活期，无配置的表零代价；纯拓扑扫
描在存活期激活时自动失效（至少解码存活期列），不深入无属性行的快
速路径。游标暂存行同样适用统一过滤。

### 验证

先补复现测试作为立案依据：同一存活期固件分别走物化读、游标批量、
游标扁平、列式批量与全局计数，五方数值一致且过期行均不可见；再合入
修复并全量通过。既有非存活期扫描性能用例确认无回归（无配置表多一
次分支判定之外无额外解码）。

### 明确不做

不放宽元数据对存活期的拒绝，不新增存活期专用计数原语，不改物化读
路径与清理语句行为。

## 落地顺序与回滚

最终状态：游标存活期过滤、embedded 纯读绑定、无方向语义锁定三项已
落地验证；恒真消除经端到端验证证明不可行而回滚，设计第一节保留完整
的机制记录与根治方向。四项修改各自收敛于原模块，任一回滚即还原对应
文件，无需数据迁移；解释输出的计划标记变化只涉及新增断言，不改变查
询数值。
