# 整图超内存长期设计

## 定位

本文只作为后续参考，本阶段不实施。当前产品承诺仍是内存优先：查询中间结果、冷顶点属性列和非活跃索引代可以落盘，主键索引、活跃索引代、边拓扑和版本链必须常驻；超过硬水位且无法回收时按容量错误拒绝写入。

## 为什么暂不实施

- 容量边界是对外承诺的一部分。放开后会改变写入准入、恢复语义和故障表现，不是调参或查询侧优化可以覆盖的。
- 主键索引、拓扑 CSR 和 MVCC 版本链目前直接与内存结构绑定；要超内存必须引入统一的页帧生命周期，并处理 pin、脏页、淘汰与恢复，影响面远超查询执行器。
- 当前需求由本地轻量部署驱动，查询侧工作内存与冷列落盘已经覆盖主要容量风险；没有证据表明需要承担整图落盘的复杂度和性能不确定性。

## 触发条件

只有在出现明确的持续写入规模需求、且接受容量语义变化时，才启动本设计。启动前应先用真实数据集确认瓶颈确实落在主键、拓扑或版本链，而不是查询中间结果或索引冷块。

## 设计原则

- 一个问题一套机制：在现有 `vertex_table`、`index_data_manager`、`edge_table` 和持久化模块内扩展，不新建平行存储引擎。
- 容量与工作内存分离：页缓存负责容量，查询预算继续负责工作内存；两者不互相冒充。
- 页帧生命周期单一来源：pin、unpin、dirty、淘汰和回收只由缓冲层维护，调用方不自行缓存跨操作页引用。
- 失败优于静默膨胀：无法pin住所需页、无法写回或配额耗尽时返回结构化容量错误。

## 分阶段演进

### 第一阶段：磁盘分级主键索引

在 `vertex_table` 内把主键映射拆成热层与磁盘桶。热层保留近期命中的键和脏页；查找未命中时通过缓冲层加载对应桶页。写入路径在提交前完成键页 pin 与脏标记，检查点把脏页并入快照。此阶段仍不开放拓扑和版本链超内存，写入准入继续按现有口径执行。

### 第二阶段：边拓扑分页

把 CSR 的行指针和邻接数组按页切分，迭代器和邻居算子通过缓冲层访问页；热点页保持 pin，冷页按 LRU 淘汰。排序后的行内有序性仍由 CSR 元数据维护，淘汰只回收页帧，不改变逻辑顺序。遍历算子需要显式处理缺页与卸页，不能假设邻接数据常驻。

### 第三阶段：版本链持久化

把版本链快照和增量写入检查点 sidecar，内存只保留活跃快照覆盖的前缀。GC 使用已发布的检查点 watermark 推进，长事务阻塞时保留必要历史但不无限增长。重启时按检查点恢复版本链，再重放之后的 WAL 意图。

## 恢复与兼容性

每一阶段都必须先定义持久化格式与恢复入口，再放开对应结构的内存上限。恢复失败、格式不匹配或校验不通过时明确报错；不为开发阶段数据提供旧格式回退。阶段之间没有临时兼容层，未完成的容量继续由准入错误拒绝。

## 验收口径

- 主键查找、邻居遍历、版本链读取在受限内存下结果与全内存基线逐值一致；
- 冷页淘汰后再次访问结果一致，脏页在检查点和重启后仍然可见；
- 内存占用受预算约束，淘汰与写回次数可观测；
- 无法回收或无法写回时返回明确容量错误，不产生孤儿文件或静默数据丢失；
- 所有新格式都有重启恢复测试，且旧阶段的容量承诺不被削弱。
