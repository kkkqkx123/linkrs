# 认证剩余三项设计决策与细化方案（含跨库对标与实现评审）

状态：设计待评审，未进入实现。范围覆盖 `permission-auth-refactor.md` 列为不做事项的三项，外加评审中发现的已有实现缺陷。

优先级：正确性与可误用抵抗优先，不考虑向后兼容，不做版本升级。

## 一、其他数据库的通行做法

### 口令策略

- MySQL 采用独立的口令校验组件，执行点挂在建用户、改用户、改口令三条语句的执行路径上，与客户端形态无关；锁定账号建用户同样必须满足策略；错误码统一为口令不满足策略。复杂度分三档：仅长度、长度加四类字符计数、再加字典词检查；另有开关禁止口令包含用户名。过期、历史复用、改密需验证当前口令是三个正交维度：过期按全局天数加按账号覆写，历史按最近 N 次与 N 天内两套口径，自助改密可要求必须提供旧口令。
- PostgreSQL 采用口令检查钩子，在建角色与改角色时触发；明文口令做长度、字母加非字母、不得包含用户名检查，可选接常见弱口令字典；对已加密传入的口令只能做等同用户名猜测，明确建议高安全场景改用外部认证。过期通过角色的口令有效期时间戳表达。
- 共同点：校验收敛在语句执行层而非各接入网关重做一遍；前端只做强度提示，后端是唯一权威；策略默认关闭或宽松，由管理员显式收紧。

### 会话令牌

- Neo4j：服务端不发会话标识，每次请求携带基础认证或外部身份令牌，驱动层管理连接；无会话猜测问题。
- MongoDB：默认挑战应答认证，口令不走明文，服务端不颁发承载令牌；逻辑会话句柄仅为客户端概念。
- Nebula 的 HTTP 网关：颁发经签名的会话标识并放在 Cookie 中传递，签名用于网关侧防篡改。
- pgAdmin：会话落盘并做完整性签名加内容加密，浏览器侧 Cookie 设为仅 HTTP 读取、安全传输、同站限制；会话标识本身高熵随机，签名绑定 Cookie 与文件防止混用。
- 行业共识（与令牌最佳实践一致）：可撤销的会话一律用服务端有状态的不透明高熵令牌；签名只解决无状态验签问题，对必须查表的会话没有免查表收益；传输窃听靠加密通道解决，重放靠过期与轮换解决，签名解决不了这两者。

### 跨域与前端存放

- 数据库线协议本身无跨域概念，跨域只存在于 HTTP 网关与管理后台。通行做法是生产环境显式白名单，绝不在生产使用通配来源；通配来源与携带凭证按规范互斥。
- 令牌存放分两派：后台管理类单页应用常见做法是浏览器本地存储加自定义请求头，优点是免跨站请求伪造，代价是跨站脚本可直接读取；Cookie 派用仅 HTTP 读取加同站限制防读取，代价是必须配套跨站请求伪造令牌。双方都承认跨站脚本得手后都守不住，纵深在于内容安全策略、输入转义与最小化令牌寿命。

## 二、原有三项决策是否合理

- 口令策略分期落地：合理，但执行点需要调整（见第三节）。原方案把查询通道校验放在查询守卫层做语句二次解析，脆弱且与执行器各执一份解析逻辑；对标 MySQL 与 PostgreSQL，应收敛到执行路径上的单一钩子。
- HMAC 签名明确不做：合理，与主流数据库与令牌实践一致。单节点有状态会话加签名没有安全收益，只有密钥管理成本与全链路类型破坏成本。
- CORS 保持开发宽松加生产白名单：合理，与各家管理后台做法一致。但原方案缺了已有开关被路由层完全忽略这一事实，须把让开关真实生效列为必改项，而非仅新增字段。

## 三、已有实现中发现的问题

按下述顺序处理，前两项建议与口令策略第一期同批修复，后续项随会话与跨域迭代修复。

- 建会话端点重复创建会话：建会话处理器先调用一次认证（认证内部已创建一个会话并丢弃），随后又创建一个会话返回。每次经该端点登录泄漏一个孤儿会话，直到空闲回收。应复用认证返回的会话，不再二次创建。
- 改密后旧会话不失效：管理员重置口令与查询通道改密均不清理目标账号的既有会话，只有禁用账号才会清理。改密后窃得的旧会话继续有效。应对除当前会话外的该账号全部会话做清理，与禁用账号行为对齐。
- 强制改密状态机存在死锁：中间件在需改密时仅放行查询路径，阻断管理面的用户改密端点；用户被要求改密，却调不到改密接口，只能走查询语句。应把自助改密与管理员重置口令端点加入放行名单，或放行整个认证自助分组。
- 默认口令违反默认策略：默认账号与默认口令均为弱口令，而默认策略要求最小长度加三类字符，种子账号开箱即不合规。处理方式是种子账号走强制改密流程豁免一次，或初始化时生成合规随机口令并打印一次，文档写明二选一，不允许静默放行。
- 会话标识明文进日志：会话创建与删除均在信息级别日志打印完整标识，日志聚合后等同令牌泄露。改为只记脱敏前后缀或哈希。
- 会话标识生成无碰撞检查：随机数直接插入映射，极小概率覆盖他人会话。插入前判重，冲突则重试。
- 登录响应过期时间恒空：响应体过期字段恒为空，前端无法做过期提示与主动续期。应按空闲超时填入实际过期时间。
- 复杂度下限与默认值自相矛盾：配置校验允许最小长度低至六位，默认却为八位；放宽下限的同时没有说明六位口令在默认四类字符下的真实强度。建议下限与文档对齐到八位，或明确六位仅供测试。
- 哈希成本存在两个真相源：鉴权配置中的成本字段与核心用户模块的环境变量各行其是，可能出现配置改了但哈希行为不变。收敛到一处读取，另一处转为透传。
- 中间件只返回空状态码：鉴权失败一律裸状态码，前端无法区分过期、锁定、需改密。改为结构化错误体，至少区分未认证、已锁定、需改密三类。
- 跨域开关被忽略：配置中的跨域开关没有任何代码读取，路由层写死通配。必须让开关真实生效（见第五节）。
- 前端会话存于持久本地存储且无过期联动：令牌长期驻留，跨站脚本可直接读取；且过期字段恒空导致前端无法预判。短期保持本地存储但接入过期时间与未认证自动登出；长期再议仅 HTTP 读取的 Cookie 方案（需配套跨站请求伪造防护，不在本期）。

## 四、口令策略细化方案（调整后）

第一期范围：长度、字符种类、不得包含用户名三项无状态校验，覆盖全部写入入口。

- 配置侧新增一个纯校验方法，逐项检查最小长度、四类字符开关与用户名包含关系，返回首个不满足项的英文原因。特殊字符集合采用常见可打印符号子集并在文档中写明，避免 Unicode 判定歧义。是否启用字典检查留待后续，不在本期引入词表依赖。
- 执行点放在两处，均为明文口令必经之处：服务层管理员建用户与重置密码通道，以及查询执行器的用户管理算子（建用户、改用户携带新口令、改密携带新口令）。不再在查询守卫层做语句二次解析。存储引擎只需透传既有接口，不新增依赖；存储侧已可读取配置，不存在反向依赖问题。
- 自助改密保留旧口令验证（存储层已有），策略只约束新口令；管理员重置跳过旧口令验证但仍受复杂度约束，与 MySQL 的双轨语义一致。
- 鉴权禁用与单用户模式下仍执行写入校验，禁用鉴权只是跳过登录环节，不放行弱口令。
- 改密成功后清理目标账号除当前会话外的全部会话，管理面与查询面统一。
- 错误映射统一为参数错误，不向调用方透露超出必要的信息；锁定账号建用户同样拒绝弱口令，与 MySQL 行为对齐。
- 前端用户管理页增加强度提示，仅做体验优化，后端保持唯一权威；是否单独暴露强度评估接口待定，默认复用同一套规则在前端做轻量镜像。

第二期（另立迭代）：过期强制。登录成功后按密码修改时间计算存活期，超期则在登录响应中标记并由中间件阻断非改密请求；与强制改密状态机共用放行名单。

第三期（另立迭代）：历史口令。需先在用户信息中新增历史哈希数组并升级快照版本，旧快照缺字段默认空数组，再接入新口令与历史比对及轮转写入。

## 五、会话方案（维持不做 HMAC，修复实现缺陷）

- 维持高熵随机不透明令牌，不引入签名。熵空间、查表模型、单节点定位均不支持签名的成本。
- 必改实现缺陷：复用认证会话消除重复创建、改密清会话、日志脱敏、生成时判重、登录响应填实际过期时间、中间件结构化错误。
- 运维指引：生产必须启用加密传输；保持空闲超时与后台回收；禁用或删除用户时保持现有清会话行为并覆盖后续新增管理入口。

## 六、跨域细化方案

- 配置侧在 HTTP 服务配置中新增来源白名单列表，默认值为空以保持当前本地行为；校验阶段对条目做来源格式检查，非法条目启动失败。
- 路由层跨域构造函数改为接收服务配置：开关关闭时不挂载跨域层；开启且白名单为空时维持宽松组合并输出警告日志；开启且非空时构造严格来源列表，收敛请求方法与请求头集合，设置预检缓存时长。当前会话标识走自定义请求头而非 Cookie，默认不开启凭证模式，避免通配与凭证的规范冲突。
- 启动日志输出当前跨域模式，宽松用警告级别，严格用信息级别。
- 配置示例与部署文档同步更新，给出严格模式样例与生产四项清单：关闭宽松模式、填精确来源、启用加密传输、前后端来源对齐。前端调用方式不变，只需确认生产构建的接口基地址与白名单一致。

## 七、迭代顺序与验收口径

- 第一迭代：口令复杂度三项校验加双通道接入，附带修复重复建会话、改密清会话、强制改密放行名单、默认口令豁免四项缺陷。
- 第二迭代：跨域白名单加开关真实生效，附带修复日志脱敏、会话判重、过期时间填充、中间件结构化错误。
- 第三迭代起：口令过期强制、历史口令存储变更、哈希成本真相源收敛。
- 签名方案无迭代安排。
- 统一约束：不引入新模块替代旧模块，不做兼容老数据的特殊分支，所有编译与测试命令沿用项目既有方式并限制并行度。
