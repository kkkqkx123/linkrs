# Linkrs 多语言绑定设计

本文对照 `crates/simvec` 已落地的多语言绑定，分析 Linkrs 如何实现同等能力，并给出分阶段的设计方案。只描述设计，不贴完整代码。实现时只改原模块，不新增替代模块；绑定按语言职责拆分，不造与现有模块重复的新封装层。

约束：Linkrs 是带存储引擎、事务、查询优化器的图数据库，无法像向量引擎那样整体装入浏览器内存，因此 WASM 绑定不在本方案范围内，下文有专门论证。

## simvec 绑定的现状对照

simvec 的绑定体系分三层，Linkrs 应当整体复用这一形态，而不是另起一套约定。

第一层是稳定的 C ABI。Rust 侧以特性门控编译 C 接口模块，产物同时输出动态库、静态库与 Rust 库三种形态，头文件由构建脚本在开启特性时自动从源码重新生成并与提交版本比对，保证头文件永不漂移。出入参约定是整套绑定的基石：所有入口返回整型状态码，入参一律借用 Complex 值走 JSON 文本复用已有序列化形状，向量走连续单精度数组，出参由库侧分配并由统一的释放函数交绑定层回收，调用者永远不直接接触释放。错误细节通过句柄上的最近错误码与最近错误文本查询，打开失败这种尚无句柄的场景走全局错误文本。

第二层是五个常驻内存形态的原生绑定：Python、JavaScript、Go、Java、R。每个绑定都是同一 C ABI 上的薄封装，封装范围全量对齐，方法命名只按各自语言习惯改写。动态库定位策略五端一致：优先读环境变量中的显式路径，其次按包相对路径查找工作区构建产物，找不到时抛出基类异常并列出尝试过的路径，打包只发布纯代码包，动态库由调用者先构建并指定路径。错误映射五端一致：少数高频状态码映射为具名类型化异常，其余统一降级为基类并保留原始数字码。资源管理五端一致：关闭可重复调用，辅以终结器或上下文管理器兜底。冒烟测试五端场景对等，覆盖集合、写入、读取、载荷索引、维护、事务全链路，另有 Rust 侧回归测试覆盖空指针、非法输入与正常往返。

第三层是浏览器内存形态的 WASM 绑定，基于内存引擎加边界薄封装，与文件语义相关的能力按空操作或缺席处理，持久化靠调用者自理快照加可选的存储适配。这是 simvec 独有的分支，Linkrs 不复制。

需要额外注意两个语言的桥接实现：Java 与 R 不是直调 C 库，而是各带一个薄 C 桥接层。Java 桥统一走标准字节形态传递文本以避开改写版编码问题，出参加载到宿主后统一释放；R 桥统一返回状态码、载荷、错误文本三元组，错误映射完全留在 R 侧。这两个桥接层的存在意味着新增语言绑定时，凡是宿主 FFI 不能直调 C 的语言，都要先写 C 桥。

## Linkrs 现状与差距分析

Linkrs 已具备 C API 基础，但规模与语义复杂度都比 simvec 高一个量级，不能直接照搬全量封装，需要先做收敛。

规模差距。simvec 对外约五十个导出函数、单一引擎句柄；Linkrs 头文件约三千八百行，近一百五十个入口，句柄多达八种：数据库、会话、事务、结果集、预处理语句、批量写入器、配置、繁忙处理器，外加迁移报告等一次性结构。一次照单全收的绑定既写不完也测不完，必须分层覆盖。

句柄关系差距。simvec 只有一个句柄，没有生命周期顺序问题。Linkrs 的句柄构成有向关系：数据库派生会话，会话派生结果集、事务、预处理语句与批量写入器，事务之下还有保存点。绑定层必须强制释放顺序，子句柄先于父句柄释放，父关闭后子句柄一律视为无效。这是设计中最容易出错的部分，需要每个语言的封装类在构造时持有父引用，关闭时先级联释放子对象。

调用约定差距。两处最关键。第一，Linkrs 的结果集有两种读取风格：游标风格的逐格访问器与整行整集的 JSON 快捷导出。simvec 只有 JSON 一种。绑定应当以 JSON 快捷导出为默认形态，仅把逐格访问器留给进阶场景，这样首版工作量接近 simvec 的查询封装。第二，Linkrs 有回调穿越 FFI 的能力：标量函数与聚合函数的注册、提交与回滚与更新钩子、查询跟踪回调。这些回调要求宿主语言函数指针反向进入 Rust，在 Python、JavaScript、R 侧需要各写蹦床层，实现成本高且容易引入悬垂指针。首版应当明确排除回调类能力，只保留声明式接口。

线程模型差距。simvec 绑定在 Go 侧用读写锁串行化句柄即可。Linkrs 会话侧已有显式契约：会话句柄不得跨线程并发共享，钩子回调永远运行在触发操作的线程上。同时嵌入式数据库在内部自带异步运行时处理向量等后台工作，绑定层不需要也不应该自建运行时。结论是绑定层对每个会话加互斥串行化，并将会话绑定到创建线程或文档中声明禁止跨线程共享，把规则写进各语言自述，而不是试图在绑定层实现跨线程调度。

错误模型差距。simvec 是十四个扁平状态码。Linkrs 是两级错误：二十三个主码加四十个左右的扩展码，分别定位大类与细分原因，错误文本走线程本地存储，会话上还附带错误位置偏移与扩展码。绑定应当映射为两级异常体系：主码决定异常大类，扩展码作为异常属性保留，错误位置偏移作为查询异常的属性暴露。具名映射只覆盖高频主码，其余降级为基类并保留数字码，与 simvec 的划分哲学一致。

构建产物差距。simvec 的包声明同时输出动态库、静态库与 Rust 库，这是原生绑定的前提。Linkrs 根包目前只输出 Rust 库，无法产生可供外部语言加载的动态库。这是 Tier 0 必须先修的前置条件，没有之一。

传输路径的额外选项。Linkrs 与 simvec 不同，还拥有基于传输 DTO 的 HTTP 客户端与可选的远程服务层。这意味着 Linkrs 绑定天然有两条传输可选：直调嵌入式动态库，或走网络协议连独立服务。直调的优势是零依赖服务端、语义与嵌入式完全一致，代价是每个宿主都要解决动态库定位；网络方式的优势是纯语言实现、免编译，代价是需要先部署服务。方案采用直调为主、网络为辅：首版五个绑定全部走嵌入式直调以复用 simvec 经验，网络绑定只作为后续可选补充，不在首版范围内。

## 为何不做 WASM

simvec 能做 WASM 的前提是存在一个专为内存设计、无文件语义、无后台线程的内存引擎，绑定只需处理索引构建等操作的空操作语义与快照导入导出。Linkrs 不具备这个前提：存储是内存映射容器加预写日志，事务与同步协调器依赖后台任务，向量与全文索引依赖运行时与文件目录。把这些全部抽象掉等价于重写半个存储引擎，投入与一个纯内存图库相当，且浏览器场景下图数据库的真实需求极弱。结论是 WASM 明确排除，浏览器与边缘侧需求由独立部署的服务加网络协议覆盖，不在本方案内。

## 设计方案

### 总体路线与目录布局

复用 simvec 的三层形态：C ABI 加固先行，每个语言一个薄封装目录，包内附类型描述与对等冒烟测试。目录放在仓库顶层，与 simvec 将其绑定放在自身包目录下的做法对称：顶层新建绑定目录，其下按语言分子目录，每个子目录自带自述、库定位逻辑、错误映射、高层封装与冒烟测试。绑定目录不进入工作区成员，不参与 Rust 构建。

动态库定位沿用 simvec 的环境变量优先加构建产物回落策略，变量名改为本项目前缀。所有自述统一声明调用者保持绑定与动态库来自同一检出，避免版本错位。版本号跟随工作区，不独立演进。

### Tier 0：C ABI 加固

在写任何语言代码之前，先完成四项加固，全部只改原模块。

第一，根包补齐动态库与静态库产物形态，使特性开启时能产生宿主语言可加载的共享库。第二，冻结头文件生成流程已存在但需补一条契约测试：头文件符号集合与源码导出函数集合双向一致，增删接口时测试先失败。第三，补齐 JSON 快捷导出的审计：凡结果集可表达的内容，必须能通过整行整集导出一次取走，避免绑定被迫逐格调用上百次。第四，把线程与生命周期契约写成文档并配测试：会话禁止跨线程并发、子句柄先于父释放、重复关闭安全、空指针与非法文本输入返回误用码而非崩溃。

### Tier 1：核心覆盖

所有五个绑定首版覆盖同一核心集合，保证任一语言可用闭环：数据库打开与关闭、内存打开、配置打开；会话创建关闭与空间切换；直接执行、参数化执行、查询校验与查询解释；结果集的 JSON 读取与释放；事务的开始提交回滚；空间、标签、边类型的增删查；会话统计；主码加扩展码的错误映射。方法命名按各语言习惯改写，语义保持一字对齐。

### Tier 2：扩展覆盖

在核心稳定后按需补齐：预处理语句的绑定与复执行；批量写入器的缓冲写入与执行；会话变量的读写快照；全文检索与向量检索入口；迁移的执行与回滚；配置的在线读取与批量更新。这一层允许各语言按需求先后落地，但落地即全量对齐已有语义，不允许子集语义分叉。

### Tier 3：明确排除

函数注册与聚合注册、扩展的装载卸载、提交回滚更新钩子、跟踪回调、繁忙处理器调优，首版明确不封装。理由是三条：回调穿越 FFI 需要每语言独立蹦床层；钩子语义与宿主垃圾回收相互作用容易出错；这些能力面向嵌入式深度用户，可通过后续专项支持，不阻塞主流读写查询场景。排除项写入各绑定自述，避免用户误判为缺口。

### 各语言形态

Python 走标准外部函数调用机制，无需编译器，首个落地。封装分四个类：数据库、会话、事务、结果集，全部支持上下文管理器与可重复关闭。复杂值走 JSON 透传，错误映射为基类加具名子类，随包提供类型存根与已类型标记。

JavaScript 走实验性外部函数接口，与 simvec 的 JS 绑定同形态。封装类与 Python 对齐，行数据经 JSON 解析为宿主对象，随包提供类型声明。关闭语义加显式资源管理符号。

Go 走跨语言编译桥接，需要 C 工具链。句柄结构体配读写锁串行化，提供是否关闭查询与终结器兜底，错误映射配辅助判断函数，分页与行数据用具名结构承载。

Java 需要先写薄 JNI 桥接层，复用 simvec 的桥接模式：文本统一走标准字节形态，出参拷贝后统一释放，错误映射留在 Java 侧。封装类实现自动关闭接口，行数据用记录类型承载，动态库定位顺序为系统属性、环境变量、构建产物、系统库路径。

R 需要先写薄 C 桥接层，复用三元组模式：每个桥接入口返回状态码、载荷、错误文本，错误映射留在 R 侧。引擎对象用外部指针承载加终结器，同一对象不支持并发调用，计数按宿主数值语义返回，复杂值经 JSON 序列化包透传。

### 测试矩阵

Rust 侧补 C ABI 回归测试：空指针、非法文本、非法 JSON、正常往返、新增接口路径。每语言一个对等冒烟测试，场景固定为打开、建模、写入、查询、载荷更新、事务、批量删除、关闭全链路，外加错误映射、重复关闭、小规模并发读写用例。加载器缺失动态库的报错路径单独成例，断言报错信息列出尝试过的路径。

### 打包分发

首版只发布纯代码包，动态库由调用者先构建并指定路径，自述统一推荐命令与路径写法。产物内嵌动态库的轮子与包管理器分发是后续工作，不在首版范围，与 simvec 当前状态一致。

### 实施顺序与验收

顺序为 C ABI 加固、Python、JavaScript、Go、Java、R。Python 与 JavaScript 无编译器依赖，先行验证核心设计；Go 验证锁串行化模式；Java 与 R 的桥接层最后写，此时核心语义已稳定。每完成一个语言即补一行能力矩阵，矩阵文件与 simvec 的绑定矩阵同格式：以头文件与源码对照为口径，逐能力标注各端有无。

验收标准：五端核心集合行为一致，冒烟测试场景对等通过；回调类排除项在自述中明确声明；任一语言缺失动态库时报错信息包含尝试路径；重复关闭与非法输入永不崩溃；绑定与动态库跨检出混用时自述给出显式警告。

## 实施状态

Tier 0 与 Tier 1 已落地并全部对真实动态库验证通过：根包补齐动态库与静态库产物，构建脚本在缺 cbindgen 时降级使用已提交头文件并告警，头文件双向一致性测试与空句柄契约测试随集成测试全绿；五个绑定（Python、JavaScript、Go、Java、R）首版覆盖核心集合，各自冒烟测试对等通过。过程中发现的两处引擎真实语义已在绑定侧适配：结果集整集导出为信封结构，取行接口直接返回行列表；查询校验失败走误用码并在消息中携带语法细节。另顺手修复仓库既有一处编译错误。能力矩阵见绑定目录总自述。

## 风险与前提

首要风险是 C ABI 仍在演进。项目处于开发期，按现有规范不做向后兼容，绑定必须与动态库同检出使用，跨版本混用不受支持，该声明写入每份自述。其次是结果集生命周期，子句柄先于父释放的规则靠封装类持有父引用强制执行，裸句柄不暴露给调用者。第三是会话线程亲和，绑定层只做串行化不做调度，跨线程共享会话属于误用，映射为误用异常而非未定义行为。第四是 Go 与 Java 与 R 的工具链前置要求，相关自述需在首节声明，不满足时直接报错而不是降级。
