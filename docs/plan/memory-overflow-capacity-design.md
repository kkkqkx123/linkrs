# 超内存数据集处理设计

## 背景与结论

当前单机图数据库以内存优先：热点拓扑、活跃索引与版本链常驻内存，冷属性列和查询中间结果可落盘。该定位适合本地轻量部署，但不能等同于“整图可超内存”。设计需要把可落盘部分与必须常驻部分分开表述，并让配置、预算和观测口径一致。

## 现状分析

### 查询侧

执行器按 chunk 流式推进，SSE 与游标按块消费，正常情况下不物化全量结果。阻塞算子持有共享的查询内存预算，预留失败后转入落盘路径：排序写有序 run 并归并，聚合、去重、物化与连接按哈希分区写 run，终端 collector 超阈值后分段落盘。run 文件带版本头、schema 指纹、分节压缩与校验，单个查询还受磁盘配额与文件数限制。

问题在于：配置文件中的单查询内存上限没有进入执行上下文，spill 目录、文件数、磁盘配额与 collector 阈值也没有配置入口；物理属性中的溢出阈值只用于解释与校验，不参与运行时决策；预算释放未做饱和保护，重复释放会抬高可用额度。

### 存储侧

存储实例以总预算、索引独立预算、软硬水位和分类记账控制 admission。写入超过硬水位时按固定顺序回收：过期缓存、索引冷块、缓存收缩、索引代回收，仍超限则拒绝写入。顶点属性列可压缩为快照落到 spill 文件或检查点 sidecar，读取时按需回炉；索引只对非活跃代做冷块淘汰。

问题在于：进程级查询 watermark 的预算固定为编译默认值，没有跟随实例预算；主键索引、活跃索引代、边拓扑与版本链仍在内存；存储侧的 `Spiller` 实际只收缩缓存，却记录了一个并不包含数据的标记文件，名称与行为不一致。

### 参考实现

Nebula 以 RocksDB 作为磁盘主存，内存 tracker 负责进程安全边界，图数据不要求常驻。Neug 用文件映射容器和巨页把容量上限交给操作系统分页。Ladybug 以带 pin 状态的缓冲管理器统一页帧生命周期，并让临时分区、 bulk copy 的主键校验 run 走真实磁盘文件。三者共同点是把“容量”与“工作内存”分开；Linkrs 已有后者的雏形，前者只覆盖了部分数据结构。

## 设计原则

- 一个问题一套机制：查询中间结果与存储常驻数据分别处理，不叠加旁路容错。
- 配置即事实：暴露出来的限额必须真正到达执行路径，默认值只能有一个来源。
- 失败优于静默膨胀：无法回收时返回结构化错误，不做无限落盘或隐式回退。
- 容量边界对外明确：允许冷属性列超内存，不承诺主键与拓扑超内存。

## 本期落地

- 在查询请求上下文中携带单查询内存预算与 spill 配置，由 API 层从统一资源配置注入，执行管线构造上下文和实例化算子时读取。
- 在资源配置中增加 spill 目录、文件数、磁盘配额与 collector 阈值，并同步更新默认配置和配置参考文档。零值的单查询内存预算解释为引擎默认，不再声称无限。
- 将 spill 文件数按单查询全局计数，提高默认值以容纳多算子共同落盘；磁盘配额随配置进入 `SpillManager`。
- 查询预算释放改为饱和释放，避免重复释放抬高可用额度，并增加对应回归。
- 进程级查询 watermark 跟随存储实例预算和水位比例，避免两个压力系统各自漂移。
- 存储侧缓存减压不再创建空的 spill 标记文件，不再对外暴露虚构的活跃 spill 列表；真实数据落盘仍由顶点列快照机制承担。

## 容量边界

支持：结果流式返回、阻塞算子的外部排序与分区落盘、冷顶点属性列的压缩淘汰与按需回载、非活跃索引代冷块淘汰、基于检查点的重启恢复。

不支持：主键索引超出内存后继续写入、活跃索引代整体换出、边拓扑按需分页、版本链跨重启保留。这些场景在导入或写入准入阶段按容量错误返回，并给出明确诊断。

## 后续方向

- 让计划期内存策略真正驱动算子切换，并在代价模型中计入 spill 成本。
- 结合受限内存回归覆盖并发查询、数据偏斜与多算子同时落盘，持续核对峰值内存、落盘量、结果一致性与耗时。
- 如需支撑整图超内存，在现有模块内扩展磁盘分级主键索引、拓扑分页与版本链持久化；参考 Ladybug 的页帧生命周期与 Nebula 的磁盘主存思路，不新建平行存储引擎。

## 验收口径

配置默认值与解析测试、查询与存储单元测试、受限内存下的大结果流式查询与外部算子落盘回归共同构成验收。重点观察预算是否生效、spill 文件与配额是否正确回收、冷列回载后结果是否逐值一致，以及超限写入是否返回明确错误。
