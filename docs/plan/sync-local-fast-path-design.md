# 本地同步快道设计方案

本文是此前向量后端一致性整改中列入远期的第一项的展开。
只描述设计，不贴完整代码。实现时只改原模块，不新增替代模块。

## 背景

同步投递链是为统一本地与远端而建的：事务提交时暂存意图，
物化到本地持久化发件箱，再由认领应用确认循环投递。
纯单机部署下全文与向量引擎都在进程内且各自带持久化，
提交线程仍要走一遍发件箱物化、认领、租约、确认才能让索引可见。
目前提交线程靠每次提交后同步跑一次投递循环来保证读写可见，
外加一个数秒间隔的后台轮询兜底。
这对本地换来了崩溃一致性，代价是写路径多了若干轮数据库往返，
延迟与竞争都高于直接写入。

## 目标与非目标

目标：纯本地部署下提交返回时索引已可见，且崩溃语义不弱于现在。
非目标：不改变远端投递语义，不改变重建流程，
不放宽任何情况下的持久化保证。

## 现状约束（改动前必须承认的三件事）

- 发件箱的物化前沿钉住了检查点的回收边界。提交后若不推进前沿，
  预写日志将无法截断并持续膨胀，暂存意图也会泄漏。
  任何快道都必须同样推进前沿，不能只跳过不交代。
- 本地引擎各自已有崩溃恢复能力（向量按集合分组提交，
  全文有自身的提交语义），直接应用的单集合原子性不低于现状。
- 幂等键与排序键是两条路径共用的去重基础，
  快道与发件箱路径必须生成同一套键，
  快道失败回退到发件箱时重放必须被识别为重复而非双写。

## 设计

按部署形状选择提交模式。组装时根据已配置的目标判定
是否全部为本地可直接应用的目标。
全本地部署走快道，含任一远端目标的部署沿用现有发件箱链路，
判定结果在启动日志中明示。

快道下提交线程直接把分组好的变更交给各协调器应用，
不再逐事件写发件箱行。但提交仍需向发件箱写入轻量提交标记，
只推进物化前沿而不产生投递事件，
检查点与回收逻辑看到的前沿语义与现在一致。
标记写入失败视为提交失败的一部分，
避免前沿落后于存储而卡住日志截断。

失败回退只有一条：快道中任一应用失败，
整批意图转入发件箱走常规投递并按现有重试与死信策略处理。
提交本身是否失败取决于失败策略，
默认倾向提交成功加后台追赶，全文与向量保持现有失败开放语义。
直接写入与发件箱写入不允许同时生效于同一事件，
键相同保证回退重放去重。

数据定义变更不进快道，建索引、删索引、删空间与删标签
继续走发件箱保序，避免结构变更与数据写入在两条路径上交错。
重建的追赶重放不受影响，仍从发件箱认领。

## 验收

- 全本地部署下提交返回后检索立即可见，不依赖后台轮询。
- 崩溃重启后索引内容与提交确认一致，不多不少。
- 发件箱前沿与检查点回收行为与现状一致，无日志膨胀。
- 含远端目标的部署行为与现在完全一致。
- 快道应用失败可观测并自动转入常规投递，无静默丢失。

## 风险

- 双路径的可见性顺序：直接应用的本地写入与发件箱中的远端写入
  对同一事务的生效时刻不同，跨引擎读事务需要明确的可见性说明。
- 前沿标记与引擎应用之间的崩溃窗口：标记先行或后行各有取舍，
  需选定一种并让恢复路径能收敛，倾向标记与应用同批原子推进，
  做不到原子则倾向先应用后标记加恢复时按存储重放补投。
- 性能收益需实测确认，若发件箱本就是瓶颈之外，快道价值有限，
  应先度量再实现。
