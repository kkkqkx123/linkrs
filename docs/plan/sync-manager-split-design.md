# 同步管理器体量拆分设计方案

本文是此前向量后端一致性整改中列入远期的第三项的展开。
只描述设计，不贴完整代码。拆分只按职责，不按好坏，
名称描述模块所做的事。实现时只改原模块，不新增替代模块。

## 背景

同步管理器持有双协调器、发件箱、接收器、投递策略、
背压、统计、重建锁与后台任务句柄，是事实上的上帝对象。
持久化发件箱单个文件两千余行，近五十个方法，
横跨事件队列、重建代际、留存裁剪、快照恢复、
前沿诊断与降级区间六种职责。
向量索引管理器与后端抽象也都超过一千行。
管理器外观虽已按生命周期、写入入口、意图暂存、投递执行、
发件箱运维、只读视图拆分子模块，但共享同一结构体状态，
拆的是文件不是职责。

## 目标与非目标

目标：每个文件只装一种职责，修改影响面可预期，
对外公有接口保持不变，行为零变化。
非目标：不改变投递语义、重建语义与任何跨包接口，
不做性能优化，不合并或删除任何能力。

## 拆分边界

发件箱按职责拆为同模块下的子文件，类型不变，
各子文件只放同一职责的固有实现。
职责划分以现有方法簇的自然边界为准：
事件生命周期负责物化、认领、确认、重试、死信与重入队；
重建代际负责代际的创建、状态流转、激活、排空、丢弃与失败；
留存裁剪负责已应用事件裁剪、留存位点计算与归档；
快照恢复负责快照创建、校验、恢复与最新的快照查找；
前沿诊断负责各目标与索引的前沿、水位等待与诊断汇总；
降级区间负责降级区间的标记、查询与清理。
共享的连接与路径等基础放在模块根部，不归任何一簇。

管理器外观收薄为门面。现有七个子模块保留，
新增的职责只从管理器结构体向外搬，不向内加。
投递循环搬入独立的投递驱动，持有管理器的必要引用，
管理器只保留认领应用确认的装配入口。
重建准入锁与进度搬入重建编排，持有索引管理器与发件箱引用。
发件箱运维里的快照与死信管理方法搬入发件箱模块自身，
管理器只做转发。搬移后管理器结构体只保留
双协调器、发件箱、接收器、运行标志与统计，
背压与消费者配置随各自的使用方走。

向量侧不动结构，只明确归属。集合命名、分组与粒度
归索引管理器；执行语义归后端抽象；同步与进度归协调器。
已完成的分组批量下沉就是该方向的先例，
后续同类重复一经发现即按此归属搬移，不另立项。

## 执行顺序

先拆发件箱，风险最低且无公有变化。
再薄化管理器门面，每次只搬一个职责并保持方法签名转发。
向量侧随问题驱动，不主动重排。
每步单独可编译可回退，合并为一次评审分多步落地。

## 验收

- 对外公有接口零变化，下游包无需任何改动。
- 同一职责的方法不再散落多处，新增能力有唯一归属可循。
- 单文件行数回到可评审规模，发件箱各子文件职责单一。
- 现有全部测试行为不变。

## 风险

- 同模块多文件共享私有状态，拆分初期可能出现循环引用式的
  方法调用，必要时把共享状态下沉为小结构体而非互相借用。
- 门面转发层会增加一层跳转，属可接受的固定开销，
  不得借机做行为微调。
- 拆分过程与功能开发并行时冲突面大，宜选稳定窗口执行。
