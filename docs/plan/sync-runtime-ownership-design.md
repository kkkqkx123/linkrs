# 同步运行时归属设计方案

本文是此前向量后端一致性整改中列入远期的第二项的展开。
只描述设计，不贴完整代码。实现时只改原模块，不新增替代模块。

## 背景

同步包的对外接口多为同步函数，内部却要驱动异步操作：
网络客户端需要反应器与定时器，投递循环需要并发认领。
目前靠一座桥接函数衔接两者，根据调用环境分别处理
多线程运行时、单线程运行时与无运行时三种情形。
协调器各自持有运行时句柄，管理器的同步执行器又包着投递，
投递内还按需派生异步工作任务。
运行时到底由谁拥有、谁负责创建与关闭，
在存储回调线程、会话线程、后台任务线程上各是什么行为，
现在没有统一说法。

## 目标与非目标

目标：运行时有唯一所有者，调用方向单一，
热路径上不再有按次创建的临时运行时，恐慌路径清零。
非目标：不改变投递语义与并发度，
不对存储与服务层做大面积异步化改造。

## 现状问题

- 句柄来源不一。向量协调器要求调用方传入句柄，
  拿不到时直接恐慌；管理器执行器按环境自适应桥接；
  后台投递任务要求调用处正好身处运行时中才能派生。
  三处各说各话，嵌入式与服务两种组装方式行为不同。
- 同步包异步互相嵌套。同步投递入口在桥接内阻塞，
  桥接内又派生异步任务做并发认领，
  单线程环境还要另起线程再建临时运行时。
  层数多，死锁与饥饿风险随调用线程类型而变。
- 热路径开销。无运行时环境下每次同步调用都新建临时运行时，
  提交线程的高频调用长期 paying 建销成本。

## 设计

确立唯一所有者。服务与嵌入式两种组装入口在启动时
创建或选定运行时并把句柄注入同步管理器，
管理器再分发给各协调器与投递驱动。
任何同步包内部不再自行探测与创建运行时，
拿不到句柄属于组装错误，尽早显式报错而非运行时恐慌。

调用方向收敛为两条。异步优先：投递核心改为异步函数，
后台驱动任务直接等待；已有运行时的调用方走异步入口。
同步只保留在存储提交回调与外部接口边界上的薄垫片，
垫片只做一件事就是把异步核心桥接到当前线程，
且垫片内禁止再派生新的并发结构，
并发只存在于异步核心内部。

后台驱动由管理器生命周期拥有。启动时派生常驻任务，
停止时_join_回收，任务句柄随管理器走，
不再依赖每次调用处的环境。提交线程的同步投递
降级为轻量触发，真正的工作由常驻任务认领，
提交返回的可见性由本地快道或显式冲刷保证，
而不是靠提交线程亲自跑完一整轮认领。

构造器不再恐慌。需要句柄的构造器一律要求显式传入，
缺失时返回可传播的组装错误。存量的遇缺恐慌构造改为
显式参数版本，调用方在组装层一次给齐。

## 验收

- 同步包内无按环境探测运行时的分支，无按次新建临时运行时。
- 无缺句柄恐慌，组装缺件在启动期显式报错。
- 同步垫片内无任务派生，并发只存在于异步核心。
- 服务与嵌入式两条组装路径行为一致，
  后台任务随管理器启停而启停。
- 现有投递并发度与重试语义不变。

## 风险

- 存储提交回调是同步上下文，薄垫片的阻塞语义必须保留，
  收敛不当会把提交线程与异步驱动互相等待，
  需明确垫片只许出现在已知的边界函数。
- 单线程运行时的嵌入式场景下常驻任务的驱动方式要单独验证，
  不能想当然复用多线程假设。
- 改动触及所有组装入口，需服务与嵌入式两侧联调。
