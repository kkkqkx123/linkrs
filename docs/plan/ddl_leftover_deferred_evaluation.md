# DDL 遗留"明确不做"项立项评估（对照 NebulaGraph）

## 1. 背景与结论

`ddl_leftover_items.md` 已实施完成。该文档各处的"明确不做"是相对实施当时阶段的不做，不是永久禁止；其中部分项随特性被真实使用、单机定位展开与运维诉求浮现，重新具备了立项条件。本文以 NebulaGraph 官方源码为对照基线，逐项给出"立项 / 维持不做"的结论与理由。

对照基线说明：本地 `ref/nebula` 目录不存在（仓库、git 历史与文件系统均无），改用从官方仓库拉取的 v3.8.0 发布源码作基线，证据索引见第 8 节。若日后本地补齐 `ref/nebula`，应以本地版本复核结论（结论对版本敏感的只有第 3.1 节）。

结论摘要：

| 原"明确不做"项 | 结论 | 立项后归属 |
|---|---|---|
| TTL 后台定时清扫任务 | **立项**（配置 opt-in，中等优先级） | 本文档第 6 节展开 |
| PURGE 专用 gRPC / HTTP RPC | 专用 RPC 维持不做；**但服务端权限分类缺陷立项**（必修，小） | 本文档第 5 节展开 |
| `ALTER SPACE ... SET COMMENT` | 维持不做（与上游一致） | 文档声明边界即可 |
| tag/edge 注释修改（相邻发现，超原范围） | 维持不做，入长期备查 | 触发条件见 3.1 |
| 计数路径 TTL 精确化 | 维持不做（与上游一致） | 文档声明边界即可 |
| 不为 PURGE 新增 WAL 操作码 | 维持不做（与上游一致） | 无需动作 |
| WAL 判别式不重编号 | 维持不做 | 无需动作 |

另有两项相邻事实，不入本次立项范围但需知晓：`CHECKPOINT` 语句无任何发布文档契约；服务端权限映射对未归类语句默认按只读放行（第 5 节立项收口时一并处理）。

遗留的长期补充项（"后续统一项"与两条长期备查方向）由 `ddl_leftover_long_term_supplement.md` 承接，其中"后续统一项"已确认不应按长期项搁置，理由见该文档第 2 章。

## 2. 立项判据

- 契约悬空：发布文档承诺的能力用户不可达，或上游默认行为（装上即生效）在 linkrs 侧缺失，导致语义不一致。
- 防误用：能力可达但权限或分类错位，使只读角色可执行变更型操作。
- 保持单机轻量：立项不引入分布式设施、替代引擎或新版模块，改动作用于现有模块。

维持不做的判据：与上游行为一致、文档已声明边界、或纯内部格式决策且无外部消费方。

## 3. 逐项评估

### 3.1 `ALTER SPACE ... SET COMMENT` 与注释类能力

Nebula 事实（v3.8.0）：

- `CREATE SPACE` 创建时接受注释（解析层有 256 字符上限，超限直接报错），注释落 meta。
- 该版本 `ALTER SPACE` 在语法上仅剩 `ADD ZONE` 一个分支，没有注释子句——即空间注释与 linkrs 现状一致，**创建时可设、不可修改**。
- `ALTER TAG` / `ALTER EDGE` 支持 `COMMENT = '...'`（语法经变更项属性列表进入校验、落 meta），这是 linkrs 不具备的能力。

linkrs 现状：`CREATE SPACE` / `CREATE TAG` / `CREATE EDGE` 创建时可设注释；DDL 定义对齐阶段已删除全部注释修改路径，`SHOW CREATE` / `DESC` 场景只见创建期值。

结论：

- 空间注释修改：**维持不做**。与上游行为一致，且本文档不引入无文档契约的新特性。发布文档在注释相关处显式写明"仅创建时可设"即可。
- tag/edge 注释修改：**维持不做，入长期备查**。上游有、linkrs 无，属于元数据管理能力补全而非语义修复。触发条件：`SHOW CREATE` 需要完整回显注释，或用户侧出现成规模的注释维护诉求。

### 3.2 TTL 后台定时清扫任务

Nebula 事实（v3.8.0）：

- **没有任何用户可触发的 TTL 清理命令或 RPC**。过期数据的物理清除完全自动：storage 启动时为每个 space 注册 RocksDB 压实过滤器，压实过程中对顶点、边、索引键判定 TTL，过期即丢弃；层级有 `min_level_for_custom_filter` 开关控制是否参与，默认全部层级参与。用户在语句层面完全无感。
- 手动触发也是一次压实而非"清理数据"：`SUBMIT JOB COMPACT` 与 storage 内部 HTTP `admin` 端点的 `compact` / `flush`。
- 因此上游的 TTL 心智是"配置后自动回收，用户无需关心"。

linkrs 现状：

- 无压实引擎，`PURGE EXPIRED` 是唯一物理回收入口，发布文档明确承诺"无后台定时任务代为执行"。
- 但项目已有多个后台定时设施先例：Outbox 保留清理（按间隔执行）、索引 GC 后台任务句柄、自动统计收集，配置框架也已有按间隔开关的先例。
- TTL 特性本身迁自上游，用户预期与上游对齐；当前形态下，未集成 `PURGE EXPIRED` 到运维习惯的部署，存储会无限增长。

结论：**立项**。单机定位下"自动"的落点只能是显式 opt-in 的后台任务，而非开启压实引擎；opt-in 保持项目"不隐藏副作用"的原则。方案见第 6 节。

### 3.3 计数路径（`count_vertices_by_tag` / `count_edges_by_type`）TTL 精确化

Nebula 事实（v3.8.0）：

- 统计任务按前缀原始迭代计数，不解码属性、不判定 TTL；统计值只有在压实物理删除过期行之后才收敛。
- 查询侧同样没有 count 聚合函数可绕过该口径。

linkrs 现状：两个计数入口分别定位为洞统计近似值与可见性行计数，供优化器统计收集与迁移使用；发布文档已声明统计数值可能包含过期行。

结论：**维持不做**。与上游行为一致——两类计数都不物化属性，精确化的代价是放弃各自的定位；过期行被物理删除后计数自然收敛。文档声明保留，作为优化器专项的后续事项，不作为语义修复项。

### 3.4 PURGE 的 gRPC / HTTP RPC

Nebula 事实（v3.8.0）：

- 维护类操作有两条通道：SQL 侧的 `SUBMIT JOB COMPACT` / `FLUSH`（走与普通语句同一条查询通道，权限按写级别校验）与 storage 内部 HTTP 管理端点（仅 `compact` / `flush`，属运维内网设施）。
- 没有"直接删除 TTL 数据"的 RPC——因为清理由压实自动完成，手动 RPC 只是触发压实。

linkrs 现状：

- 专用 RPC 确实没有，但通用查询入口（gRPC `ExecuteQuery`、HTTP 一元与流式、CLI、嵌入式）已能承载 `PURGE EXPIRED`，与上游"维护复用 SQL 通道"同构。专用 RPC 维持不做是正确的。
- **发现缺陷**：服务端权限映射按 SQL 文本前缀分类，未命中任何已知前缀的语句落入默认只读分支。`PURGE EXPIRED` 因此被按只读放行：只读角色即可执行物理删除。流式入口只拦截配置语句，同样经过该权限门。上游同类操作按写级别校验。
- `CHECKPOINT` 语句同样落入默认只读分支，且它无发布文档契约，问题同源。

结论：**专用 RPC 维持不做；权限分类缺陷立项**（必修，小）。方案见第 5 节。

### 3.5 不为 PURGE 新增 WAL 操作码

Nebula 事实：删除即普通键值删除，写路径无独立操作码；物理清除点在其压实阶段而非写路径。

linkrs 现状：purge 删除复用既有的删顶点 / 删边记录，天然过 WAL、可被崩溃恢复。

结论：**维持不做**。两条路径形态一致，新增操作码只会带来恢复链路改动而无收益。

### 3.6 不重新编号 WAL 操作码判别式

linkrs 现状：空出的判别式留空不重编号，配合文件头版本提升实现"旧文件显式拒绝启动"。

Nebula 无对应概念（其 WAL 为 raft 日志，不做 schema redo 流的版本对齐）。

结论：**维持不做**。纯内部格式决策，现行实现已满足"显式失败优于静默忽略"。

## 5. 立项一：维护语句权限分类修正

目标态：变更型维护语句在任何入口（gRPC 一元、HTTP 一元、流式）都以写/维护级权限放行；发布文档与实现逐条一致。

范围与要点：

- 识别面：服务端权限守卫的语句分类表。当前按 SQL 文本前缀归类，未命中分支默认只读。修正为对维护类语句显式归类：`PURGE EXPIRED` 归到 schema/维护级权限；`CHECKPOINT` 同步评估归类（其语义为触发快照，属写级别）。
- 归类依据的选型：前缀枚举补齐改动最小，但每新增一个维护语句都要再补一处；基于解析后语句类别（AST 类别）建立"类别 → 权限"映射可一次覆盖后续语句，但需要处理解析失败路径的回退。建议先以最小改动补齐维护语句归类，类别映射作为后续统一项记录。
- 同步修正文档表述：DDL 文档 PURGE 章节从"无对应的 gRPC / HTTP 接口"改为"无专用 RPC，经通用查询接口执行，需具备该空间维护权限"，并补权限小节；为 `CHECKPOINT` 补文档契约（它当前无任何发布文档）。
- 流式与导出：流式入口沿用同一权限门，仅需确认归类一致；导出为读路径，不受影响。（实施备注：流式入口对普通语句原先并未实际调用权限门，仅命令类语句经一元路径间接过门；本次补齐流式入口对普通语句的权限门，使"一元与流式行为一致"成立。）
- 测试：只读角色执行 `PURGE EXPIRED` 被拒绝且有可读错误；无维护权限的普通写角色执行被拒绝；具备维护权限的角色执行成功；拒绝动作在一元与流式入口行为一致。
- 验收：上述测试全绿；发布文档 PURGE / CHECKPOINT 小节与实现逐条对应；`cargo check --workspace` 零告警。
- 后续统一项（本文档记录，暂不立项）：服务端权限分类仍以 SQL 文本前缀为输入，前缀枚举每新增一个维护语句都需补一处；后续可改为基于解析后语句类别（AST 类别）建立"类别 → 权限"映射，一次覆盖后续语句，需同步处理解析失败路径的回退与既有 DCL 专用分支的合并（病根分析见 `docs/issue/dcl-auth-bypass-prefix-matching.md` 与 `docs/issue/dcl-permission-matrix-drift.md`）。

## 6. 立项二：TTL 后台自动清理（配置 opt-in）

目标态：TTL 语义补齐为"配置即回收"的上游心智，回收默认关闭、显式开启；开启后按固定间隔自动对配置了 TTL 的 schema 执行既有有界批量清除；`PURGE EXPIRED` 立即可用的能力不变。

设计要点：

- 文档先行：改写发布文档 TTL 工作原理中"过期行的物理删除需要显式执行 `PURGE EXPIRED`，无后台定时任务代为执行"的契约，改为"默认显式执行；开启后台清理后按配置间隔自动执行"，并同步 PURGE 章节的"无后台任务"表述。
- 配置：新增清理总开关与执行间隔两个配置项（默认关闭），落在既有配置节与配置参考文档中；间隔为 0 或开关关闭均表示不启动。
- 存储层：后台清理任务与现有索引 GC 后台任务同构，复用后台任务句柄与线程池；每轮按空间枚举，逐空间调用既有的统一 purge 入口（不带目标 schema，即清理该空间全部配置了 TTL 的标签与边类型）；单轮串行、批删除逻辑与内存有界性沿用既有实现，不新写删除路径。
- 服务层：启动时按配置启停；句柄形态与 `StorageGcOps` 一致，便于后续暴露观测。
- 可观测：每轮汇报各 schema 清除行数，写入日志与既有指标；与 `PURGE EXPIRED` 结果集同口径。
- 并发与幂等：后台任务单实例，显式语句与后台串行化由单实例天然保证；删除走正常 MVCC 写路径，重复执行幂等（已清除则各 schema 汇报 0 行）。
- 风险与缓解：后台清理与显式清理争用 IO——按配置限批、低优先级线程；开关默认关闭，避免现有部署行为静默改变；配置开启后文档契约同步发布，不允许"开启后有文档未描述的行为"。
- 验收：开关关闭时无后台任务且无任何自动删除；开启后到期数据在间隔内被自动物理回收，行数汇报正确；`PURGE EXPIRED` 立即可用且与后台共用同一实现；默认值下既有测试不回退；文档契约与实现逐条对应。
