# 同步包职责分析

本文描述 `linkrs-sync` 的现有实现结构，并评价职责划分是否合理。
配套整改方案见 `sync-responsibility-remediation.md`。
文档使用自然语言，不贴完整代码。

## 现状总览

`linkrs-sync` 的自我定位是派生二级索引的协调层，不拥有检索引擎。
全文检索的实现在 `linkrs-fulltext`，向量检索的实现在 `simvec` 与
`vector-client`，本包只负责协调：事务暂存、持久化投递、重试与重建编排。

主链路为写入经存储层回调进入同步管理器，生成跨目标意图，
在提交时物化到本地持久化发件箱，再由后台投递循环按目标逐个认领、
应用、确认，失败按策略重试或进入死信。重建走快照扫描加态势追赶，
在发布保护下切换索引。

## 模块结构

- 同步管理器外观：统一的事务边界与投递入口，内部按生命周期、
  写入入口、意图暂存、投递执行、发件箱运维、只读视图拆分子模块，
  但共享同一个结构体状态。
- 全文协调器：持有全文索引管理器与按索引粒度的批处理器，
  另有事务缓冲，兼具直接写入、缓冲提交与查询代理能力。
- 向量协调器与索引管理器与后端抽象：协调器叠加同步能力，
  管理器负责索引元数据与生命周期，后端抽象屏蔽本地与远端实现差异，
  另有投递调优策略与远端配置转换。
- 持久化发件箱：基于本地数据库的物化、认领、租约、确认、
  重试、死信、快照与诊断能力，是投递的唯一可信状态。
- 接收器：按目标记录幂等收据与水位，用于重放去重与迟到判定。
- 重建驱动：全文与向量各自实现扫描、回填、多轮追赶与发布，
  共享 admission、空源保护与进度口径。
- 批处理、重试、熔断、运行时桥接、指标装饰、类型转换、
  检查点清单与恢复，属于横切与运维支撑。

## 合理的部分

- 协调与引擎分离的方向正确，引擎差异收敛在后端抽象内，
  投递主链路不因本地或远端而分叉。
- 以持久化发件箱为中心的投递语义完整，
  预过滤避免纯图变更的写放大，实体级排序键保证同实体串行，
  幂等收据保证重放安全。
- 重建的正确性手段齐备：发布保护、暂存隔离、追赶收敛、
  空源保护与重建互斥，结果可解释。
- 失败策略分层清晰：认证失败暂停投递，可重试退避，
  不可重试进入死信，禁用引擎只计数不丢状态。

## 存在的问题

- 包职责过载。暂存、投递、重建之外，还装入索引生命周期、
  查询代理、向量化与重排、类型转换、检查点与恢复。
  查询与推理能力本应属于查询层与服务组装层，
  检查点恢复更接近存储与迁移职责。
- 全文与向量两套写入范式并存。全文协调器保留直接写入与缓冲提交
  的旧路径，向量走发件箱认领的新路径。
  两套一致性语义与读写可见性并存，容易误用。
- 管理器与发件箱过大。同步管理器持有双协调器、发件箱、
  接收器、策略、背压、统计与重建锁，是事实上的上帝对象。
  发件箱把持久化、租约、快照、诊断、降级与等待水位装在一起，
  修改影响面大。
- 向量三层边界模糊。集合命名、分组、粒度、暂存与发布逻辑
  分散在协调器、管理器、后端与重建四处。
  协调器同时承担同步、查询、向量化、重排与进度，
  写入路径同步阻塞调用向量化服务，延迟与放大风险高。
- 错误分类依赖字符串匹配。投递把类型化错误先转成字符串，
  再用子串判断禁用、认证与可重试性，脆弱且难以覆盖。
  投递并发来源不唯一，策略与消费者配置各说各话，
  同一并发值在两处重复推导。
- 存在可选的循环依赖。全文包的测试与开发依赖同步包，
  同步包又可选依赖全文包，特性组合下形成双向引用，
  与自称的单向依赖图不符。
