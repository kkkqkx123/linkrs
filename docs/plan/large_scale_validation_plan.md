# 大规模与长期运行验证计划

**日期**: 2026-10-04
**性质**: 独立验证任务，对应 `docs/plan/performance_optimization_remaining_plan.md` 第 2.6 项
**依赖**: 无代码改动前置；需要专门的运行环境与较长时间窗口

---

## 一、目标

当前性能验证最大规模约 1M（`csr_perf_bench` 核心仅 4096 顶点），且均为短时运行。本任务补齐以下缺口：

1. 10M+ 顶点/边规模下的规模曲线（吞吐、延迟、内存）。
2. 长期写入下的老化行为：压缩/编码增长、索引膨胀、checkpoint 开销随数据量增长。
3. 大规模下的崩溃恢复与重启时间。
4. 大规模下的检索（全文/向量）与并发行为。

## 二、环境前置

1. release profile 构建；关闭调试断言与计数分配器。
2. 内存需足以容纳 10M 级数据集及其索引；建议独占机器，避免后台任务干扰。
3. 注意 SIMD 目标：仓库 `.cargo/config.toml` 默认 `x86-64-v3`，运行时需 AVX2 硬件；旧 CPU 需以 baseline 目标重建，否则数据不可比。
4. 存储介质需固定并记录（NVMe/SSD/HDD 会显著影响 WAL 与 checkpoint 结论）。
5. 关闭或固定后台 checkpoint 参数，使各轮可比；单独设置一组观察 checkpoint 老化的参数。

## 三、数据集与工作负载

### 3.1 数据集
- 顶点/边规模梯度：1M、5M、10M（必要时 20M）。
- 标签与属性：至少一个带多属性的顶点标签、一个多属性边类型，属性包含定长数值与变长字符串，以覆盖列编码与 FSST 路径。
- 可选：高基数与低基数属性各一列，覆盖 HLL/编码选择差异。

### 3.2 工作负载
1. 批量导入：顶点批量、边批量，记录总吞吐与阶段耗时。
2. 点读：随机点查（顶点/边），记录 p50/p95/p99。
3. 邻接遍历：1/2/3+ 跳、变长路径、最短路、高度数 hub 最坏情形。
4. 聚合/OLAP：count、group-by、percentile、大范围扫描。
5. 范围扫描与谓词下推：利用列统计与 zone map 的选择性场景。
6. 崩溃恢复：checkpoint 后重启、WAL 尾部回放（含边）、重启到可用状态的时间。
7. 并发：多客户端读写混合、写写冲突、只读快照扩展性。
8. 检索：全文 BM25 延迟/召回；向量 HNSW 查询 recall/latency vs ef/M。

## 四、长期运行老化观察

1. 持续写入下的内存增长曲线（属性列、版本链、冲突索引、GC 水位）。
2. 压缩/编码：列编码选择随时间的变化、FSST 符号表增长、可回收字节。
3. 索引膨胀：二级索引与冲突空间索引的条目数随提交增长（结合 prune 批量化的内存上界观察）。
4. checkpoint：单次耗时、写放大、WAL 文件轮转与截断频率随数据量增长。
5. 观察是否存在拐点（例如 prune、GC、checkpoint 的频率或成本随规模非线性上升）。

## 五、指标与产物

- 统一采集：吞吐（ops/s、MB/s）、延迟分位、内存 RSS/分配量、磁盘占用、WAL/checkpoint 次数与耗时、恢复时间。
- 产物：每个规模/场景一份结果报告，含环境说明、数据集描述、原始数值与曲线；集中归档到 `benches/results/` 之外的专用目录（避免污染常规基准）。
- 建立可重复运行的入口脚本与固定随机种子，保证轮次可比。

## 六、执行方法

1. 先跑小规模（1M）确认流程与基线，再放大。
2. 每个场景至少重复多次，报告分位而非单点。
3. 前后对照使用同一环境、同一数据集、同一参数；任何环境差异需显式记录。
4. 将结果与既有小规模基准对照，标注规模放大后的偏差。

## 七、验收

1. 产出 1M/5M/10M 的规模曲线与长期运行报告。
2. 关键指标（写放大、checkpoint 耗时、内存增长、恢复时间）随规模单调且无异常拐点。
3. 崩溃恢复在大规模下仍能正确回放（含边 WAL 尾部）。
4. 检索在 10M 规模下的 recall/latency 达到可接受水平，并记录与 ef/M 的关系。

## 八、风险与约束

1. 需要独立环境与长时间窗口，不宜与日常开发编译/测试争用资源。
2. 大规模运行可能触发 OOM 或超时，需分阶段、可中断、可续跑。
3. 结论强依赖硬件与存储介质，报告中必须完整披露环境，避免跨环境误比。
4. 本任务不含代码修改；若发现性能缺陷，另行建 issue 与优化任务。
