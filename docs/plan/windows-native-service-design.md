# Windows 原生服务与跨平台服务化设计

本文描述服务端在三个构建目标上的服务化终态，只描述设计，不贴完整代码。实现时只改原模块，不新增替代模块；平台集成按职责拆分，不造替代性新模块。

## 背景与决策

构建矩阵覆盖三个目标，服务化成熟度却不一致：Linux 已随就绪通知整改切为原生 `Type=notify`；Windows 依赖外部 NSSM 包装；macOS 尚无部署资源。NSSM 已长期不维护，继续保留意味着把停机正确性寄托在一个无人维护的外部二进制上。现决定：Windows 改用 `windows-service` 实现进程内原生服务，不再保留 NSSM；macOS 不需要进程内代码，仅补打包资源。

## 目标与非目标

目标：三平台服务语义对齐为同一句话，即监听绑定成功后报告就绪、退出前报告停止；Windows 单二进制同时支持服务模式与交互模式；NSSM 相关脚本与文档整体退役。

非目标：安装启停管理不引入统一库，现有部署脚本体系维持；看门狗、心跳、配置热重载不在本次范围内；数据与配置格式无任何变化，不存在兼容问题。

## 设计

统一层仍是自研的调用约定而非外部库，因为三家服务管理器的进程内语义不可统一：`systemd` 要主动数据报，Windows 要接入状态机并响应停止控制，`launchd` 什么都不要。`systemd.rs` 保持不动，新增与其职责对等的 Windows 平台模块并以平台门控隔离，对外暴露同样的就绪与停止语义，现有调用点复用绑定后与退出前的同一组钩子。

Windows 服务集成只依赖 `windows-service` 一个构件，置于平台专属依赖段，不触碰现有任何版本。是否采用此前已用文档查证的标准形态：服务入口复用现有启动流程，被服务管理器拉起时走服务入口，交互运行时走现有控制台路径并在分发失败时回落，保证现有前台运行与排障方式零变化。就绪在监听绑定成功后向管理器上报运行中，语义与 `READY=1` 对齐；停止控制不自建退出路径，而是触发优雅停机。

为此需要唯一一处结构改动，即引入可编程的停机触发器。当前停机完全由系统信号驱动，服务管理器的停止控制无处接入；改动后信号与停止控制 firing 同一个触发器，下游的超时强制退出与资源关闭逻辑复用不变。这是本次唯一的跨平台行为变更点，Linux 与 macOS 的信号路径语义保持原样。

NSSM 退役随原生服务上线同步完成：删除 Windows 下的安装卸载与状态脚本，部署文档中的 Windows 章节改写为原生服务注册与管理方式；Windows 配置模板保留，配置内容不受影响；Linux 打包与 `systemd` 单元不受影响。已用 NSSM 部署的实例按先卸载旧包装服务、再注册原生服务的路径迁移，数据目录不动。

macOS 侧零代码改动：新增 `launchd` 服务描述模板与文档段落，复用已有的 `SIGTERM` 优雅停机路径；服务描述中明确日志位置与开机自启语义即可。

## 验收

Windows 服务管理器中服务状态与进程实际监听状态一致；从管理器停止服务走完优雅停机并清理现场；交互运行方式与此前一致；NSSM 相关文件与文档引用清零；macOS 描述文件可直接装载并随系统启停；三平台正常启停日志均可观测。

## 风险与前提

首要前提是具备可验证的 Windows 构建与冒烟环境，否则服务入口与双模式回落逻辑无法验收，该环境需先于实现就绪。服务分发失败回落的分支需覆盖测试，避免交互运行被误判。服务描述与注册文档以实现时的实际参数为准，文档与脚本保持同一次改动内对齐，避免重蹈单元与实现脱节的问题。
