# 同步包职责整改方案

配套分析见 `sync-responsibility-analysis.md`。
本文是允许出现任务编号的唯一位置，代码注释中不得引用这些编号。
方案描述使用自然语言，不贴完整代码。

## 本次范围

本次只落地同步包内部、无跨包公有接口破坏的三处整改，
一次完成。跨包的职责搬移与大拆分记入远期方向，
需要存储、查询与服务层协同，不在本次执行。

## 节点一：投递失败类型化

- 现状：投递把应用错误先转成字符串，再用子串判断禁用、
  认证与可重试性，类型信息在中途丢失。
- 改法：引入投递内部的失败载体，保留原始类型化错误的分类结果
  与可读信息。向量错误沿用其自带的类型化分类，远端认证失败
  在转换边界即归为专用的认证变体，禁用态用显式标志表达，
  不再用字符串推断。
  全文错误按是否永久合法区分可重试与死信，
  解码失败与无目标投递视为永久失败。
  投递的重试、死信与暂停逻辑只看类型化分类，
  持久化到发件箱的仍然是原可读信息，保持运维可见性不变。
- 验收：投递路径不再出现字符串子串分类调用，
  禁用、认证、可重试、永久失败四条分支均由类型驱动。

## 节点二：投递并发单一来源

- 现状：后端策略与消费者配置各存一份并发值，
  投递循环内再按策略名重新推导一次，
  同一数值有两处推导，容易分叉。
- 改法：删除管理器中冗余的策略存根，
  策略注入时一次性换算为消费者配置，
  投递循环只信任消费者配置的并发值。
  策略结构体本身保留，仍是调优的唯一入口，
  只是不再在投递时二次解释。
- 验收：投递循环内无策略名分支，
  策略注入后消费者配置即最终值。

## 节点三：删除死亡的字符串分类器

- 现状：向量错误上同时存在类型化分类与字符串分类两套入口，
  字符串分类是为投递擦除类型后的补救。
- 改法：在节点一落地后删除字符串分类入口，
  只保留基于类型的分类。调用方一律先分类后转字符串，
  不允许先转字符串再反推类型。
- 验收：字符串分类入口无残留，包内无调用方。

## 执行顺序

节点一先行，节点二与节点三随同落地。
三者同属投递路径，合并为一次代码修改与一次编译验证。

## 远期方向（本次不执行）

- 统一全文写入范式，只保留发件箱认领路径，
  删除直接写入与事务缓冲旧路径，需先迁移全文包的测试用法。
- 将查询代理、向量化与重排移出同步包，
  同步只接收已向量化的载荷，查询入口收敛到查询层。
- 按职责继续拆分发件箱与后端抽象，
  解除全文包与同步包的双向可选依赖，
  全局推行类型化错误，替换字符串匹配。
