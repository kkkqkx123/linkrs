# Linkrs 剩余对齐问题分阶段修改方案

**日期**：2026-11-18  
**问题来源**：`docs/issue/linkrs-remaining-parity-issues.md` 是剩余问题的单一真相源；本文件只描述修改顺序、落点、护栏与验收，不重新定义问题。

## 总则

- 先处理被实测放大的算子缺口，再处理口径、并行放行和深水存储项。
- 所有改动收敛到原模块，不新增替代模块，不做向后兼容包袱。
- 每个阶段独立可回滚：回退该阶段修改的原模块文件即可，不需要数据迁移。
- 正确性优先于速度：快路径只在可证明等价的窄前置下触发，其余形状保持原路径。
- 每个新规则或快路径必须先补反例与空输入用例，再动执行代码。
- 基准结论必须来自安静窗口的重复测量；测量期间有他人构建任务的结果只能作量级证据。

## 已冻结的基线

devs 2026-11-18 两轮 LSQB sf0.1 实测显示：原有九条纯计数仍为 0.15–0.60 ms，编译中位数 0.01–0.03 ms；新增算子中 `group_by_count` 为 1.31–1.50 秒、`distinct_limit` 修正排序后约 1.11 秒、`join_two_hop` 为 35–49 ms、`variable_path_count` 为 1.10–1.35 秒。原始日志与三方 JSON 在 `perf-data/parity/results/2026-11-18/`，结论与表格在问题文档。

## 阶段零：固化测量与用例底座

**目标**：把已经跑通的 smoke 用例变成可重复、可归因的基准，而不是继续靠一次性观察指路。

**修改位置**：`src/bin/linkrs_parity_bench.rs`、`benches/parity/`、`graphdb-ben` 侧对比脚本。

**做法**：

- 新增 compare 脚本，读取三方 JSON，按用例名合并状态、行数、首值、执行中位数、编译中位数、RSS 与库体积；偏差达到 20% 的条目高亮，跳过项单列。
- 为当前算子用例生成同规模 expected。整数用例逐值比对；PageRank 等浮点用例使用相对误差 1e-3；TopN 必须先稳定排序再比对，避免无界 LIMIT 的首值漂移。
- 给每个新增用例补充计划标记采集，至少记录是否走元数据计数、count-only、typed dedup、分组快路径、TopN、分区与回退原因。
- 在本阶段保持引擎行为不变，只补观测与报告。

**护栏**：expected 必须来自本规模参考实现，禁止把 sf100 数值套到 sf0.1/sf1；方言不兼容用例继续留在 `benches/parity/skip.txt`。

**验证**：同一提交在安静窗口跑两轮，三方用例状态、行数与计划标记稳定，compare 脚本输出可复现。

**不做**：不在本阶段改算子实现，不引入近似比较掩盖语义差异。

## 阶段一：分组计数与去重热点

**目标**：先消除实测中两个秒级用例，预期把 `group_by_count` 与 `distinct_limit` 从秒级压到毫秒级或几十毫秒级。

**修改位置**：聚合执行算子、去重执行算子、相关规划与优化规则、DQL 聚合测试。

**做法**：

- 分组计数：在聚合算子内为窄形状增加列式分组计数路径。前置限定为单一分组列、单个 `count(*)` 或 `count(变量)`、无逐聚合过滤、无多列分组、无去重修饰。执行时直接从 typed column 读取分组键，在定长键的局部哈希表中累加，避免逐行构造 `Vec<Value>`、`ValueRowContext` 和重复 `contains_key` 探测。满足前置时整批累加，否则保持现有逐行路径。
- 空值与边界：先锁定分组键为 NULL、空输入、单组、全同键、高基数列五类语义。可空分组键若无法在不解码的前提下证明等价，明确走慢路径，不为了快路径放宽语义。
- 去重加排序分页：在 Dedup 算子中为单列整型键增加 typed 去重路径，避免每行 `Vec<Value>` 克隆与全行哈希；保留原始行语义，只把“是否首次出现”的判定换成定长键集合。TopN 仍位于去重之后，不把 LIMIT 提前到未排序输入之前。
- 分组聚合与去重分别补每算子行数、耗时和内存计数，阶段结束时用 Profile 数据确认瓶颈是否从执行算子移走。

**护栏**：

- 快路径与慢路径在五类固件上整数结果完全一致。
- 任何聚合过滤、可空分组键未证明等价、多键分组、非计数函数存在时，立即回退原路径。
- 去重快路径不得改变行顺序、重复度语义或 NULL 可见性。

**验证**：devs 上以 `group_by_count`、`distinct_limit` 和九条纯计数为固定门，跑安静窗口两轮；同时跑 DQL 聚合与 metadata count 全量单测。数值必须一致，耗时下降至少一个数量级才算闭环。

**回滚**：还原聚合算子、Dedup 算子和对应测试的修改文件。

**不做**：不在本阶段改存储层，不做多谓词复杂下推，不对去重做有损近似。

## 阶段二：两跳连接与变长路径

**目标**：把 `join_two_hop` 和 `variable_path_count` 的秒级/几十毫秒成本降到与 Ladybug 同数量级，同时锁定路径计数语义。

**修改位置**：Expand 计数尾、路径规划器、递归片段算子、遍历相关测试。

**做法**：

- 两跳连接：在现有 count-only 注解基础上扩展窄形状，覆盖“单标签锚点 + 固定两跳 + 全部边类型明确 + 无属性谓词 + 只数末端边”的形状。执行时用邻接批次数值直接累加第二跳度数，不生成中间路径行；任一条件不满足则回到通用展开。
- 变长路径：先锁定 `count(k)` 在 `*1..2` 下究竟计数路径还是计数边，并用小固件钉死自环、重复边、悬空端点和方向变体。随后在递归片段算子中为定长范围、无属性过滤、无路径实体输出的纯计数形状增加基于前沿计数的展开，不物化完整路径列表。
- 路径与边列表输出保持原路径；新快路径只服务于纯计数，不为提升数字牺牲可解释性。
- 复用阶段零的计划标记，确认快路径确实生效，而不是靠缓存偶然变快。

**护栏**：

- 两跳计数必须与通用路径逐例相等，包括空端点、悬空端点和自环。
- 变长路径的 Trail、WALK、默认唯一性语义不得混用；无法证明等价的形状直接慢路径。
- 多源最短路继续保持显式语义，不静默截断。

**验证**：devs 上固定 `join_two_hop`、`variable_path_count` 与 `find_path` 端到端测试；数值一致后记录两轮中位数。

**回滚**：还原 Expand 计数尾、路径规划器与递归片段算子的修改文件。

**不做**：不在本阶段做图算法优化，不实现近似计数。

## 阶段三：谓词与过滤聚合向量化

**目标**：补齐带谓词计数、分组计数和空输入语义，并把已经正确的慢路径收敛到可证明等价的快路径。

**修改位置**：扫描谓词下推、聚合执行算子、分组规划、DQL 聚合与元数据计数测试。

**做法**：

- 扩展可下推形状：等值与范围谓词下推到扫描谓词后，聚合侧复用无谓词向量化路径；只做完整下推，不做部分下推。
- 带逐聚合 `FILTER` 的计数在窄前置下尝试批内掩码累加；任一聚合带过滤时保持关闭全局行计数快捷路径与批量表达式路径的现有语义，直到掩码路径通过全量反例测试。
- 分组可空参数用单测锁定 NULL 分组键与空输入行为；空输入全局计数继续输出单行零，分组空输入继续输出空集合。
- 去重计数维持慢路径，本阶段只补基准记录，不做向量化。

**护栏**：可下推与不可下推两种形态数值必须一致；下推失败保持原计划，不引入“下推一半、残差再过滤”的复杂路径。

**验证**：新增过滤计数快慢路径对照基准；devs 上记录 `filter_id_range`、`filter_or`、`aggregate_filtered_count` 的计划标记与数值。方言专用用例仍进跳过清单，不强制三方对比。

**回滚**：收紧下推形状或还原聚合算子修改。

**不做**：不做多谓词组合下推，不向量化去重计数。

## 阶段四：可观测与资源口径

**目标**：让 EXPLAIN、PROFILE 与三方报告使用同一套阶段与资源字段，消除“元数据显示了但解释输出看不到”的口径分叉。

**修改位置**：管线执行入口、解释格式化、`PlanDescription`、parity runner、compare 脚本。

**做法**：

- EXPLAIN 文本增加编译阶段与执行阶段的独立展示，字段直接来自现有请求级画像，不另造一套计时。
- `PlanDescription` 增加顶层峰值内存与库体积；每算子峰值内存继续由 Profile 提供，类型化布局只做计数，不改变分配行为。
- parity JSON 增加数据库体积、RSS 峰值、缓冲池上限与溢出计数；compare 脚本把这些字段列成独立表，不与查询耗时混在一起。
- 阶段零的计划标记在解释输出中可读，包括 count-only、typed dedup、分组快路径、分区回退原因。

**护栏**：显示分支不得参与代价决策；直接估算调用保持不变；新增字段默认值为零或空字符串，不改变计划哈希与查询数值。

**验证**：同一查询多次运行，编译耗时稳定、执行耗时随规模变化；EXPLAIN 字段与 runner JSON 一致。

**回滚**：还原计时打点与格式化修改。

**不做**：不调整代价模型本身，不新增内存超限降级策略。

## 阶段五：分区灰度放行

**目标**：在算子快路径收敛之后再评估并行，避免用分区掩盖单线程算子慢的问题。

**修改位置**：`ParallelConfig`、配置文档、分区规划核心、链装配、并行扩展基准。

**做法**：

- 保持总开关默认关闭，灰度表只放行纯计数链；全局聚合待阶段一的分组快路径证明正确性与溢出可控后再单独放行。
- 放行仍要求存储自证数据域与布局版本齐备，任一缺失回退；经济门、实际分区数、回退原因写入计划标记。
- 配置文档与服务透出补齐两个放行开关；普通扫描与连接继续关闭。
- 在安静窗口按形状 × 放行开关 × worker 数跑矩阵，用不受分区影响的边扫描作对照组；对照组同样漂移时判环境无效并重跑。

**护栏**：未放行形状计划不变；放行前后整数结果一致；8 worker 不优于 4 worker 时按既有封顶结论保留，不自作主张放宽。

**验证**：`parallel_partition_execution.rs` 与 partitioning 单测全绿；矩阵基准记录实际分区数与回退原因。

**回滚**：关闭对应放行条目即可。

**不做**：不做跨分片事务与动态重分区。

## 阶段六：图算法与方言适配

**目标**：把当前 Linkrs 专用路径语法与真正的算法图基准分开处理，避免方言差被误判为性能差。

**修改位置**：路径规划器、递归片段算子、图算法函数、parity 查询适配、skip 清单。

**做法**：

- 先把 `aggregate_filtered_count` 与 `shortest_path` 维持为 Linkrs 专用微基准；在 skip 清单保留原因和解禁条件。若三方可接受统一 GQL 形态，再新增适配后的同名用例，不覆盖原用例。
- 固定长度递归、Trail 与最短路先以慢路径跑通并锁定数值，再考虑不动点中间结果物化与受控并发；并发度受分区配置约束。
- 纳入 PageRank、WCC、加权最短路；k-core、SCC、Louvain 继续 skip。graph500 数据目录当前只有 schema 与 copy 文件，生成数据前不纳入报告。
- 数值门槛：整数精确，PageRank 等浮点相对误差 1e-3；迭代次数与阻尼因子写入环境块。

**护栏**：多源最短路保持显式语义；不做近似算法与截断采样；对手不支持的方言不进入三方表。

**验证**：soc-livejournal 或同等图数据上三方一致后记录趋势；不足时保留慢路径数字，不上报伪对齐。

**回滚**：还原算子优化与查询适配文件。

**不做**：不做 Louvain、SCC、k-core 的近似实现。

---

## 阶段七：存储与事务深水项

**目标**：在查询侧收敛后处理持久化下限与顶点装入的剩余空间，避免与算子改动互相干扰。

**修改位置**：持久化协调器、WAL 管理器、快照管理器、存储批量操作、顶点表写入。

**做法**：

- 保留 WAL 组提交、批量会话、专用检查点线程池与显式容量错误；io_uring 受内核限制，不在当前环境启用。
- 冷检查点第二阶段与批量回放保持冻结，先完成收尾段同口径分段计时，再决定是否解冻批量应用。
- 分片并行顶点装入前完成四项审计：身份分配器锁粒度、预留释放并发安全、跨分片补偿顺序、提交映射合并；审计未过不实施。
- 同步点与 WAL 格式保持不动，不通过牺牲持久性换导入速度。

**护栏**：崩溃恢复与容量超限用例全绿；批量中断后重放结果与逐语句导入一致。

**验证**：全量导入两轮以上，与 11.2–11.3 秒基线对比；WAL、恢复、回滚基准与并发写入用例全过。

**回滚**：还原组提交、并行检查点与顶点装入相关文件。

**不做**：不做跨机复制、在线迁移与静默截断。

---

## 阶段间的硬门槛

- 阶段一未把两个秒级用例压下来之前，不做分区放行，也不用图算法用例转移焦点。
- 阶段四的字段未与 runner JSON 对齐之前，不以 EXPLAIN 文本作为性能结论。
- 阶段六之前不把 Linkrs 方言用例计入三方数值对比。
- 阶段七只有在阶段一到六的查询数值全部稳定后才启动。
- 任一阶段的数值回归立即停止该阶段，先补反例再继续。

## 当前状态与后续收敛

截至 2026-11-23，阶段一的原始秒级用例已由 1.1–1.5 秒降到约 90–120 ms，typed 分组计数和分区局部 TopK 均已在 PROFILE 中确认生效；阶段二的两跳与变长计数已降到约 6 ms；阶段三的过滤计数已降到约 1.2 ms。详细证据见 `docs/issue/linkrs-remaining-parity-issues.md` 第 35 节。

阶段一的“秒级瓶颈”已消除，但相对 Ladybug 仍约 15–30 倍，且收益依赖 benchmark 显式放行并行，生产默认配置未启用。因此首条硬门槛按原始字面已满足，按下一阶段 20 ms / 15 ms 目标仍未闭环。后续不重新划分阶段，也不改写上述历史目标；针对阶段一、二的收敛实施与生产配置更新写入 `docs/plan/stage1-stage2-current-gap-remediation.md`，该文件继承本方案的护栏与不做项。

首轮回测已于 2026-11-23 在 devs 完成：release 构建与 partitioning / typed group / local topk / parallel / DQL / storage 全绿，生产默认已切到 `workers=8, max_partitions=8, allow_ordered_parallel_expand=true`。固定门中两条阶段一用例仍在约 100–130 ms，未达 40 ms / 30 ms 中间门；阶段二两跳约 6.2 ms，未达 4 ms。新增自耗时证据显示扫描读取与展开读取合计占主导，后续按问题清单第 37 节转入扫描枚举/可见性与目的端属性读取；不得因配置收益而宣称算子目标闭环。
