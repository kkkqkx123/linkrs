# 条件合并与配置更新完整实现设计方案

本文针对此前保留的两处显式拒绝给出是否完整实现的决策与设计方案。
约束保持不变：只修改原有模块，不新建替代模块；
中文写文档，代码与注释保持英文且不引用本文档结构编号。

## 1. 背景与问题

合并语句携带动作子句时规划器产生条件选择节点，
而流式装配层显式拒绝该节点类型。
无动作的合并走存在则跳过的插入路径，可正常执行。
边模式携带动作子句此前走纯插入路径属于静默丢弃，
现已改为规划期显式拒绝。

配置更新语句解析通过但规划层无对应分支，
最终以不支持操作显式失败。
展示配置语句仅返回占位行，不反映真实配置存储。

两处均为响亮失败而非静默错误，符合误用抵抗要求，
但用户文档已按可用形态记载合并动作语义与配置更新示例，
构成文档与实现偏差，必须二选一：完整实现或修正文档。
本方案决策为两者均完整实现，但实现厚度不同。

## 2. 是否需要完整实现

合并条件执行需要完整实现。理由是其属于核心写入语义，
两家参考项目均支持，文档已给出点边示例与幂等承诺。
裸合并加后续独立更新不能替代原子语义，
并发下探查与写入分离会产生重复数据。
显式拒绝只能作为过渡，不能作为终态。

配置更新需要完整实现，但走薄实现。
理由是文档已承诺查询内配置形态，且嵌入式与网络服务共用同一查询引擎，
仅靠服务层管理接口无法覆盖嵌入式场景。
但配置变更属于全局副作用，不适合走图数据流式算子，
应复用服务层已有的校验、持久化与重启语义，而非在查询引擎内另建一套。

优先级上合并先于配置。合并是数据面正确性缺口，
配置是管理面便利性缺口。

## 3. 合并条件执行设计

现状是规划器对点模式产生条件选择节点，
条件为存在性探查，分支为更新或插入加更新。
装配层对该节点无条件拒绝。
分支体所需的写入能力均已存在，
包括存在则跳过的插入、按替换或合并的更新、空映射清空。
缺失的仅是条件求值与分支二选一的编排。

方案对比有两种。流式条件算子方案为新增条件分支规约与运行时算子，
按数据块逐行路由到不同分支。该方案通用性强，
但合并的判定本质是标量存在性探查而非逐行路由，
当前条件选择节点亦无数据输入子节点，仅有分支与 detached 参数尾，
为其补齐逐行路由属于过度设计，且输出列名在分支间并不一致，
需要额外的并集对齐。

推荐采用管线层标量条件编排。规划器维持现状，继续产生条件选择节点，
装配层不再直接拒绝，而是由管线编译层识别该节点并走专用合并执行路径。
执行过程限定在同一事务快照内分两步：
先对合并模式做存在性探查，再按探查结果编译并执行被选中的分支计划。
分支计划的编译复用已有的物理计划构造能力，
分支的执行复用已有的插入与更新写入算子，
包括整映射覆盖标记与空映射语义。
无动作合并保持现有插入路径不变，避免回归。

各层改动限定在原有模块内：
解析与绑定层不变，裸集合子句合并进两条分支的语义保持；
规划层不变，点边模式统一产生条件选择结构，
边模式携带动作不再拒绝，随管线编排一并获得支持，
此前为防静默而加的显式拒绝在编排落地后移除；
管线层新增标量条件编排，负责探查求值、分支选择、分支计划编译与顺序执行，
以及插入与更新两种输出列名的统一；
执行层无需新增算子类型，不触及数据块路由。

事务语义上探查与分支执行必须在同一事务作用域内完成，
探查使用执行上下文的事务快照，分支执行沿用同一作用域，
避免探查与写入之间出现并发插入导致的重复创建。
输出上无论走匹配分支还是创建分支，均返回统一的受影响行描述，
不再透出内部分支的插入与更新列名差异。

## 4. 配置更新设计

现状是解析器仅接受单项赋值形态，绑定层透传，
规划层路由到维护规划器但无对应分支，
执行层无对应节点与算子，展示配置返回占位行。
服务层管理接口已具备完整的配置读写能力，
包括按节取值、类型解析、是否需要重启的判定、持久化与回滚。

方案对比有两种。查询引擎内完整规划执行方案需要新增配置更新节点、
计划规约、算子类型与执行器，并把全局配置句柄 plumbing 到查询与执行上下文。
该方案层间耦合最重，且容易与服务层的持久化与重启语义分叉。

推荐采用意图加服务应用的薄实现。
查询引擎仅负责语法解析、表达式求值与意图构造，
不直接触碰全局配置存储。
管线层对配置更新语句仿照分析语句走 bypass 路径，
在规划前求值配置表达式并构造结构化意图，
意图携带模块名、配置名与求值后的标量值。
网络服务层收到意图后调用既有的配置更新能力，
复用取值校验、类型解析、持久化、重启标记与回滚语义。
嵌入式场景由宿主按同样语义应用意图，查询引擎不内嵌存储路径。

各层改动限定在原有模块内：
解析层不变，维持单项赋值约束，不引入多项逗号形态；
绑定层维持透传，不做语义改写；
管线层新增 bypass 分支，负责表达式求值与意图构造，
求值失败按执行错误返回；
服务层新增意图应用入口，复用既有管理接口的校验与持久化逻辑，
不另建配置写入通道；
展示配置的占位实现随本工作一并修正为读取真实配置存储，
模块参数透传而非忽略，未知模块返回明确错误。

权限与作用域上配置更新走直接写路径分类，
沿用现有的管理操作鉴权，不经过只读快照与计划缓存。
模块词汇与服务层节名保持一致，文档中写明对应关系。
需要重启的配置项返回明确的重启标记而非静默生效。

查询内配置形态仍不新增，维持已有评估结论。
参考项目的逐项配置调用对应本项目的独立配置更新语句，
表函数调用与配置设置职责分离。

## 5. 测试与验收

合并侧在现有解析单测之外新增执行用例：
点模式匹配分支与创建分支分离用例，
边模式匹配分支与创建分支分离用例，
裸集合子句同时作用于两条分支的对照用例，
空映射清空行为用例，
整映射覆盖与逐项合并的对照用例，
并发幂等用例，以及未知标签与缺失主键等错误形态用例。
每个用例验证写入后读取的完整属性集合，而不仅是被写入项。

配置侧新增用例覆盖合法更新与读取回显、
未知模块与未知配置名的明确拒绝、
类型不匹配的明确拒绝、表达式求值失败的拒绝、
需要重启项的标记返回、持久化后重启可读、
以及无权限主体的拒绝行为。
展示配置用例覆盖无模块、有模块与未知模块三种形态。

回归范围包括存在性子查询、合并写入、导入链路、
全文与向量检索、集合运算与递归公用表表达式，
确认条件编排与配置 bypass 未扩散到常规读写路径。
同一工作包的用例一次性补齐后统一运行，合并为尽量少的完整运行次数。

## 6. 风险与回退

合并的主要风险是探查与分支执行不在同一快照，
通过管线层强制同一事务作用域控制。
次要风险是条件变量未绑定到输入行，
标量编排通过探查语句自包含求值规避，不依赖 detached 参数尾。
输出列名不一致通过管线层统一封装控制，不透出分支差异。

配置的主要风险是全局副作用与重启语义不清，
通过复用服务层既有语义与重启标记控制。
次要风险是模块词汇分叉，通过文档对应关系与未知模块拒绝控制。

回退方式均为 revert 管线层编排与 bypass 分支，
恢复显式拒绝行为。规划器产生的条件选择结构保留，
解析层加法不受影响，已有无动作合并与展示配置占位行为不受回退牵连。
