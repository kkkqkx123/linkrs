# 有意保留的弱类型说明

本文列出后端弱类型治理后仍然保留动态表示的位置，说明每处保留的理由。判断标准只有一条：动态性来自业务本质而非标注缺失的，保留；标注缺失导致前端类型丢失的，已经修复，不在此列。

## 受限属性值模式

查询行、查询参数、会话变量、批量标识与属性映射、向量载荷、会话变量快照、配置值、属性缺省值等字段，运行时类型仍为通用 JSON 值，模式层通过受限属性值模式给出候选分支。

保留理由是属性值本质无模式。图的属性名由用户建模决定，后端无法预先枚举；查询返回的列同样由语句决定。受限模式只收敛文档形状，不改变线路形状：大整数经前端大整数路径按字符串到达，时间与二进制按字符串到达的约定保持不变。前端据此使用统一的行与单元格类型，而不是每个页面各自定义一次。

涉及的位置包括查询请求与批量请求的绑定参数、查询结果行、游标分页行、批量顶点与边的标识与属性、向量点的载荷、会话变量快照与赋值回执、配置单项值与属性缺省值。这些位置的未知类型是合理的，前端不应再做二次裸转。

## 迁移计划体与历史条目

迁移计划响应中的计划体本身是引擎生成的动态 JSON，历史记录中的历史条目数组同理。外层信封已有固定类型，内层保持通用值是合理的，因为计划体的结构随版本规则演进，逐字段建模只会制造虚假的稳定性承诺。

## 全文索引列表

全文索引列表与不一致索引列表的元素为通用值。保留理由是索引描述符跨越多种引擎实现，字段含义随引擎而异，统一建模会丢失信息或频繁变更。外层同样已有固定信封。

## 流式、文本与二进制载荷

查询流与迁移进度流为事件流，导出下载为二进制，指标端点为纯文本格式。这些通道在开放协议里本来就不该有 JSON 响应体，前端保持原始请求解析。开放协议中出现的空结构对应的是事件流的内容类型，不是缺失的类型。

## 状态码契约

用户创建与启停与授权、会话删除等接口以状态码本身为契约，响应体为空是正确的。不应为满足类型完整而补充无意义的数据传输对象。

## 图数据详情

网页控制台的顶点与边详情、邻居列表返回属性映射，运行时为通用值是合理的，理由同受限属性值模式：属性名由用户建模决定。但这些接口的外层信封仍有收敛空间，见同期遗留任务分析。
