# 编译服务器性能基准测试设计方案

## 1. 概述

目标是在编译服务器（`ssh devs`）上建立可重复的性能基准测试环境，用于替代本地 WSL2 环境的性能测量（本地 CPU 虚拟化、核数少、干扰大，不适合出性能数字）。

暂定路线：**本地编译基准可执行文件，scp 复制到编译服务器后执行**。编译服务器不安装 Rust 工具链，保持基准环境干净。本方案已完成服务器现状摸底与目录创建，并给出隔离与控制手段。

## 2. 服务器现状（已实测）

| 项目 | 结论 |
|------|------|
| 主机 | `itc`，Ubuntu 18.04，内核 4.15，x86_64 |
| CPU | 2 × Xeon E5-2667 v3，8 核 16 线程每颗，共 32 逻辑 CPU，基准频率 3.2GHz，均支持 AVX2 |
| NUMA | 2 节点，node0：0-7,16-23；node1：8-15,24-31，跨节点距离 21，节点内 10 |
| 超线程配对 | 0-16、1-17 …… 7-23（node0），8-24 …… 15-31（node1） |
| 内存 | 31GB（node0 约 15.9GB，node1 约 16.1GB），当前空闲充足 |
| 磁盘 | `/data` 9.1T，共用 918G，可用 7.7T |
| 目录 | `/data/kkkqkx/linkrs` 已创建，含 `bin/`、`data/`、`results/`、`scripts/` 四个子目录 |
| 工具 | 有 `taskset`、`numactl`、`chrt`；无 `perf`、`cpupower`、`docker`、`cset`；无 Rust 工具链 |
| 权限 | 当前用户 `itc` 无 sudo（需密码），cpuset 不可写，`systemd-run --user` 不可用，只能做软隔离 |
| 常驻干扰 | rabbitmq、mongod 常驻，后台负载低但存在；当前 3 用户在线，为共享编译服务器 |
| 中断分布 | 中断集中在 CPU0、CPU1、CPU10、CPU31，应避开这些核跑基准 |
| 频率策略 | 32 核全部 `powersave`，无 root 无法切换，频率抖动是当前最大误差源 |
| ASLR | 全局开启（值为 2），无 root 时只能对单个进程关闭 |
| 内核版本 | 4.15，无 io_uring，涉及异步 IO 的基准口径需注意与本地高版本内核的差异 |
| 网络 | 本地到服务器 scp 已验证可用 |

本地构建机为 Arch Linux（glibc 2.44，WSL2，5 核 i5-8250U），与服务器 glibc 2.27 不兼容，见第 4 节。

## 3. 远端目录规划

```
/data/kkkqkx/linkrs/
├── bin/        # 从本地 scp 来的基准可执行文件，按版本分子目录存放
├── data/       # 基准数据集（与仓库 benches/data 对应，按需同步）
├── results/    # 每次运行的原始输出与基线对比，按日期加 git short sha 命名
└── scripts/    # 运行封装脚本（前置检查、绑核启动、结果归档）
```

二进制与结果按版本隔离存放，避免新版本覆盖旧基线。数据集与二进制版本对应关系记录在结果目录的说明文件中。

## 4. 构建与分发

### 4.1 关键阻塞：glibc 不兼容

本地 Arch 的 glibc 2.44 编出的动态链接二进制，在服务器 glibc 2.27 上无法运行（高版本 glibc 符号在低版本上不存在）。**暂定方案的“本地编译后直接 scp”必须先解决此问题，否则二进制起不来。**

### 4.2 构建方式对比

第一推荐是 musl 静态构建。在本地加装 musl 目标后以静态方式编译基准，产物不依赖远端 glibc，可直接在 Ubuntu 18.04 上运行，无需服务器做任何配合。代价是首次需配置 musl 工具链，且个别依赖 C 库的特性需验证。

第二备选是旧版本容器构建。用与服务器同代的系统镜像做构建，产物 glibc 基线与服务器一致，兼容性最稳。但本地需可用的容器运行时，当前链路未经验证。

第三是不推荐的远端直接编译。在服务器上安装 Rust 后编译虽然不存在兼容问题，但编译过程本身占用 CPU 与磁盘，会污染基准环境，且与“服务器只跑基准”的定位冲突。

结论：默认走 musl 静态构建路线；若 musl 下个别基准依赖受限，再对该基准单独采用容器构建。

### 4.3 产物形态

各包基准均为 `harness = false` 的 criterion 基准，`cargo bench` 实际产出的是 `target/release/deps/` 下自带 main 的可执行文件。远端运行时不需要 cargo 与 Rust，直接执行该二进制即可，支持 criterion 自带的参数（如按名称过滤用例、保存基线）。同步时连同数据集一起复制，保证版本对应。

### 4.4 编译配置

仓库当前基线为 x86-64 通用编译加运行时分发，向量距离内核按实测能力选择实现。本地 i5-8250U 与服务器 E5-2667 v3 均支持 AVX2，因此同一份基线二进制在两边都能跑且自动用上 AVX2 路径，无需为服务器单独调编译参数。如需对比编译期特化的收益，可额外以 native 参数编一版做对照轮，不作为默认口径。

每次发布二进制时记录编译器版本、编译参数、git 提交与产物校验信息，与基准结果同目录存放，保证结果可追溯。

## 5. CPU 与内存隔离设计

### 5.1 分配原则

基准独占一个 NUMA 节点，把操作系统、常驻服务、中断与他人编译任务留在另一个节点。禁止基准跨 NUMA 节点运行，避免远端内存访问引入固定延迟差。

### 5.2 推荐分配

默认配置独占整个 node1，即逻辑 CPU 8-15 与 24-31，共 16 线程，内存绑定 node1。node0 留给系统、rabbitmq、mongod 与其他用户，且中断重灾区（CPU0、1、10、31）全部落在保留侧之外或非基准核上。

纯物理基线取 node1 的 8 个物理核（8-15），不使用其超线程兄弟（24-31），用于排除超线程争抢的干净对照。

冒烟测试取其中 4 核（8-11），用于快速验证二进制可运行性，不出正式数字。

多线程扩展性测试在上述集合内逐级放开核数，观察加速比拐点。

### 5.3 绑定手段（无 root 可用）

以 numactl 同时约束 CPU 节点与内存节点，再以 taskset 限定具体核列表。两者叠加使用，numactl 保证内存本地性，taskset 保证核列表精确。启动前用 numactl 硬件信息确认节点划分未变化。

## 6. 无 root 现状下的控制手段

以下为当前权限可实际执行的控制，按重要性排序。

亲和性与内存绑定：按第 5 节执行，这是最有效的隔离，现状完全可用。

单进程 ASLR 关闭：用 setarch 对单个基准进程关闭地址随机化，减少尾延迟抖动，无需 root。

优先级：普通用户只能把 nice 值调大（降低自己优先级），无法调小或使用实时调度。现状不要指望靠 nice 抢占资源，保证独占核才是正道，chrt 实时优先级需特权，当前不可用，如实记录即可。

环境变量：保持仓库约定的单线程测试配置，避免基准进程内部线程数失控；并行扩展基准由用例自身控制线程数，不受该变量干扰。

前置检查：运行前检查系统负载、在线用户与高占用进程，负载高于阈值或有他人编译任务在跑时等待或告警，不强行出数。频率策略只能读取不能修改，每次运行把当前策略与实测频率记录进结果，作为误差分析依据。

缓存与磁盘：无 root 无法清理页缓存，改用每次运行使用新数据目录、启动前同步写入、criterion 自带预热轮次来收敛缓存状态。数据集放在同一块磁盘的固定目录，避免跨盘差异。

统计方法：依赖 criterion 自带的预热加测量窗口，同一配置跨进程重复运行取中位数，异常单轮直接丢弃重跑，不合并不同日期、不同负载下的数字。

## 7. 需要 root 的硬隔离（未来工作，需管理员配合）

以下手段现状不可用，列为后续申请管理员配合事项：把基准核划入专用 cpuset 并禁止其他任务迁入；内核启动参数隔离基准核并减少时钟中断干扰；把频率策略切为 performance 或锁定固定频率；把磁盘与网卡中断亲和性迁出基准核；运行前清理页缓存与交换；安装 perf 用于采样分析；约定基准专用时间窗口，窗口内暂停其他编译任务。其中频率锁定一项收益最大，应优先申请。

## 8. 标准运行流程

本地按选定构建方式编译并确认产物版本信息；将二进制与对应数据集同步到远端版本化子目录；远端执行前置检查，不满足阈值则等待；按第 5 节绑核启动，单进程可附加关闭 ASLR；运行冒烟子集确认通过后再跑全量；将原始输出、环境快照（核列表、频率策略、负载、内存节点信息）与版本信息归档到结果目录；回传结果摘要，原始文件留存远端。

## 9. 结果收集与回归口径

原始输出与按包归档的文本报告保留在远端结果目录，本地只回传摘要与结论。回归判断以 criterion 基线对比为准，锚定查询延迟类阈值作为优化工作的基线门。跨版本对比只允许在同核集、同内存节点、同构建方式下进行，任一条件变化则单独标注，不直接对比数字。

## 10. 风险与后续工作

最大风险是频率策略不可控导致的误差，其次是共享服务器上他人任务的偶发干扰，需以严格的前置检查与重复测量对冲。glibc 兼容性需在首次同步前验证 musl 产物可运行。后续工作依次为验证 musl 构建链路、补齐运行封装脚本、申请频率策略与 cpuset 权限、引入 perf 采样。内核 4.15 与本地高版本内核的 IO 路径差异需在解读存储层数字时单独说明。
