# 存储设计决策差异分析

## 概述

本文档对比分析 Ladybug（ref/ladybug）与当前项目（linkrs）在节点、节点属性、边、边属性存储结构上的设计决策差异。这些差异反映了不同的设计目标和权衡，而非简单的实现缺陷。

---

## 1. 节点存储决策差异

### 1.1 行组 vs 分片

| 方面 | Ladybug | 当前项目 |
|------|---------|----------|
| **结构** | NodeGroup → ChunkedNodeGroup → ColumnChunk → ColumnChunkData | ShardedVertexTable → VertexTable → ColumnStore → Column |
| **组织方式** | 固定大小行组（默认 NODE_GROUP_SIZE） | 动态分片（基于 CPU 并行度，最多 256 分片） |
| **并发模型** | 行组级别并发 | 分片级别并发 |

**决策分析**：

- **Ladybug 选择行组**：适合大表的高效批量扫描和压缩，行组作为压缩和刷盘的基本单元。适合读密集型场景。
- **当前项目选择分片**：通过 `fxhash(external_id) & (num_shards - 1)` 路由，支持高并发写入。适合写密集型场景。

**结论**：这是合理的设计决策差异。当前项目优先考虑并发写入性能，Ladybug 优先考虑扫描效率。

### 1.2 内部 ID 编码

| 方面 | Ladybug | 当前项目 |
|------|---------|----------|
| **类型** | `uint64_t` 全局唯一偏移量 | `u32` 内部 ID，编码为 `(segment << 12) | slot` |
| **空间** | 8 字节 | 4 字节 |
| **限制** | 理论上支持 2^64 节点 | 每分片最多 4096 槽位，跨分片交织 |

**决策分析**：

- **Ladybug 的 uint64_t**：简单直接，无槽位限制，但占用更多内存。适合超大规模数据。
- **当前项目的编码**：更紧凑（4 字节 vs 8 字节），但 `(segment << 12) | slot` 编码有 4096 槽位限制。跨分片交织设计使得全局 ID 仍保持唯一性。

**结论**：这是权衡决策。当前项目牺牲了单分片容量换取内存效率。在中小规模数据下（<10 亿节点）是合理的选择。

### 1.3 主键索引

| 方面 | Ladybug | 当前项目 |
|------|---------|----------|
| **数据结构** | ART（自适应基数树）或 Hash 索引 | `HashMap<IdKey, u32>` + `Vec<Option<IdKey>>` |
| **持久化** | 支持磁盘持久化（art_index_disk.cpp） | 仅内存，崩溃后需重建 |
| **懒加载** | IndexHolder 延迟加载 | 无 |

**决策分析**：

- **Ladybug 的 ART 索引**：支持前缀扫描和范围查询，可持久化到磁盘，崩溃恢复快速。
- **当前项目的 HashMap**：实现简单，O(1) 查找，但不支持范围查询，且崩溃后需从列数据重建。

**结论**：这是当前项目的一个设计短板。HashMap 方案在功能和可靠性上不如 ART 索引，但实现复杂度更低。

## 2. 节点属性存储决策差异

### 2.1 版本管理位置

| 方面 | Ladybug | 当前项目 |
|------|---------|----------|
| **位置** | Vector 级别（VersionInfo） | Column 级别（每列维护版本链） |
| **粒度** | 每个向量（默认 1024 行）一个版本记录 | 每行每列独立版本链 |
| **开销** | 低（向量化管理） | 高（每列维护 `row_start_ts` + `version_chains`） |

**决策分析**：

- **Ladybug 的 Vector 级版本**：批量管理版本，内存开销小，适合高吞吐场景。但粒度较粗，单行更新需标记整个向量。
- **当前项目的 Column 级版本**：细粒度控制，支持单行单列精确更新。但每个 Column 维护 `VersionEntry { start_ts, end_ts, value }` 链表，内存和 CPU 开销大。

**结论**：当前项目的细粒度 MVCC 设计增加了复杂度和开销。对于大多数场景，向量化版本管理已足够。

### 2.2 压缩策略

| 压缩类型 | Ladybug | 当前项目 |
|----------|---------|----------|
| **ALP（浮点）** | 支持 | 支持 |
| **BitPacking（整数）** | 支持 | 支持 |
| **Constant（常量）** | 支持 | **不支持** |
| **FSTT（字符串）** | 不支持 | 支持 |
| **Dictionary** | 支持 | 支持 |
| **RLE** | 支持 | 支持 |

**决策分析**：

- **Ladybug 缺少 FSTT**：FSTT（Fast Simple Symbol Table）对字符串压缩效果更好，特别是短字符串场景。
- **当前项目缺少 Constant**：当列中 99%+ 值相同时，Constant 压缩可将存储从 O(n) 降至 O(1)。

**结论**：当前项目缺少 Constant 压缩是一个功能缺失。FSTT 是当前项目的优势。

### 2.3 元数据丰富度

| 方面 | Ladybug | 当前项目 |
|------|---------|----------|
| **元数据结构** | ColumnChunkMetadata（PageRange, CompressionMetadata） | ColumnStats（min/max/null_count/distinct_count） |
| **压缩元数据** | 包含压缩类型、ALP 参数、min/max 边界 | 仅压缩类型和统计信息 |
| **Zone Map** | 每个 ColumnChunk 有 min/max 统计 | 每 1024 行一个 ZoneBounds |

**决策分析**：

- **Ladybug 的丰富元数据**：支持更精确的谓词下推和压缩优化决策。
- **当前项目的简单统计**：实现简单，但可能错过一些优化机会。

**结论**：这是实现复杂度的权衡。当前项目的元数据足以支持基本的谓词下推。

## 3. 边存储决策差异

### 3.1 CSR 实现

| 方面 | Ladybug | 当前项目 |
|------|---------|----------|
| **结构** | 标准 CSR：偏移数组 + 长度数组 + 节点分组 | 主块 + 溢出块：`MutableCsr` 两级设计 |
| **内存布局** | `offsets[v]` → `edges[start..start+length]` | 主块扁平数组 + `HashMap<u32, Vec<Vec<Nbr>>>` 溢出 |
| **复杂度** | 低（标准实现） | 高（溢出块、OverflowIndex、SequentialRun 检测） |

**决策分析**：

- **Ladybug 的标准 CSR**：简单高效，内存连续，缓存友好。但动态边操作需要重新组织。
- **当前项目的两级设计**：支持高效的动态边添加（避免频繁重分配），但增加了复杂度和碎片化风险。

**结论**：当前项目的溢出块设计增加了实现复杂度。对于写密集场景有一定优势，但可能带来碎片化问题。

### 3.2 拓扑-属性耦合

| 方面 | Ladybug | 当前项目 |
|------|---------|----------|
| **CSR 条目** | 仅存边 ID（轻量级） | `Nbr` 结构体：endpoint + rank + edge_id + delete_ts + prop_offset |
| **属性访问** | 通过 CSR 偏移直接访问属性列 | 通过 `prop_offset` 查找 PropertyTable |
| **遍历开销** | 低（仅加载拓扑） | 高（加载包含属性偏移的 Nbr） |

**决策分析**：

- **Ladybug 的分离设计**：CSR 仅存储轻量级边 ID，属性在独立列中按需读取。遍历时只加载拓扑数据，属性读取延迟到需要时。
- **当前项目的耦合设计**：`Nbr` 结构体包含 `prop_offset`，将拓扑和属性访问耦合在一起。遍历时必须加载完整的 Nbr（24 字节），即使不需要属性。

**结论**：当前项目的耦合设计增加了遍历开销。Ladybug 的分离设计更优。

### 3.3 MVCC 粒度

| 方面 | Ladybug | 当前项目 |
|------|---------|----------|
| **边级别** | VersionInfo 向量化管理 | 每个 Nbr 有 `delete_ts` |
| **属性级别** | Column 级别版本链 | PropertyTable 行级时间戳 |
| **开销** | 低（批量管理） | 高（每边每属性独立追踪） |

**决策分析**：

- **Ladybug 的向量化 MVCC**：批量管理版本，内存开销小。删除操作标记向量级别，适合批量删除。
- **当前项目的细粒度 MVCC**：每个 Nbr 有 `delete_ts`，PropertyTable 有 `row_create_ts` + `row_delete_ts`。支持精确的单边单属性版本控制，但开销大。

**结论**：当前项目的细粒度 MVCC 设计增加了复杂度和开销。对于大多数场景，向量化 MVCC 已足够。

## 4. 边属性存储决策差异

### 4.1 属性访问路径

| 方面 | Ladybug | 当前项目 |
|------|---------|----------|
| **存储位置** | RelTableData 内的 Column 列 | 独立的 PropertyTable |
| **行映射** | 通过 CSR 偏移直接访问（O(1)） | `HashMap<EdgeId, u32>` 映射（均摊 O(1)） |
| **缓存友好** | 高（连续内存访问） | 低（HashMap 随机访问） |

**决策分析**：

- **Ladybug 的直接偏移**：CSR `offsets[v]` 直接指向属性列的起始位置，O(1) 时间访问，内存连续，缓存友好。
- **当前项目的 HashMap 映射**：需要先通过 `edge_prop_map: HashMap<EdgeId, u32>` 查找 `prop_offset`，然后访问 PropertyTable。HashMap 访问有随机性，缓存不友好。

**结论**：当前项目的 HashMap 映射方案在性能上不如 Ladybug 的直接偏移方案。

### 4.2 空闲空间管理

| 方面 | Ladybug | 当前项目 |
|------|---------|----------|
| **策略** | 标记删除 + 重写 | `free_list` 回收机制 |
| **复杂度** | 低 | 高（`TieredTombstoneManager` + `free_list`） |
| **空间效率** | 低（标记删除后空间不立即释放） | 高（回收空闲槽位） |

**决策分析**：

- **Ladybug 的简单策略**：删除操作仅标记，空间在 checkpoint 时通过重写释放。实现简单，但可能造成临时空间浪费。
- **当前项目的回收机制**：`free_list` 立即回收空闲槽位，`TieredTombstoneManager` 分层管理墓碑。空间效率高，但实现复杂。

**结论**：这是合理的设计决策。当前项目的回收机制在空间效率上更优，适合长期运行的场景。

### 4.3 二级索引

| 方面 | Ladybug | 当前项目 |
|------|---------|----------|
| **索引** | 无专门机制 | `PropertyValueIndex`：`HashMap<prop_name, HashMap<encoded_value, HashSet<u32>>>` |
| **用途** | 依赖列扫描 | 支持属性值快速查找 |

**决策分析**：

- **Ladybug**：不提供属性值索引，依赖列扫描和谓词下推。
- **当前项目**：提供 `PropertyValueIndex`，支持按属性值快速查找边。

**结论**：当前项目的二级索引是功能优势，但增加了写入开销和内存使用。

## 5. 磁盘格式决策差异

### 5.1 文件组织

| 方面 | Ladybug | 当前项目 |
|------|---------|----------|
| **粒度** | 每个表一个文件 | 每个分片/边类型多个文件（meta.bin, columns.bin 等） |
| **管理** | 简单（单文件） | 复杂（多文件 + Section ID） |
| **压缩** | 页级压缩 | zstd 页压缩 + 列编码 |

**决策分析**：

- **Ladybug 的单文件**：管理简单，原子性好，但文件可能很大。
- **当前项目的多文件**：支持更细粒度的备份和恢复，但增加了管理复杂度。

**结论**：这是合理的设计决策。当前项目的多文件方案更灵活，适合运维场景。

### 5.2 崩溃恢复

| 方面 | Ladybug | 当前项目 |
|------|---------|----------|
| **机制** | WAL + ShadowFile（COW） | WAL + 原子重命名（shadow file） |
| **索引持久化** | 支持（ART 索引可持久化） | **不支持**（主键索引和属性索引不持久化） |

**决策分析**：

- **Ladybug**：完整的崩溃恢复机制，索引可持久化，崩溃后快速恢复。
- **当前项目**：WAL 保证数据持久性，但索引不持久化，崩溃后需全表扫描重建。

**结论**：当前项目的索引不持久化是设计短板，影响崩溃恢复性能。

## 6. 总结

### 6.1 合理的设计决策差异

| 差异 | 当前项目选择 | Ladybug 选择 | 适用场景 |
|------|-------------|-------------|----------|
| **并发模型** | 分片（Sharding） | 行组（NodeGroup） | 当前项目适合写密集；Ladybug 适合读密集 |
| **边属性隔离** | 独立 PropertyTable | 嵌入 RelTableData | 当前项目更灵活；Ladybug 更紧凑 |
| **版本管理** | Column 级版本链 | Vector 级 VersionInfo | 当前项目更精确；Ladybug 更高效 |
| **空闲空间** | free_list 回收 | 标记删除+重写 | 当前项目空间效率更高 |
| **二级索引** | PropertyValueIndex | 无 | 当前项目查询能力更强 |

### 6.2 当前项目的设计短板

| 短板 | 影响 | 严重程度 |
|------|------|----------|
| **主键索引不持久化** | 崩溃恢复慢，大规模数据不可用 | 高 |
| **属性访问路径间接**（HashMap 映射） | 性能开销，缓存不友好 | 中 |
| **CSR 溢出块设计** | 复杂度高，可能碎片化 | 中 |
| **拓扑-属性耦合**（Nbr 结构体） | 遍历时加载不必要的属性偏移信息 | 中 |
| **细粒度 MVCC 开销** | 每属性列维护版本链，内存和 CPU 开销大 | 中 |
| **缺少 Constant 压缩** | 高重复值列空间浪费 | 低 |

### 6.3 Ladybug 的优势

1. **标准 CSR 实现**：简单高效，内存连续，缓存友好
2. **拓扑-属性彻底分离**：遍历时只加载轻量级拓扑数据
3. **向量化版本管理**：批量管理版本，内存开销小
4. **索引持久化**：崩溃后快速恢复
5. **丰富的压缩元数据**：支持更精确的谓词下推

### 6.4 当前项目的优势

1. **高并发写入**：分片设计支持多线程并发写入
2. **灵活的边属性管理**：独立 PropertyTable 支持更灵活的属性操作
3. **FSTT 字符串压缩**：对短字符串压缩效果更好
4. **二级属性索引**：支持按属性值快速查找边
5. **细粒度空间回收**：free_list 立即回收空闲槽位

## 7. 建议的改进方向

基于以上分析，当前项目可考虑以下改进：

1. **主键索引持久化**：实现 ART 或 Hash 索引的磁盘持久化
2. **属性访问路径优化**：将 HashMap<EdgeId, u32> 替换为数组+偏移方案
3. **CSR 结构简化**：评估溢出块设计的必要性，考虑标准 CSR
4. **拓扑-属性分离**：将 Nbr 结构体简化为仅存 edge_id，属性访问延迟到需要时
5. **MVCC 优化**：评估 Column 级版本链的必要性，考虑向量化版本管理
6. **添加 Constant 压缩**：对高重复值列使用 Constant 压缩

这些改进需要在性能、复杂度和功能之间进行权衡，建议分阶段实施。
